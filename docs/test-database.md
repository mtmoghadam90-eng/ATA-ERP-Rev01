# یک نسخهٔ آزمایشی از دیتابیس

هدف: بتوانید با داده‌های واقعی کار کنید، هر چیزی را امتحان کنید، و دیتابیس اصلی
دست‌نخورده بماند.

---

## چرا «کاربر تست» جواب نمی‌دهد

خواستهٔ طبیعی این است: «اگر با یوزر تست وارد شدم، اطلاعات در دیتابیس تست ذخیره
شود». این کار **نباید** انجام شود، و دلیلش معماری نیست، ایمنی است.

یک پروسهٔ برنامه یک اتصال به دیتابیس دارد (`getDb()` عمداً یکی است — pool مال
همان یک client است و یک client به ازای هر request، SQL Server را تمام می‌کند).
برای مسیریابی بر اساس کاربر باید هر درخواست تصمیم بگیرد به کدام دیتابیس بنویسد؛
و آن‌وقت **یک باگ در همان تصمیم یعنی نوشتن تست روی دیتابیس واقعی**. آن باگ هم
بی‌صدا است: هیچ خطایی نمی‌دهد، فقط یک رکورد آزمایشی وسط داده‌های واقعی می‌نشیند.

راه درست ساده‌تر و امن‌تر است: **یک نسخهٔ دوم از خود برنامه، روی یک پورت دیگر،
با `DATABASE_URL` متفاوت.** هیچ منطق مسیریابی وجود ندارد چون هیچ تصمیمی گرفته
نمی‌شود — پروسهٔ تست فقط *یک* دیتابیس می‌شناسد و آن هم کپی است. برای وارد شدن به
محیط تست، آدرس دیگری باز می‌کنید:

| | آدرس | دیتابیس |
|---|---|---|
| اصلی | `http://192.168.1.104:3000` | `ata_erp` |
| تست | `http://192.168.1.104:3100` | `ata_erp_test` |

---

## ⚠️ مهم‌ترین نکته: کپی، خودش پیامک می‌فرستد

یک دیتابیس restore‌شده هنوز «دیتابیس تست» نیست — **همان دیتابیس اصلی است با یک
اسم دیگر**. و این برنامه به‌محض بالا آمدن، خودش کارهایی می‌کند:

- یک `setInterval` یک‌دقیقه‌ای صف پیام‌ها را خالی می‌کند. هر پیامی که در کپی صف
  شده باشد **واقعاً فرستاده می‌شود** — پیامک، بله یا ایمیل — به شمارهٔ واقعی
  مشتری واقعی، چون کپی همان شماره‌ها را دارد.
- جاروی ورک‌فلو در اولین ورود روزانه اجرا می‌شود و روی هر رکوردی که از موعدش
  گذشته وظیفه می‌سازد و **پیام بیشتری در صف می‌گذارد**.

پس اولین کاری که با یک کپی می‌کنید این است که ارسال را خاموش کنید — و «یادم
می‌ماند» مکانیزم نیست. `npm run db:prepare-test` مکانیزم است.

## مرحله به مرحله (روی سرور)

### ۱. ساخت کپی

```powershell
powershell -ExecutionPolicy Bypass -File E:\Apps\ATA-ERP-Rev01\scripts\copy-to-test-db.ps1 `
    -SqlUser ata_app -SqlPassword <رمز>
```

`BACKUP` با `COPY_ONLY` (زنجیرهٔ بکاپ واقعی دست نمی‌خورد) و بعد `RESTORE` با
اسم جدید و فایل‌های جابه‌جا شده. از دیتابیس اصلی فقط **خوانده** می‌شود.

اسکریپت اگر اسم مقصد «test» نداشته باشد یا با اسم دیتابیس اصلی یکی باشد، **رد
می‌کند**.

### ۲. یک چک‌اوت دوم برای برنامهٔ تست

```powershell
cd E:\Apps
git clone <repo> ATA-ERP-Test
cd ATA-ERP-Test
npm ci
```

چک‌اوت جدا و نه فقط یک `.env` دیگر، به یک دلیل مشخص: `UPLOADS_DIR` برابر
`process.cwd()/uploads` است، پس یک پروسهٔ دوم در همان پوشه، فایل‌های آزمایشی را
داخل پوشهٔ آپلود **واقعی** می‌ریزد.

### ۳. `.env` مخصوص تست

```ini
PORT=3100
DATABASE_URL="sqlserver://192.168.1.104:1433;database=ata_erp_test;user=ata_app;password=<رمز>;trustServerCertificate=true;encrypt=false"

# گزارش‌گیری Power BI را به جای دیگری ببرید، وگرنه یک sync از روی کپی،
# جدول‌های واقعی گزارش را بازنویسی می‌کند.
ERP_SQL_DATABASE=ata_erp_reporting_test
```

### ۴. امن کردن کپی — این مرحله را رد نکنید

```powershell
npm run db:prepare-test
```

`settings.messaging.dryRun` را روشن می‌کند. این همان سوییچ خود برنامه است و
**قبل از** پیدا کردن provider چک می‌شود، پس مسیر کامل ارسال (قالب‌ها، ساعات
سکوت، رکوردهای outbox، سیاست retry) همچنان تمرین می‌شود و فقط دم در متوقف
می‌ماند.

اگر `DATABASE_URL` به دیتابیسی اشاره کند که «test» در نامش نیست، اسکریپت **رد
می‌کند** — چون کار این اسکریپت خاموش کردن ارسال است و این کاری نیست که به‌طور
تصادفی روی دیتابیس اصلی انجام شود.

> حد صادقانهٔ این محافظ: نام است، نه چیز دیگر. دیتابیسی که اتفاقاً «latest» نام
> داشته باشد از این محافظ رد می‌شود. این تنها ویژگی connection string است که
> بدون پرسیدن از سرور دیده می‌شود، و کارش این است که یک فاجعهٔ بی‌صدا را به یک
> جملهٔ «رد شد» تبدیل کند.

### ۵. اجرا

```powershell
npm run build
npm run start     # روی PORT=3100
```

## چه چیزی دست‌نخورده می‌ماند و چرا

اسکریپت آماده‌سازی داده را **پاک‌سازی نمی‌کند**:

- **داده‌ها** دقیقاً همان‌طور که کپی شده‌اند می‌مانند. کپی‌ای که نام‌هایش عوض
  شده، دیگر همان باگی را که دنبالش بودید بازتولید نمی‌کند — و بازتولید، تنها
  دلیل وجودش است.
- **کاربران و رمزها** دست‌نخورده. وارد شدن با حساب همان کسی که مشکل را گزارش
  کرده، معمولاً کل ماجراست.
- **توکن‌های API** دست‌نخورده. آن‌ها در برابر *همین* نسخه احراز هویت می‌شوند، پس
  یک توکن کپی‌شده یک توکن تست است.

## به‌روز کردن کپی

هر وقت خواستید داده‌های تازه داشته باشید، همان دو دستور را دوباره بزنید:

```powershell
powershell -ExecutionPolicy Bypass -File ...\copy-to-test-db.ps1 -SqlUser ata_app -SqlPassword <رمز>
cd E:\Apps\ATA-ERP-Test ; npm run db:prepare-test
```

`RESTORE` با `WITH REPLACE` کپی قبلی را بازنویسی می‌کند، پس هر چه در محیط تست
ساخته بودید از بین می‌رود — که همان چیزی است که از یک محیط تست می‌خواهید.

**بعد از هر restore دوباره `db:prepare-test` را بزنید.** کپی تازه، تنظیمات تازه
دارد و `dryRun` دوباره خاموش است.

## اگر کپی بالا نیامد

**`Login failed for user 'ata_app'` روی دیتابیس تست:** یک restore، کاربر دیتابیس
را از login سرور جدا می‌کند (نام یکی، SID متفاوت). اسکریپت وقتی با `-SqlUser`
اجرا شود خودش این را درست می‌کند؛ با احراز هویت ویندوزی، دستی بزنید:

```sql
USE [ata_erp_test];
ALTER USER [ata_app] WITH LOGIN = [ata_app];
```

**`RESTORE` می‌گوید دیتابیس در حال استفاده است:** نسخهٔ تست برنامه هنوز بالاست.
اول ببندیدش. (اسکریپت خودش `SINGLE_USER WITH ROLLBACK IMMEDIATE` می‌زند، ولی
فقط روی کپی — هرگز روی دیتابیس اصلی.)
