# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Persian (RTL) ERP/CRM web app for "Abzar Tamin Arshia" — a single-company internal tool covering customers, projects (sales opportunities), proformas, products/inventory, suppliers, purchase orders, transactions, tasks, packaging/delivery, and after-sales service. UI text and enum values are in Persian throughout; comparisons and status logic frequently key off Persian string literals (e.g. `'برنده'` = won, `'باخته'` = lost).

## Commands

```bash
npm run dev          # tsx server.ts — Express + Vite middleware on http://localhost:3000 (frontend + API together)
npm run build        # vite build (client) + esbuild bundle of server.ts -> dist/server.cjs
npm run start        # node dist/server.cjs (production; NODE_ENV=production serves dist/ instead of Vite)
npm run lint         # tsc --noEmit — the only standing check; there is no test suite
npm run sync:report  # push a flattened copy of the data into the SQL Server reporting tables
npm run test:rules   # the derived-figure rules, with no database — run before every commit
npm run test:ui      # renders modals into jsdom; catches state reset by a re-render
npm run test:e2e     # drives the real HTTP API end to end (writes to the configured database)
```

Three scenario suites exist (`test:rules`, `test:ui`, `test:e2e`); there is no ESLint. `npm run lint` (type-check) is the sole standing gate — run it after changes. **`noUnusedLocals` is on**, so a dead import or an orphaned `useState` fails the build; that is what keeps the tree clean without a linter. Unused *parameters* are allowed on purpose. **It covers `scripts/` too, and `deploy.ps1` refuses to deploy when it fails**, so anything a script imports must be a declared dependency: `scripts/uiScenario.ts` imported `jsdom` while that package was only ever present locally as an extraneous leftover, and the deployment stopped on the server with TS2307. Note `clean` uses `rm -rf` (won't work in PowerShell; use the Bash tool or delete manually on Windows).

**A hook below an early return is a white page.** `useBrowserTab` was written next to the value it reads, which sits under `App`'s early return for the login screen — so it ran for a signed-in user and not for a signed-out one, and every sign-in crashed the whole application with React's "Rendered more hooks than during the previous render". Nothing here could see it: a hook is an ordinary call to the type-checker, no derived figure was wrong, every endpoint answered correctly, and there is no ESLint to run `react-hooks/rules-of-hooks`. `src/utils/hookOrder.ts` now reads the source for that shape and `test:rules` fails on it. **Call hooks above every `return` in a component**, and if a hook needs a value computed further down, compute that value at the top too.

**Verifying non-trivial logic.** Since there is no test suite, the working practice is to write a throwaway `__something.ts` script at the repo root, run it with `npx tsx`, and delete it once green — this has repeatedly caught real bugs (the SKU decoder round-trip, the delta-merge lost-update case, the `extractNameAndCode` regex). Never leave those files behind. Server endpoints are verified by launching a second instance on another port (`PORT=3100 npx tsx server.ts`) — but it reads `DATABASE_URL` from `.env` like any other, so **point that at a scratch database or clean up what the test created**.

## Architecture

**Single full-stack process.** `server.ts` runs Express and mounts Vite as middleware in dev, so one `npm run dev` serves both the React SPA and the JSON API. In production the same file serves the built `dist/`.

**Persistence is SQL Server, through Prisma.** `prisma/schema.prisma` holds 35 models; `src/server/db.ts` exposes a single `getDb()`. Every module is one service under `src/server/services/` (queries plus record-level visibility) and one route file under `src/server/routes/` (HTTP, validation, permission gate) — `customerService.ts` and `routes/customers.ts` are the reference implementation. Port is overridable with `PORT`; the connection with `DATABASE_URL`.

The flat JSON document store this replaced is **gone**: no `database.json`, no `ALLOWED_KEYS`, no `/api/data/:key`, no `/api/versions` polling, no `saveToStorage`. Comments across the codebase still explain what a piece of code used to do in those terms — that is deliberate history, not a live description. A few endpoints survive outside the module pattern, on `server.ts` itself:
- `POST /api/login`, `/api/change-password` — bcrypt auth with in-memory per-IP/per-user rate limiting
- `POST /api/upload` — multer + sharp image resize/compress to `uploads/`, with path-traversal guarding
- `GET /api/rates` — today's scraped rates, returned without being stored
- `GET /api/report/preview` · `GET /api/report/sql-test` · `POST /api/report/sql-sync` — Power BI reporting sync
- `GET /api/db-health` — connectivity plus the schema check (authenticated)

**Each screen owns its own data.** There is no global store worth the name: `src/useERPStore.ts` is down to the session, the settings and a couple of helpers. A view calls the list hook for its module (`useProjectList`, `useProformaList`, …), which pages against the server; a detail record is fetched when it is opened. Writes go through the module's `src/api/*.ts` client, and every non-GET emits a change event (`src/api/liveData.ts`) so anything showing a count or a list re-reads itself.

**Concurrency is resolved in the database, not in the browser.** Clients no longer hold collections, so there is nothing to reconcile: a write is a row update inside a transaction, and the "another user changed this while you were editing" machinery went with the document store.

**Passwords never round-trip in the clear.** The server hashes on save and strips the hash from login responses. Use `isBcryptHash()` to detect an existing hash — **not** `startsWith('$2b$')`: bcryptjs emits `$2a$`, and that mismatch used to re-hash stored hashes on every users save, permanently breaking that user's login. Seed users default to password `123`, which triggers `mustChangePassword`.

### Cross-cutting systems

- **Derived status logic** — Proforma and project statuses are computed, not stored raw. **Filtering the grid by status means filtering by the *outcome*, which is not a column**: the filter sent its value at `proformas.status`, where only «پیش‌نویس» and «ارسال شده» ever live, so «تأیید شده (برنده)», «باخته» and «لغو شده» matched nothing and the grid came back empty (and «نیمه برنده» could not be asked for at all). `outcomeWhere` in `proformaStatus.ts` turns each outcome into the query that finds it — spelled out without `not` on a nullable column and without `every`, so NULL needs no remembering — and `matchesWhere` is a small evaluator for that subset so `test:rules` can hold the clauses against `getProformaOutcome` over **every** combination of lines rather than against a second reading of the rule. The screen no longer re-filters the page it was handed. `src/server/proformaStatus.ts` is the authority (`getProformaOutcome`, `deriveProjectStatus`), and writing a proforma re-derives its project in the same transaction. `getProformaOutcomeStatus` in `useERPStore.ts` is a client copy of the same rule, kept only so a grid can colour a row without asking; change both or neither. `test:rules` runs both over every combination of document status, cancellation and line statuses and fails if they disagree, so the instruction is no longer the only thing holding them together.
- **Sales follow-up is a second axis on a proforma, and never a second spelling of the outcome.** A quotation sent three weeks ago with nobody on it and one the customer asked us to raise again after Nowruz have the *same* derived outcome — «جاری» — and are completely different situations for the sales desk. So `Proforma.followUpState` spells only the three things the outcome cannot: `OPEN`, `DEFERRED`, `NO_RESPONSE`. There is deliberately no `WON`/`LOST`/`CANCELLED`/`SUPERSEDED` here; those are derived one column away (`getProformaOutcome`) and a second copy is how two columns come to disagree. The pure rules are `src/utils/salesFollowUp.ts` and `test:rules` covers them. **The next action is not on the proforma either** — the open `SALES_FOLLOW_UP` task related to it *is* the next action, its date, its assignee and its priority, so there is one record to edit rather than four columns to keep in step; `test:rules` fails a `nextAction` column appearing on the model. **The owner is `Project.salesExpert`, never `Proforma.creator`**: a support engineer routinely prepares the document for a job somebody else is selling, and `SALES_EXPERT` in a workflow rule resolves through the proforma's project (which is why `enrichPayload` resolves the proforma **first** — it is what supplies the project id the other blocks then read). **Task creation stays in the workflow engine**: `create_task` gained `taskKind`, `skipIfOpenSameKind` (the duplicate check, an option on the action rather than a law in the engine — "one task for ever" is not true of every automation) and a proforma relation when the payload names one, and the new `proforma_status_change` trigger reports the *stored* status moving, which `proforma_outcome_change` cannot — sending a quotation changes the first and not the second. It fires only on a real change, and on a document created already sent. The standard rule is **seeded** in `seedData.ts` rather than written into code, so when it fires, who it lands on and how long they have are all editable in Settings; an existing database keeps its own `settings.workflows` and needs the rule added there by hand. **Completing a follow-up is one transaction** (`completeFollowUp` in `followUpService.ts`) — closing the task, recording the result, moving the follow-up state and raising the replacement must succeed together, or a quotation ends up marked as actively followed up with the task completed and nothing chasing it; the close is a conditional `updateMany` so a double-clicked button raises one next action. The generic task update **refuses** to tick a `SALES_FOLLOW_UP` task for the same reason, while the automatic closing writes with `updateMany` and is unaffected. A terminal outcome closes that proforma's follow-ups (both the ordinary save and the outcome modal do it, inside the transaction) and touches **no** `GENERAL` task — an ordinary task attached to the same document does not stop being necessary because the quotation was won. `settings.dropdownItems.followUpResults` is what the customer said and is **not** a loss reason: «خرید به تعویق افتاد» is a deferral, `settings.lossReasons` is untouched, and `test:rules` holds the two lists apart. **A settled quotation is not in the queue at all** — a won, lost or cancelled document needs no next action, and «نیمه برنده» is settled too (it is reached when some lines were won and the rest closed off, which the business reads as decided; the outcome rule does not separate that from a part-won document with lines still «جاری», and both are treated as settled), and «پیش‌نویس» has not been sent to anybody. That is a *derived* value, so filtering on `isCancelled` and the stored status lets every won and lost document straight through (a fully-won proforma still has `isCancelled: false` and a stored status of «ارسال شده»), which is how the screen came to ask for a next action on finished sales; `chaseableWhere` builds the clause from `outcomeWhere` and `test:rules` holds it against `getProformaOutcome` over every shape, including a stored status nobody designed for. **`proformas.status` is NOT NULL, so no clause may filter it against null** — Prisma rejects that on a non-nullable column with «Argument `status` is missing» and the whole screen renders its error text instead of a list; `openAt` carried such a branch and the sweep's own null case was hiding it. A *line's* status is nullable and its null branches are correct and necessary, which is why the check walks the tree and only inspects `status` keys outside an `items` clause. Excluding by outcome rather than by whether the automatic sweep has run is also what makes the screen right for documents written before the feature existed — theirs were never closed because they never had any. The queue (`listFollowUpQueue`) is **ranked, then paged**: the rank comes from the open follow-up task, so no database can sort by it — paging in SQL and sorting the page afterwards put an overdue quotation from six months ago on page three of a list whose entire purpose is to put it first, and reported the unfiltered total beside a health-filtered page, which reads exactly like a missing record. It is a bounded scan (`QUEUE_SCAN_LIMIT`) with a `truncated` flag the screen shows, two reads in total, and every figure on a row is derived, never stored.
- **A project has its own follow-up tab, and it is not the queue.** `projectFollowUpReport` / `GET /api/sales-follow-up/project/:projectId` answers «what has happened on *this* job», which is a different question from the queue's «what should the sales desk do next, across the company» — so it deliberately **includes the settled quotations** the queue excludes: a won document with three recorded chases behind it is exactly the history being asked for. Each quotation carries its own `settled` flag, and a settled one is offered no next action and no health badge, which is the rule the queue screen was corrected for. Two reads, never one per row: the project's quotations, then one query for every follow-up task belonging to them, with the history newest-first. Recording a result and raising the next action reuse `FollowUpCompletionModal` and `salesFollowUpApi.reactivate`, so one flow writes a follow-up wherever it is started. The route is registered **before** `/api/sales-follow-up/:proformaId/reactivate` or «project» is read as a proforma id.

- **A revision is an explicit relation; two quotations sharing a project are not versions of each other.** A project here legitimately carries several open proformas at once — the temperature instruments, the pressure instruments, the flow meters — so nothing may infer that an older one is superseded because a newer one exists. `Proforma.previousVersionId` is a self-relation a person creates through «نسخه جدید همین پیش‌فاکتور» on the Copy button, which now asks which kind of copy it is; «پیش‌فاکتور مستقل» is the old behaviour and records nothing. A second revision of the same document is **refused** (`assertVersionChain` / `versionRefusalReason`) because the chain would fork and neither branch would be the live one — the message names the revision to work from instead. After a revision saves, the screen asks what becomes of the previous version and offers exactly two answers: cancel it, or leave it. **«باخته» is deliberately not one of them** — issuing a revision is not losing a sale, and filing it as one would poison every report built on `settings.lossReasons`. Cancelling uses the ERP's own `isCancelled`, assigns no loss reason and closes the old document's open follow-ups; it is not offered at all when the previous version already has a settled outcome. Being the base of a revision blocks ordinary deletion (`countProformaReferences` counts `nextVersions`), with a message that says to cancel it instead.
- **The front page's sales figures are derived, and two of them were derived wrongly.** `src/server/dashboardMetrics.ts` is the pure half, covered by `test:rules`. **A won contract stops moving with the exchange rate once it is paid.** «مجموع قراردادهای برنده» converted every won document at *today's* rate, so a contract invoiced, collected and closed two years ago moved every time the dollar did. `wonValueRial` splits the value in two: the settled part is frozen at the rial that actually arrived (the receipt's own `exchangeRate` — the difference between it and the invoice's rate *is* the exchange gain, so the invoice's rate is only a fallback for a row written before that box existed), and the outstanding part still converts at today's. A fully paid contract therefore stops moving altogether, an unpaid one floats exactly as before, and a rial document comes out at its own amount whatever the receipts say. A foreign receipt with no rate at all settles **nothing** — guessing at today's rate would put the frozen figure back on the rate, which is the fault being fixed. Money paid above the invoice is not sale value, so the settled part is capped and the rial that went with the excess carved off in proportion; `effectiveRate` (`rial / wonAmount`) is what splits the same money across the document's lines so «درآمد به تفکیک دسته» still adds up to the total beside it. **Conversion is counted per opportunity, never per document.** A project here carries several live quotations and several revisions of each, so a job quoted ten times and won once read as one win in ten and every corrected typo pushed the company's conversion down. `opportunityGroups` makes one data point per project (a proforma with no project stands alone), and `opportunityOutcome` reads it through `decidingProformas` — the *same* selection `deriveProjectStatus` makes, extracted so the front page and the project card cannot disagree about who won. That also means a later quotation for extra scope does not un-win a project, which "just take the newest one" would. `conversionByCategory` uses the same set and is no longer a raw sum over every `proforma_items` row. `averageProformasPerProject` is «چقدر رفت و برگشت داریم». The cost of all this is that the service reads proforma rows rather than aggregating in SQL — unavoidable, since every one of these rules is derived from line statuses — so the projection is narrow and the reason is written where it happens.
- **Workflow rules engine** — `settings.workflows` (`WorkflowRule[]`) is a user-configurable automation system. Mutations fire `processWorkflowRules(triggerType, payload)` (e.g. `'customer_created'`, `'proforma_outcome_change'`, `'product_low_stock'`). When adding a mutation that should be automatable, emit the matching trigger. A rule can also be **time-based** (`triggerType: 'time_elapsed'`): it names a date the record already carries, a number of days, and which side of it — `direction: 'after' | 'before'`, so a reminder can fire *before* an expiry (`src/utils/workflowSchedule.ts`, shared by the editor and the engine so a subject cannot exist in one and not the other). `days` is never negative; the side is its own field, and `sweepRange` reaches into the future for a "before" rule or the record would never be looked at. There is no cron here, so `ensureWorkflowSweepRanToday` runs once per Shamsi day, started at login and never awaited (the rate refresh is the same shape on a two-hour clock); `POST /api/workflows/run-due` is the manual button. Each firing is inserted into `workflow_firings` **before** the actions run and the unique index `(ruleId, entityId)` is what enforces once-per-record — the sweep runs again tomorrow and the record is still past its due day. `executeRule` is the one implementation both kinds of trigger share.
- **Per-project milestone automation** — a *second*, separate engine: `src/server/services/milestoneAutomation.ts`. `ProjectMilestone` rows are checkpoints on one job; `project.milestoneRules` (JSON) attaches "raise a task" / "notify someone" to a milestone by `triggerMilestoneId`. `runMilestoneRules` fires for the milestones that went open→done in a write (the transition, never the state, or every save re-raises everything); `applyCategoryMilestoneTriggers` completes the ones bound to an activity category when that category opens or closes, matching through `sameCategory`. Both run **after** the parent transaction commits — a task that cannot be created must not roll back the tick. Because a milestone is *referenced* by the rules, it must never go through `syncChildren`: `syncMilestones` in `projectService.ts` reconciles by id, and `projectToWriteInput` sends the id back.
- **A blank worth a warning is not the same thing as a required field.** `settings.projectDataGapFields` is a separate list, and the project card draws a small amber badge naming what is missing (`src/utils/projectDataGaps.ts`, covered by `test:rules`). It cannot be `requiredFields.projects`, because a required field is enforced *on save*: switching one on says nothing about the projects already on the system and makes every one of them unsavable the next time somebody opens one to fix a typo. The field catalogue is `REQUIRED_FIELDS_METADATA.projects` — no second spelled-out list of a project's fields — and three rules keep the badge honest: a key the record does not carry at all is skipped rather than reported (a list row omits some columns, and a gap nobody can fill in is a badge nobody can clear), a numeric zero is an answer and not a blank, and an **empty** configured list means «warn about nothing» and must not fall back to the default or the feature cannot be turned off. `test:rules` also checks every default field actually arrives on a grid row, since `rowToProject` writes each key explicitly and one it never sets would warn about nothing, silently.

- **Configurable required fields** — `settings.requiredFields[module][fieldKey]` (boolean) drives dynamic validation. `src/utils/requiredFields.tsx` holds `REQUIRED_FIELDS_METADATA` (the master list of validatable fields per module) and the validation helpers. **Invariant: every metadata entry must correspond to a form field that actually calls `isFieldRequired`/`renderFieldLabelWithAsterisk`, and vice versa** — drift in either direction silently breaks the toggles (a field that can't be toggled, or a toggle that does nothing). `test:rules` now reads the source and checks this, in three directions: a switch with no form, a form with no switch, and — the one the first two miss — a field the form *validates* while offering nowhere to type it, which makes the form impossible to submit once the switch is on. Watch the controls that are not `<input>`s: a chip group, a `SearchableSelect` or a pair of buttons draws the asterisk but the browser enforces nothing, so those need an explicit check in the submit handler. `isFieldRequired` falls back to `DEFAULT_REQUIRED_FIELDS` per field, so a field that was previously hard-coded `required` must have its default set to `true`.
- **Customers have five separate creation forms** — four call `addCustomer` (`CustomersView`'s inline linked-customer form, the shared `QuickAddModal`, and *separate* inline modals inside `ProformasView` and `TransactionsView`), while the `CustomersView` **main form builds records itself and calls `batchUpdateCustomers`** — so grepping for `addCustomer` alone misses it. Any customer-level rule must be applied to all five or it is trivially bypassed. Supporting utils: `customerValidation.ts` (at least one of mobile/phone/email/province), `iranProvinces.ts` (31 provinces + `canonicalizeProvince` so one province can't be stored two ways), `customerDuplicates.ts` (soft warnings; hard block only on economic-code collision), `customerLabel.ts` (adaptive homonym disambiguation in dropdowns), `customerMigration.ts` (reassign history to a replacement customer before deletion).
- **The bulk product import's features column is parsed by `src/utils/productFeatureSpec.ts`.** The importer read it into `featuresRaw`, carried it through the whole batch and then sent `features: null` — so a sheet listing thirteen features per product imported none of them and reported success. The format is documented in a note on the sheet's own header: features split by `|`, options by the Persian comma `،`, and an optional code in parentheses after a feature name or an option value. **A trailing parenthesis is a code only if it could be a token in a SKU** (`[A-Za-z0-9._-]{1,16}`): «2.5Mpa(ANSI300#)» is a pressure rating written the way an instrument catalogue writes it, and reading it as a value-with-a-code would store «2.5Mpa» and silently drop the half the engineer cared about. Only the first colon separates, so a value may contain one. The update path applies features too, but sends **only** `{ features }`: `updateProduct` reads `stockLevel` and `variants` as the levels the caller wants and reconciles the difference into stock movements, so writing back a record read a moment earlier would undo any adjustment made in between — on the one screen whose job is bulk stock changes. A blank cell means «not specified»; a row matched by one of the product's SKUs sets them just the same, because features belong to the product.
- **SKU generation and decoding** — `src/utils/skuUtils.ts`. `generateSku` builds `{productCode}-{featureCode}{optionToken}-…` where the option token is the option's own `code`, falling back to its 1-based serial (`getOptionToken`). `decodeSku` is the inverse and **must stay in sync with it**; it first tries an exact stored-variant SKU match, then parses structurally. Excel import accepts the same `name(code)` convention for options.
- **Supplier-inquiry workflow steps** — `src/utils/inquirySteps.ts` derives steps automatically from user actions (price entered → initial offer, price changed → revision, offer confirmed → final offer, winner set → winner), keyed by `autoKey` for idempotency. Step titles resolve against the user-editable `settings.dropdownItems.supplierInquirySteps` by keyword, not hardcoded strings.
- **The prices already obtained are searchable by the item, not only by inquiry.** «سوابق قیمت» (`InquiryPriceHistoryTab`, `GET /api/supplier-inquiries/price-history`, `listPriceHistory`) answers the buyer's actual question — «آخرین قیمتی که برای فلومتر توربینی ۶ اینچ گرفتم چقدر بوده» — and needed no new column: `supplier_inquiry_items` has carried `productId`/`variantId` since the module was written, so the whole history was already on disk with no way to ask. It queries the **lines**, not a page of inquiries: picking the matching lines out of a page of offers pages the wrong set, and a supplier whose one matching line sits on inquiry 200 falls off page 1, so the answer changes with the page size. Three rules it carries. **A line with no price is not a price** — an inquiry sent and never answered has lines at zero, and listing those as «قیمت‌های دریافتی» is the same error as an uncosted proforma line reading as pure margin. **The discount belongs to the offer, not to the line**, so the stored `priceForeign`/`priceRial` is a pre-discount figure: `discountKeepFraction` in `src/utils/inquiryPriceHistory.ts` derives the payable proportion *from `computeInquiryTotals`* rather than re-implementing percent-then-amount, which is what stops the history and the offer card quoting one offer as two amounts — `test:rules` sums the lines against `inquiryTotalRiyal` over five discount shapes. **The range spans every match, not the page** (a «کمترین قیمت» that changes when you turn the page is worse than none), so it is a bounded scan with a `truncated` flag, and it is computed **only once the query is narrowed**: the cheapest unit price across every part ever quoted mixes flow meters with bolts and the figure it produces is a bolt. Two things easy to get wrong: the route must be registered **before** `/api/supplier-inquiries/:id` or Express answers 404 for an inquiry whose id is the literal string «price-history» (pinned by `test:rules`), and a user without `costs` is **refused** here rather than served the redacted copy the rest of the module gives them — this screen is nothing but prices, and a blank table cannot be told from «no history». `test:ui` asserts the tab fetches nothing until it is opened.
- **A supplier's offer is a list of files, in two places at once.** A quotation arrives as a covering letter, a datasheet and a price list, and `technicalOfferUrl`/`financialOfferUrl` could hold one of each — so the rest went in as a second inquiry or nowhere. `technicalOfferFiles`/`financialOfferFiles` are JSON (`[{name,size,url}]`) and the original single-URL columns still carry the **first** entry, so the grid's link, the download button and the Power BI export are unaffected; `parseOfferFiles`/`offerFileColumns` in `src/utils/attachments.ts` are the only readers and writers, and never read both (the first file would appear twice). The service derives the URL column from the list on every write, so the two cannot be stored out of step, and a caller sending only a URL — every integration written before this — is still understood. The card's project label reads the row's **own** joined `project.code`/`project.name`; it used to resolve the id against the project picker's current matches, so a job outside that page read «نامشخص», and the code is there because several projects here are genuinely called the same thing.

- **The product configurator is one component, used by two forms.** `ProductConfiguratorModal` ticks a catalogue item's features and enforces its `configRules`; the pure part — selections to SKU attributes, to specification lines, and back — is `src/utils/productConfig.ts`, and `ensureVariantForAttributes` in `src/api/productVariants.ts` is the single place a SKU is found or created. It lived inside `ProformasView` until the supplier-inquiry form needed the same thing. Two rules it carries: a feature with **two** values ticked is a legitimate question for a supplier («316 or 304») but identifies no single SKU, so it produces specification text and no SKU rather than a wrong one; and the id of a created SKU is read back from what was saved, never made up — a line's `variantId` is a real foreign key. The inquiry form fetches the **full** product on opening, because a picker row's `configRules` are empty and a configurator that cannot see the rules offers combinations the catalogue forbids. `test:ui` renders it and asserts a rule fires as boxes are ticked. **A feature or an option can be defined from inside it** (`onCatalogueEdit`, gated on the `products` permission at both call sites and by the route itself): the catalogue is never complete at the moment somebody is quoting from it, and the alternative was to abandon the proforma, add the option on the products screen and start again. The modal builds the mutation and the *host* performs the write through its own `updateProductById`, because sending a picker row back erases `configRules` and the price calculator. `catalogueNameRefusal`/`catalogueCodeRefusal` are the pure rules: a name is what `mergeSpecText`, the SKU attributes and `decodeSku` all match on, so a duplicate (compared with the formatting and spacing removed) is refused, and a code is restricted to a SKU token because `decodeSku` splits on `-`.

- **A proforma line's specification belongs to the product it names, and the outgoing product is an argument.** `describeProductSpec` in `productConfig.ts` subtracts *both* products' stored descriptions and feature names before keeping what the user typed. It used to subtract only the incoming product's, so switching from A to B kept every line of A's description — and since a new line is seeded from whichever product the picker happens to hold first, the default product's specification was printed above the chosen one on almost every line. Lines are matched with `stripRichMarks` applied, for the same reason `mergeSpecText` does it. **A line can also be copied** (`handleDuplicateItemLine`), and the copy carries **no** `id`: that field is the row the client read the line under and `preserveLineCosts` matches on it, so two lines sharing one would both claim a single stored row.

- **A screen that writes to the catalogue has to remember what it wrote.** The proforma form's SKU `<select>` draws its options from the product picker's rows, which were fetched before the configurator created the SKU — and a `<select>` whose value matches no option renders its placeholder, so the line read «انتخاب ترکیب مشخصات» with a perfectly good `variantId` on it. `productOverrides` keeps every product this screen has saved, replacing a row of the same id and otherwise appending, so a product written to stays reachable after the search term moves on.
- Product variant filtering uses `configRules` (`ProductConfigRule[]`) on products.
- **Audit log** — `logAction()` records CREATE/UPDATE/DELETE/LOGIN/LOGOUT with before/after snapshots LZW-compressed via `src/utils/compress.ts`, capped at the most recent 1000 entries.
- **Jalali/Shamsi dates** — the app runs on the Persian calendar. Use the helpers in `src/dateUtils.ts` (`getTodayShamsi`, `toShamsiStr`, `addWorkingDaysToShamsi`, etc.); dates are stored as Shamsi strings, not ISO. Persian/Arabic digits are normalized with a `faToEnDigits`-style helper before parsing.
- **Live exchange rates** — `GET /api/rates` scrapes tgju.org HTML for USD/EUR/AED/CNY (alanchand.com behind it) with hardcoded fallbacks; used to price items in multiple currencies. `src/server/services/rateRefresh.ts` brings the *stored* rates up to date **every hour** (`FRESH_FOR_MS`): started (not awaited) at login, awaited with a short budget by `GET /api/exchange-rates`, and driven by a ten-minute `setInterval` in `server.ts` so an afternoon with nobody signing in still gets a fresh rate — the tick must stay well inside the window (`test:rules` reads it out of `server.ts`), because a half-hourly tick against an hourly window leaves ninety minutes between refreshes. **The failure mode is silence**: the scrape reads two web pages, and when a markup change or a blocked outbound request stops it, nothing on any screen said so — the rates simply stopped moving and the only symptom was somebody pressing the manual button every morning. `rateRefreshReport()` travels with `GET /api/exchange-rates` and the rates screen draws it, reason and unread currencies included. Freshness is the age of `lastUpdated`, asked of the database as well as of this process, so a restart does not re-scrape what was fetched minutes ago. Server-side because refreshing needs the `settings` permission and the first person in each morning usually lacks it; one in-process promise so a busy 08:00 does not scrape four ways at once. `refreshDecision` is the pure scheduling rule and is covered by `test:rules`.

### Frontend conventions

- One view component per module under `src/components/` (`CustomersView.tsx`, `ProformasView.tsx`, etc.), switched by `activeView` string state in `App.tsx` — there is no router. **`src/appModules.ts` is the single list of those modules** (id, name, description) and everything that has to agree about them reads it: the sidebar, the settings screen's ordering tab, the default order in `seedData.ts`, and the «no access to module X» message. There were four copies and the messaging module was added to one, so it appeared in the menu and could not be reordered — the ordering tab looks each stored id up in its own list and renders nothing for one it does not know. The catalogue is deliberately free of React so `scripts/seedDb.ts` can import it through `seedData.ts`; icons live in `src/components/moduleIcons.ts` as a `Record<AppModuleId, …>`, so a module added without one **fails `npm run lint`** and `deploy.ps1` will not deploy past it. `test:rules` covers the rest: every catalogue id has a `case` in `App.tsx`'s switch and every case is in the catalogue, the seed order matches, and neither screen has grown a fresh copy of the list. A `?printModule=&printId=` URL opens a document directly for printing.
- Tailwind v4 (via `@tailwindcss/vite`), dark mode through a `dark` class on `<html>` persisted to `localStorage`.
- Types are centralized in `src/types.ts`; seed data in `src/seedData.ts` (`DEFAULT_SETTINGS`, `SEED_EXCHANGE_RATES`) except `SEED_USERS`, which lives in `useERPStore.ts`. Both are imported by `scripts/seedDb.ts` for `npm run seed:db`, not by `server.ts`.
- Excel import/export via `exceljs`/`xlsx` in `src/excelUtils.ts`; financial math in `src/utils/finance.ts`.
- **Printed documents are HTML printed by the browser, never rasterised.** Each screen builds a whole standalone page, `inlineDocumentAssets` turns its `/uploads/…` paths into data URIs, and `printHtmlDocument` (`src/utils/printDocument.ts`) writes it into a hidden iframe and prints that. The resulting PDF carries embedded fonts and real selectable text — verified. Do **not** reach for html2canvas/jsPDF: those photograph the page, and Persian text photographed at screen resolution is the poor quality this replaced. Each document owns its `@page { size: A4; margin: … }` and `print-color-adjust: exact`; without them the browser prints its own URL-and-date header and drops every background colour.
- **A printed proforma runs to several pages, and the rules for that live in `src/utils/proformaDocument.ts`.** It was six hundred lines of template literal inside `ProformasView`, which is why nobody could look at it: judging a printed document means printing it, and that needed a browser, a session and a database. As a pure function of its inputs it can be rendered to a real PDF by a real browser in a throwaway script and the pages examined — which is how the reported fault was reproduced and the fix confirmed. **An eight-item proforma printed page one with a letterhead, a buyer panel and no goods at all**, and began the items on page two: the goods table sat in a box marked `break-inside: avoid`, so the browser was being told to keep the *entire* list on one sheet, and when it would not fit it moved the lot. Four rules now hold the layout, and `test:rules` reads the document the builder produces and fails on each of them. **Keeping a row whole is the `<tr>`'s job and keeping the table whole is nobody's** — the avoidance is scoped to `.table-container tr`, because the document frame's own rows are `<tr>`s too and an unbreakable one there would mean the whole body had to fit a single page. **Nothing of unbounded length may be unbreakable**: the terms are free text a user can make as long as they like, so `.notes-card` and `.financial-grid` lost their avoidance while the totals panel, six short rows, kept it. **The letterhead repeats because it is the frame table's `<thead>`** — `display: table-header-group` is the one mechanism a browser implements for this, and unlike a `position: fixed` banner it *reserves* the space on every page instead of painting over what is there. **The address bar is defined once and placed twice**: the copy in the `<tfoot>` reserves the strip on every sheet and its ink is hidden when printing, while a `position: fixed` copy draws it — a footer group alone leaves the bar floating mid-page on a short final sheet, and a fixed bar alone reserves nothing, which is what used to print the last row of goods underneath it. Two smaller things that cost a render each to find: a repeated footer group is given very slightly less room than it occupies and the overflow is painted over the *next* page's letterhead, so `.print-footer` keeps `padding: 8px 0 6px` of slack (a sweep of twenty page shapes needed six pixels; zero failed eleven of them); and `white-space: pre-line` keeps the newline between a tag and its interpolation, which printed a blank line above every specification. **The seal block is compact, and it never starts a page alone.** It was about 48pt tall with 20px of air above it and a heading repeating what the panel below already labelled; at 38pt, with the heading gone and the strip shorter, four of the shapes that used to end on a sheet carrying nothing but a stamp no longer do. Shrinking cannot win that argument on its own — whatever height the block is, some document ends a point short — so `.signatures` also carries `break-before: avoid`, which asks the browser to keep it with the totals; being a preference rather than a demand it cannot recreate the unbreakable-block fault above. Its sizes are in **one** place now: every dimension used to be an inline style written out twice, once for a template with a company stamp and once for one without, so the same block was two different heights depending on a setting nobody connected to it. **Verifying a change here means printing it**: `renderProformaDocument` is pure, so a throwaway script drives a headless Chromium over a sweep of documents — item counts crossed with the length of the terms — and asserts on the resulting PDFs (one letterhead per page, the address bar at the same y on every page, nothing painted above the top margin, goods on page one, and no last page carrying only the seal). Serve the Google font from a local cache while doing it: a render that silently falls back to Tahoma paginates differently and will send you chasing a break that does not exist.
- **A proforma line's specification carries formatting, and it is still plain text.** `src/utils/richText.ts` defines four markers — `**درشت**`, `__زیرخط__`, `_مورب_`, `==هایلایت==` — and `RichTextField` is a textarea with a toolbar that wraps the selection plus a preview. Storing HTML instead was rejected for three reasons that all still hold: the product configurator reads that field line by line and tags in the middle of «جنس بدنه: …» would stop it recognising its own output (`mergeSpecText`/`selectionsFromSpecText` strip marks before matching, so bolding a feature line does not make the configurator append a duplicate); the field is interpolated straight into the printed document, and `renderRichText` **escapes first and applies the marks after**, which closes the hole a stray «<» in a tolerance already opened; and every plain-text reader keeps working, with `stripRichMarks` for the ones that want the words alone. Underline is matched before italic or `__` reads as two empty italics, and a run never spans a newline so an unclosed marker formats nothing rather than swallowing the rest of the page. `test:rules` covers the arithmetic, `test:ui` covers the toolbar reading the textarea's own selection. The proforma's own **«شرایط و توضیحات» block is the same field type**, and it is not only printed: `updateNotesWithDelivery` (now in `src/utils/deliveryNotes.ts`, extracted so it can be tested) writes and rewrites the delivery section *inside* it and finds that section by the words at the start of a line — so it compares against a `stripRichMarks`ed copy while splicing the original lines, or bolding «زمان تحویل:» hides the section and every later delivery change appends a second one below the first.
- **Money is formatted by `formatMoney` (`src/numUtils.ts`), in Latin digits.** Amounts get copied into bank portals and spreadsheets. `toLocaleString("fa-IR")` on an amount is a bug; on a count in prose («نمایش ۵ از ۱۲») it is correct.

## SQL Server

The move off the flat JSON document store is **finished**: all 18 modules have a Prisma-backed service and REST API, and every screen reads and writes through it. Nothing loads `database.json` any more, and the file, its endpoints and its seeding are gone.

### What the migration was for

The recurring pattern, and the one to expect in anything added next: a screen holds every record so it can compute something across all of them, and that computation silently breaks once the list is paged. Each of these moved to the server, where the whole set is still visible:

- **the winning supplier inquiries of a project** — found by walking every inquiry in memory (a project may have several: one supplier per part of the scope)
- **how much of a won item is still unshipped** — promised minus already shipped, across every proforma and delivery
- **document numbers** — `startSeq + collection.length`, which under paging is one page. The count moved to SQL but the arithmetic stayed, and it was wrong in a second way: every template is scoped (a project code, a year and month, a transaction type) while the count was the whole table, so a document on one project advanced the next number of every other, and a failed-then-retried save came back «…-C2» with «…-C1» never issued. `nextSequence`/`renderAround` in `src/server/documentNumbers.ts` count the numbers already issued under the same rendered prefix; `startSeq` is the floor. Covered by `test:rules`.
- **an after-sales record's status** — rolled up from its rows, and the column the grid filters on
- **dashboard revenue** — eight collections reduced to a dozen numbers

- **Schema** — `prisma/schema.prisma`, 35 models, deployed via `prisma/migrations/0_init`. Things Prisma can't express (the filtered unique index on `customers.economicCode`) live in `prisma/sql/extra-indexes.sql` and must be re-run after any migration that rebuilds those tables.
- **Client** — `src/server/db.ts` exposes a single `getDb()`. **Prisma 7 has no built-in SQL Server connector**: it connects through `@prisma/adapter-mssql`, and without the adapter the first query throws "requires a driver adapter". One client per process — the adapter owns the connection pool (`mssql` default max 10), and a client per request would exhaust SQL Server.
- **The customers grid's per-column header filters run on the server** (`CustomerColumnFilters`/`COLUMN_FIELDS` in `customerService.ts`, one allowlisted query parameter per column, each through `searchClause` so Persian variants match). They were collected into local state and never applied at all — the inputs did nothing. Filtering what the browser holds would have been worse than nothing: it filters one page and calls it the answer.
- **Lists are paginated, always** — `src/server/listing.ts` (`parseListQuery` → `paginationArgs`/`buildResult`). `MAX_PAGE_SIZE` is 200, so no caller can pull a whole table. Sort and filter field names are **allowlisted per endpoint**; an unchecked value would go straight into Prisma's `orderBy`. `searchClause` expands a term into its Persian variants (ی/ي, ک/ك, fa/ar digits) because SQL Server's collation treats them as different characters and a search would silently miss rows.
- **Module pattern** — one service under `src/server/services/` (queries + record-level visibility) plus one route file under `src/server/routes/` (HTTP, validation, permission gate). `src/server/services/customerService.ts` and `src/server/routes/customers.ts` are the reference implementation; follow their shape. Routes take `RouteDeps` (`src/server/routes/types.ts`) so they reuse `server.ts`'s single definition of `requireAuth`/`requireKeyAccess`; `sendError` maps Prisma error codes to Persian messages without leaking table names. **Settings, exchange rates and the audit log are the one exception** — all three share a single `src/server/routes/admin.ts` (backed by `adminService.ts`) rather than one file each. None of the route files mount through `express.Router()`/a path prefix either: every `register*Routes(app, deps)` call extends the same shared `app` directly with full `/api/...` paths, registered in sequence from `server.ts`.
- **Two screens borrow another module's permission flag** — `afterSalesServices` and `supplierInquiries` have no permission key of their own; access is gated server-side by `packagingDelivery` and `suppliers` respectively (`KEY_PERMISSION` in `src/server/auth.ts`). The client mirrors this via `SCREEN_PERMISSION_ALIAS` in `src/types.ts`, used by both `App.tsx`'s route guard and `Sidebar.tsx`'s menu filter — checking `permissions[screenId]` directly for either screen is wrong, since that key never exists on `User.permissions`.
- **`costs` is the one permission that is not a screen.** Every other flag answers "may this user open this module"; `costs` answers "may they see these fields inside modules they already have" — warehouse staff need the inventory screen and the sale price, and must not learn the purchase price. `canSeeCosts` in `src/server/auth.ts` reads it **strictly** (`permissions?.costs === true`), *not* through `hasPermission`, which treats an absent key as granted; absent means denied here so no account written before the flag existed is quietly given access. `src/server/costs.ts` is the single list of what counts as a cost, now across **five** places: the product/SKU price calculator (`priceCalc`), purchase-order landed cost and line prices, supplier-inquiry offers (including the auto step notes, which quote the amount back in prose), **proforma line `unitCost`/`costCurrency`/`costSource`**, and **customer gross profit** (`grossProfitRial`, `grossMarginPercent`, `costCoveragePercent`, `grossProfitScore` — revenue and the rank stay). Redacting one and not the others just moves the leak. Redaction happens **in the route, on the way out**, never only in the component: hiding a column hides it from the person looking at the screen and from nobody else. Writes split two ways — purchase orders and inquiries are *refused* (`refuseCostWrite`), while products and proformas go through with the cost put back (`stripProductCostInput`, `preserveLineCosts`), because those are records such a user legitimately edits all day. `preserveLineCosts` matches by the line `id` the client read the row under, which is why `ProformaItemInput` carries an `id` that `mapItem` deliberately never stores. `assertLinesCosted` is skipped for these users too — demanding a cost from somebody with no way to enter one locks them out of the screen. The screens hide the same fields (`canSeeCosts` in `src/utils/permissions.ts`) purely as a courtesy, so nobody is shown boxes they cannot fill.
- **Append-only collections never go through `syncChildren`** — inquiry steps, project activities, referrals and their messages, module notes, and the stock ledger. Each has its own add-one endpoint. Removal is restricted: a derived (`isAuto`) inquiry step cannot be deleted at all, and an activity cannot be deleted once its referral has replies.
- **Money and stock are computed, never accepted.** Proforma and purchase-order line totals are recomputed from quantity × price; a PO's landed cost from its own stored exchange rate. Transactions convert foreign amounts at the document's rate. **A proforma's money is computed by one rule, `computeProformaTotals` (`src/utils/proformaTotals.ts`), which the form and the server both run.** There were two implementations: the form rounded the discount and the tax to whole units and the server did not, so a document approved on screen as «۹۶۸ دلار» was stored — and printed, and settled against — as 968.22. The rounding is the form's, because the form is what a person reads and agrees to before pressing save. What is deliberately **not** rounded is the line totals and therefore the subtotal: a line has to read quantity × unit price and the lines have to sum to the subtotal printed under them, so only the figures a percentage derives are rounded — and `finalAmount` is built from the rounded parts, so the printed document adds up. `getWonItemsCurrencyAmount` rounds its own share-of-the-document figures the same way for a نیمه‌برنده. The printed document reads the stored totals rather than recomputing, so there is no third copy; `test:rules` fails either side that grows its own discount arithmetic again. Existing records keep their old figures until re-saved.
- **The settlement rate is the rate on the day the money arrived, and it is never the invoice's own rate.** The difference between the two *is* the realized exchange gain, so filling the receipt's rate box with the proforma's `historicalExchangeRate` — which this form briefly did — makes every rial paid above the invoice's rial value read as an overpayment: a real 100,454,200 gain filed under «مبالغ تخصیص‌نیافته» while the gain column said zero. `calculateProformaFinance` was right; its input was not. The box is no longer prefilled; both rates are offered as one-click buttons with what each would realize spelled out, the implied one computed to **four decimal places** because that is what the column stores (rounded to the whole rial it strands a few hundred rial as a phantom overpayment). The field is also shown whenever the linked proforma is in another currency, not only beside a typed foreign amount — for a rial receipt against a dollar invoice, the ordinary case here, the figure that decides the whole exchange gain could not be entered at all. `ProformaFinanceReport.actualReceivedRiyal` means every rial received; `allocatedReceivedRiyal` is the part that went against the debt and is what the realized gain is measured on — the two were one field reporting the second under the first's name.
- **A foreign amount of zero is not a foreign amount.** `rialAmountOf` derives a document's rial figure and the test was `foreign != null` — zero is not null, so a plain rial receipt that happened to carry a settlement rate was rewritten to `0 × rate`. The form sends `0` for an empty foreign box by construction and fills the rate in from the proforma being paid, so **every rial receipt against a foreign-currency proforma was stored at zero**: the document existed, the ledger read «۰ ریال», and nothing said why. Guarded in the service rather than in the client that tripped it — the server is the authority on this figure and an integration posting the same shape hits the same thing — and `positiveOrNull` now stores both `amountForeign` and `exchangeRate` as NULL when they are not figures, so the column says which kind of document this is. **Sold, received and outstanding must be three figures about one thing:** the finance row reported `totalRemainingCurrentRiyal` (today's rate) beside a sales figure at the historical rate, so a project with nothing received showed more outstanding than it had ever sold — and people typed the larger figure into a receipt and were warned it exceeded the sale. It reports `totalRemainingHistoricalRiyal`; the today's-rate figure and the exchange gain or loss stay in `summary` under their own headings.
- **A ledger row names things from itself, never from a picker's matches.** The grid printed «پ.ف: ناشناس» and the incomplete-rates tab silently skipped documents, because both resolved the proforma by `proformas.find(...)` against the *picker's* current search results — so a document was named only while its proforma happened to be loaded, which in practice meant only the one just saved, and saving a second renamed the first. `LIST_SELECT` joins `proforma` (number **and** currency, the second being what decides whether a receipt needs a settlement rate) alongside customer, supplier and project. Same trap on the write side: the party name was resolved out of the customer/supplier picker and stored as «مشتری ناشناس» when the match list had moved on — a blank is stored instead, and `rowToTransaction` falls back to the joined name.
- **Searching the transactions ledger reaches the project and the counterparty, not only the document's own columns.** `transactionSearchClause` adds relation filters for the project's code and name, the customer, the supplier and the proforma. Every row shows those, and the «تراکنش‌ها» button on the project summary puts a project into the search box — so a flat search over `documentNumber`/`referenceNumber`/`partyName`/`notes` answered «no results» for a project that plainly had documents. `partyName` is often null in particular: the grid falls back to the joined names. The button sends the project **code**, because codes are unique and several projects here are genuinely called the same thing.
- **A transaction entered by mistake is edited or deleted** — there is no reversing entry, by explicit decision. There used to be one, the textbook answer, and the screen never grew a button to issue it: every document is written «تأیید شده», a confirmed one refused deletion, and the error told the user to do something the application gave them no way to do. Deleting removes the effect in full because the effect *is* the row — a transaction moves no stock and reconciles nothing, it only contributes its amount to totals computed from the rows that exist — and the audit entry keeps the whole document. `countsTowardBalance` is the balance rule and is written as an **exclusion** (`پیش‌نویس`, `لغو شده`): a status nobody anticipated must count as money rather than silently vanish. `ابطال شده` still counts, because a database written before this may hold a reversed original *and* its opposite entry, and those cancel only if both are counted. Three things around it were broken in the same way — by a rule that could not be acted on: the amount guard compared a stored `undefined` against the form's `0` so it refused **every** edit of a confirmed document while blaming a figure nobody had touched; the three summary cards summed the page in hand over every status while a correct server `/summary` existed unused; and the settlement rate was read off a proforma **list row**, which did not carry `historicalExchangeRate`, so the box was filled with nothing every time.
- **A received purchase order reconciles stock against the ledger**, not by revert-then-reapply: it reads what it has already credited (`referenceType`/`referenceId`), compares with what its lines and status now say, and writes only the difference. Idempotent and self-correcting; un-receiving targets zero.
- **Passwords are write-only.** Every user read goes through an explicit `select` that omits `passwordHash`, so a new column cannot leak by default. Callers without the `users` permission get a name-only directory projection rather than a refusal, because the assignment pickers need it. Changing permissions, deactivating an account, or setting a password bumps `sessionEpoch`, which invalidates cookies already issued.
- **`toNumber` translates Persian punctuation, not just digits** — `٫` (U+066B) is the decimal separator; leaving it in place turned `"۱۲٫۵"` into NaN and then into the fallback, silently storing 12.5 as 0.
- **All 18 modules converted**: customers, projects, proformas, products/inventory, suppliers, purchase orders, transactions, tasks, supplier inquiries, deliveries, after-sales, users, settings, exchange rates, audit log, project activities, referrals, module notes.
- **Dates are two columns** (`xDate` DATE + `xDateJalali` string) and `src/server/dates.ts` is the only place that maps between them. Use `expandDateFields` in a service, `jalaliRangeFilter` for a range. Two traps it exists to close: a JS `Date` built from local midnight serializes as 20:30 the *previous* day on this UTC+03:30 host (everything here is `Date.UTC`, read back with UTC getters), and both calendars are written `YYYY/MM/DD` — so `"2026-07-28"` parsed as Shamsi becomes 2647 CE. The year selects the calendar (1200–1600 ⇒ Jalali).
- **Line-item grids** use `syncChildren` (`src/server/childSync.ts`): delete and re-insert inside the parent's transaction, with `lineNo` recording the user's order. Absent means "not edited"; `[]` means "the user removed them all" — conflating those wipes a grid on any partial save. **Never use it for entities that are referenced or append-only** (product variants, activities, referrals, inquiry steps, the stock ledger); rebuilding those breaks foreign keys and destroys history. Variants are reconciled by identity in `productService.ts` instead.
- **Money and derived status are computed server-side, never taken from the request.** `src/server/proformaStatus.ts` holds the outcome rules (a proforma's outcome derives from its line statuses; a project's status derives from its proformas) and writing a proforma re-derives its project in the same transaction. Proforma totals are recomputed from the stored lines.
- **Stock moves only through `applyStockDelta`**, which writes the ledger entry and the new level together — so a movement can't exist without its history. An edited stock field is diffed into a movement; manual adjustments take a signed delta, not a new level, so concurrent adjustments add up. For a product with variants the parent level is the sum of its SKUs.
- **`stockLevel` means *free to sell*, not *physically present*.** Goods bought against a job were sold before they were bought, so they must never become quotable. Won proforma lines supplied from the warehouse deduct the level at the moment they are won (`reconcileProformaStock`). A packing list's issue always passes `affectsAvailable: false` — it writes the ledger and leaves the level alone. A foreign purchase order's receipt does the same **only when the order is tied to a project** (`reconcileStock` in `purchaseOrderService.ts` passes `affectsAvailable: !po.projectId`): those goods were sold before they were bought, so they were never anyone's to promise. An order with no project is a general/warehouse purchase — nothing has claimed the units, so receiving them raises the available level like any other stock. The ledger is the physical record; the level is the promise, and the two differ on purpose while job-specific goods sit on the shelf. All of these reconcile by difference against what they have already written (`referenceType`/`referenceId`), so editing or deleting the document corrects the ledger instead of doubling it.
- **The ledger is append-only for everyone except a system administrator**, who can correct or delete a single row (`updateInventoryTransaction`/`deleteInventoryTransaction`). The gate is `user.isSystemAdmin`, not the `products` permission — a warehouse account with full stock write access still cannot rewrite what the warehouse did. The level is corrected by the **difference** inside the same transaction, and only when the row's own stored `affectsAvailable` says it moved the level in the first place; that flag exists on the row precisely so a correction can put back exactly what it took. A row's product, SKU and source document are not writable — moving a row between products is a delete plus a fresh adjustment, where both halves are visible. Both operations write an audit entry with before/after.
- **Record-level access is applied inside the query**, never as a post-filter — otherwise the pagination totals leak the existence of records the user can't see. `visibilityClause` returns `undefined` for a user with the module permission and `{ ownerUserId: user.id }` otherwise, and writes re-check it before touching the row.
- **Bodies are picked, not spread** — routes copy only an allowlist of writable fields, so a client can't set `id`, `createdAt`, `ownerUserId`, or a derived column like `mobileNormalized`.
- **Seeding** — `npm run seed:db` (users, settings, exchange rates only; no demo business data). Idempotent: users upsert on `username` and never have their password overwritten, settings and rates are create-only so live values aren't reset.
- `npm run db:deploy` / `db:generate` wrap the Prisma CLI. `GET /api/db-health` reports connectivity (authenticated — the error text names the server and database).

## Power BI reporting

Reporting is a **separate, one-way export** and is unaffected by the migration above — it targets its own `ata_erp_reporting` database. `src/reporting/flatten.ts` turns the document store into 25 flat tables (each nested array becomes a child table carrying its parent's keys denormalized), and `src/reporting/sqlSync.ts` loads them into a SQL Server `rpt` schema inside one transaction (replace-all; volumes are small). **Custom fields get two of those tables**: `custom_fields` is the dictionary (id → module, label, type, options) and `custom_field_values` is every record's answers unpivoted to one row per (module, record, field) with the label denormalized on. They exist because `customValues` is keyed by field *id* while the label lives in `settings.customFields`, which never reached the reporting database — so the JSON arrived as a bag of `cf-…` keys nobody could read. The per-module `custom_values` JSON column stays for existing reports. A value whose field was later deleted is kept with `is_defined = false` rather than dropped. **All ten modules the settings screen offers now carry `customValues`** — `packagingDelivery` and `afterSalesServices` got theirs in `20260823000000_custom_values_two_modules`; before that a field could be defined for either and filled in nowhere, because no table had a column for the answer. `CustomFieldsForm`/`CustomFieldsDetailView` take `CustomField['module']` rather than their own spelled-out union, which is how they came to be two modules behind. `FlatDataset.columnTypes` declares types the loader must not guess: `value_number` is empty until a numeric field is filled in, and inference would create it as NVARCHAR and silently turn every later figure into text. Power BI reads that with its native connector. Dates stay Shamsi **strings** by explicit user decision — they convert them in Power BI. `flattenUsers` deliberately omits `password`; credentials must never reach the reporting DB. Setup and suggested relationships: `docs/powerbi-setup.md`.

## Deployment

Live on a **shared** Windows server (`192.168.1.104`) alongside IIS, SQL Server, Power BI Report Server, MSMQ, Sentinel licence servers, VMware and VoIP — so changes there must be additive only. Never edit the server's folder directly: develop locally, push, then run `scripts/deploy.ps1` on the server, which backs up the data, pulls, installs, lints, builds, and **only restarts the app if lint and build both pass** (restoring the previous build otherwise). Full guide, including one-time setup and rollback: `docs/deployment.md`.

## Gotchas

- `server.ts` is bundled by esbuild (`npm run build`), which resolves every import at bundle time — so its imports (routes, services, `src/server/*`) must stay statically analyzable, no dynamic paths. Seed constants (`SEED_USERS` etc.) are **not** among them: `scripts/seedDb.ts` imports those directly and runs unbundled via `tsx`, never through `server.ts`.
- Seeding is `npm run seed:db` and creates users, settings and exchange rates only — never demo business data. It is idempotent: users upsert on `username` and never have a password overwritten.
- The server binds `0.0.0.0` and has no session/token auth beyond the login endpoint; it assumes a trusted LAN. Do not expose its port to the internet.
- **A callback prop handed to a child that fetches must be stable.** `MessagingView` built its `report`/`flash` helpers inline, and the tabs below list `onError` among the dependencies of the `useCallback` that loads their data — correct in itself, but a new function on every parent render meant a new `load`, so the effect watching it fired again. `App` re-renders whenever the sidebar badge poll returns (a minute) and on every live-data change event (any write, anywhere), so the screen refetched over and over and jumped back to the top each time. `useCallback` with an empty dependency list is right for a helper that closes over nothing but state setters. `npm run test:ui` renders the screen under a parent that re-renders and asserts the fetch count does not grow — the same shape as the price-calculator test below, and the same family of bug.

- **`<input type="number">` cannot hold a decimal being typed.** The HTML value-sanitisation rules report a value that is not a *complete* floating-point number as the empty string, so the instant somebody types the point in «0.7» the handler is given `""`, `Number("")` is 0, and the controlled value re-renders over what was typed — the field is unreachable by keyboard and only the spinner arrows get there. It was reported on the assistant's «خلاقیت», and the same control was on the supplier-inquiry discount, where the same three keystrokes silently turn 2.5% into 25%. `NumberField` (`src/components/NumberField.tsx`) is the answer and every numeric box should use it: a text input with `inputMode`, the typed text held as a draft, and a number reported only once `parseDecimalInput` finds a whole one — `null` means «not yet», which is what lets «0.», «-» and «» exist on the way to a figure. It accepts Persian digits and `٫`, rejects a keystroke that could never become a number, and resyncs the box on blur so a clamped figure shows the cap. The rules are pure in `src/utils/numberInput.ts`; `test:rules` covers them and `test:ui` types a decimal one keystroke at a time through the real DOM node — jsdom implements the same sanitisation, so driving the handler with a made-up `{value}` would skip the very step under test.

**A modal must not seed its state from an object prop.** `useEffect(..., [initialValues])` where the parent builds `initialValues` inline re-seeds on *every* render of the screen behind the modal — and those screens re-render on their own, so a half-typed form was silently reset to zero, repeatedly. Key the seeding on what means "start again" (open, and the subject's id) and read the values through a ref. `npm run test:ui` renders the price calculator and asserts a typed figure survives a parent re-render.
- **Shallow-copying arrays of records is a trap.** `const next = [...items]; next[i].field = x` mutates the objects the store still holds, which made before/after comparisons identical — that silently stopped SKU stock changes from being logged as inventory transactions and corrupted audit-log snapshots. Always replace the element: `next[i] = { ...next[i], field: x }`.
- Persian text in **console/CLI** output is mangled by the Windows console codepage, so `scripts/*.ts` print English. JSON API messages stay Persian (they render correctly over HTTP and are shown to users).
- Windows PowerShell 5.1 doesn't enable TLS 1.2, so GitHub downloads fail until `[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12` is set.
- **`DATABASE_URL` is a JDBC-style string, not a URL.** `sqlserver://host:1433;database=…;user=…;password=…` — do **not** percent-encode the password: `%40` is read literally and fails with `P1000`. Only `; = { }` need escaping, by wrapping the value in braces.
- **`sqlcmd` connects with `QUOTED_IDENTIFIER OFF`**, and SQL Server refuses to create filtered or computed-column indexes in that state (`Msg 1934`). `prisma/sql/extra-indexes.sql` sets it explicitly; pass `-I` as well when running SQL by hand.
- **A second instance on another port is not an isolated one.** `PORT=3100 npx tsx server.ts` still reads `DATABASE_URL` from `.env`, so any endpoint you exercise writes to the **real** database. Point `DATABASE_URL` at a scratch database, or clean up what the test created and assert the counts back to zero.
- **Git Bash mangles Persian in `curl -d`** — the UTF-8 arrives as `?????`, which then looks like an application bug (e.g. `mobileNormalized` coming back `null`). Drive HTTP tests from a Node script using `fetch` instead of composing them in the shell.
- npm blocks package install scripts by default here. That was harmless for `esbuild` (its binary arrives via optionalDependencies) but **not** for Prisma, whose engines come from its install script — approve with `npm approve-scripts` and `npm rebuild` if Prisma commands fail.
- **A migration that has shipped is history — never edit it.** Prisma records a migration by *name* and never runs it again, so amending an applied one reaches every repository and no database. This is not hypothetical: `discountAmount` was added to `20260808000000_inquiry_discount` after that migration had run, so `discountPercent` existed and `discountAmount` did not, and the whole supplier-inquiry module answered P2022 — "The column `discountAmount` does not exist in the current database" — on every read and write, while `_prisma_migrations` listed every migration as applied. Add a new migration instead, guarded with `IF COL_LENGTH(...) IS NULL` so it is safe on databases built after the amendment. `src/server/schemaCheck.ts` now verifies the *columns* the migrations create, not just their names, because names alone cannot see this.
- **`npx prisma migrate dev` cannot run here** — the SQL login has no `CREATE DATABASE` right, so the shadow database fails with `P3014`. Write the migration SQL by hand (see `prisma/migrations/20260803000000_*`) and apply it with `npm run db:deploy`. `migrate diff` is also unhelpful: it wants to re-create ~18 DEFAULT constraints that introspection does not report, burying the real change.
- **`assertComplete` cannot see a handler that builds a fresh object.** The partial-record guard fires on a list row *spread* into a write payload, so a handler that reads a row and constructs a new literal slips past it — `handleCopyProforma` copied a proforma from the grid row, whose lines carry only name, quantity and status, and the new document came out with no prices, no product ids, no specs and no costs. What surfaced was the cost check refusing the save, naming lines whose cost was filled in perfectly well on the document being copied. Any handler the grid calls with a row must load the detail record itself (`isPartial` → `api.get(id)` → `detailTo…`), the way `handleOpenPrint` does; `test:rules` pins both.
- **A cast is not a check.** The client adapters end in `as unknown as Product` and friends, because the client types carry fields a list row does not. That means a wrong field name inside the object literal compiles cleanly and fails at runtime — three separate bugs reached the browser this way (`calculatedLandedCostRIYAL`, `calculatedLandedCostForeign`, and `useUserDirectory()` returning `{ users }` rather than an array). Open the screen; a green type-check proves less here than usual.
- **Ids belong to the database, and a line's `productId`/`variantId` is a real foreign key.** The proforma configurator auto-created a SKU, gave it `var-${Date.now()}`, saved the product *without awaiting it* and put its own id on the line — but `reconcileVariants` assigns the id on insert, so the line referenced nothing and the whole proforma failed with P2003. `sendError` mapped that to «این رکورد … قابل حذف نیست», which describes a delete the user was not doing. Three things now hold it: `src/server/refIntegrity.ts` (`scrubProductRefs`) drops a dangling reference so the document still saves, `sendError` answers a non-DELETE P2003 with "one of the selections no longer exists", and `test:rules` reads the source for both — every line-writing service must scrub, and no screen may write a made-up id onto a foreign key.
- **After-commit side effects must never fail the request.** The audit entry, the notification, the workflow rules and the project timeline run *after* the write transaction on purpose — but they were awaited plainly, so anything one of them threw came back out of the route as a failed save: the record existed, its document number was taken, and the user made a second one. `src/server/afterCommit.ts` logs and swallows. Same rule as `milestoneAutomation.ts`.
- **An uploaded folder name must be Latin.** `/api/upload`'s `folder` query param is sanitized with `[^a-zA-Z0-9_-]`, so a Persian name reduces to an empty string and the file lands in the uploads root instead — silently. The Persian folder names users see (the project documents tab) are a *logical* grouping stored on the record as `manualDocuments[].folderName`, not directories; the two are unrelated. Customer satisfaction letters show the pattern: logical folder «رضایت‌نامه‌ها», physical folder `satisfaction-letters`. `src/server/uploadsDir.ts` owns `UPLOADS_DIR` and is the only place that maps a `/uploads/...` URL back to a path — `resolveUploadPath` returns null for anything outside it, which is what stops the letters zip from being asked for arbitrary files.
- **A "kind" tag identifies a document, not its name or folder.** Both `projectConfirmation` and `satisfactionLetter` are entries in a project's `manualDocuments` JSON marked with `kind`, because a user may rename a file or move it between folders — so neither can stand in for what the document *is*. `src/server/services/satisfactionLetters.ts` reads them back with a `manualDocuments: { contains: kind }` pre-filter (a cheap `LIKE` that SQL Server can run) and then parses each candidate, which is the authority. That screen deliberately answers with the whole filtered set rather than a page: its amount filter is computed from won proformas and Prisma cannot put a relation count in a `where`, so paging first would filter the wrong set. The whole-set work happens on the server, bounded, with a `truncated` flag rather than silently dropped rows.
- **Customer value is two axes and a matrix, never an average.** `src/utils/customerValue.ts` is the rule and is pure: *Realized* (gross profit 50, frequency 20, recency 15, payment 10, cost-to-serve 5) and *Potential* (five 1–5 judgements weighted 30/20/20/20/10), each 0–100, and the A/B/C/D rank comes from the **matrix** of the two against `highRealizedThreshold`/`highPotentialThreshold`. `CVI = realized×0.6 + potential×0.4` orders customers *within* a rank and must never decide one — a new customer with no history and high potential has to come out C, and averaging first calls them D. A customer whose five potential answers are not all filled in is `PENDING`, not zero: unknown is not low. **A customer who has never had a confirmed purchase is `PROSPECT` («مشتری بالقوه») and gets no rank at all** — half of A/B/C/D is a judgement about money that has changed hands, so ranking a lead puts them at D, "low value, low priority", which is backwards for an account the sales team is working on. `determineRank` takes `hasConfirmedPurchase` as a **required** argument so the type-checker names every call site, and checks it *before* the potential assessment (an unassessed prospect is still a prospect). Their stored `realizedValueScore` is 0 and `customerValueIndex` is null — not a low score but an inapplicable one, since payment and cost-to-serve are 15 points of manual opinion about somebody who has never paid an invoice — and they are sorted by potential instead, excluded from the matrix and from the population averages. The signal is `hasEverPurchased`, which reads `lastPurchaseDate` (**every** sale ever) and never `purchaseFrequency` (the evaluation period only): a customer who last bought three years ago is *lapsed*, not a prospect, and their recency score already says so. The first confirmed sale moves them into the matrix with no other change, through the recalculation the write already schedules. `test:rules` covers all ten acceptance scenarios plus this rule. Weights must total exactly 100 or the settings refuse to save — they are the divisor of a weighted average, so 90 would deflate every score by a tenth and the whole table would drift down a rank together.
- **Where the sales figures come from.** A sale is a proforma whose outcome is won or part-won (`getProformaOutcome`, so a cancelled document with `برنده` lines is not one); one proforma is one purchase however many lines it has; **the sale's date is the project's `winningDate`** — «تاریخ تایید (ابلاغ قرارداد)», stamped when the project first becomes won — falling back to the proforma's `issueDate` only when there is no project or none was stamped (`saleDateOf`). Not the issue date: a quotation written in Farvardin and approved in Mehr is a Mehr sale, and that gap is routine here, so the issue date puts the sale in the wrong evaluation period and makes the customer look months staler than they are — 2 months against 8 in the covered case, which is two whole recency bands. Because the effective date can come from the project, the evaluation window **cannot be a SQL `where`** on `issueDate`: `collectRawFigures` scans candidates cheaply, lets `saleDateOf` decide what falls in the period, then reads only those in full. **Cost of goods is now a column on the sale line** — see the entry below; the two older sources survive only as fallbacks for rows written before it, and a line with none of the three is left out of **both** sides of the margin rather than counted as pure profit, with `costCoveragePercent` recording how much of the revenue could be costed so a suspiciously good margin reads as missing data. Gross profit and frequency are **percentiles against customers active in the period**, so they are meaningless alone and one customer's sale moves everyone else's score — which is why there is no correct way to recalculate a single customer, and why `recalculateAll` is the only real entry point. Writes schedule one through `customerValueRecalc.ts`, which coalesces and can never fail a save; a daily job ages recency on.
- **Every proforma line carries its own cost.** `ProformaItem.unitCost` / `costCurrency` / `costSource` are the home of record, and a save is **refused** — client and server both, `assertLinesCosted` in `proformaService.ts` — if any line has neither a figure nor an explicit «بدون بهای تمام‌شده». The rules are pure in `src/utils/costOfGoods.ts` and covered by `test:rules`. Four things force the design: a product's cost changes, so looking it up when a report needs it rewrites last year's profit and re-ranks customers who bought nothing since; a free-text line has no product to look anything up from; `PurchaseOrderItem.proformaItemId` is a plain column that `syncChildren` orphans on the next save; and an uncosted line reads as **pure margin**, which flatters exactly the sales nobody bothered to cost. The figure is in the **proforma's own currency**, matching `unitPriceRial` beside it — that is what makes the margin *percentage* independent of the exchange rate, and it is why `handleCurrencyChange` must convert cost and price together. `costSource` distinguishes evidence (`PURCHASE_ORDER`, `PRICE_CALCULATOR`) from assertion (`MANUAL`), a deliberate zero (`NONE` — a service line, or goods the customer supplies) from a blank, and the migration's own guess (`BACKFILL`). **A received purchase order corrects the estimate** — `pushActualCostToProformaLines` in `purchaseOrderService.ts` writes the real landed cost onto the lines it supplied, but only where the stored source was never a person's answer (`null`/`PRICE_CALCULATOR`/`BACKFILL`/`PURCHASE_ORDER`; `MANUAL` and `NONE` are left alone). It sums across **every** received order pointing at that line, so a split purchase blends by quantity and re-saving writes the same figure; un-receiving does not restore the guess. It schedules a customer-value recalculation, because the gross profit behind those ranks has moved. `NONE` storing a real zero rather than a null is the whole reason the check can tell "there is no cost" from "nobody has got to this yet". Two screens capture it: the line grid on the proforma form, and the **outcome modal** — a line marked won with no cost is the one that corrupts the ranking, so that table has a cost column too and legacy documents get answered there rather than dead-ending on save. A technical proforma quotes no prices and is exempt at both ends. `TransactionsView`'s rate-only write deliberately **omits `items`** so it does not have to pass the check.
- **The proforma line's price calculator loads the whole product; the screen only has list rows.** A product `LIST_SELECT` carries no `priceCalc`, and its variants come back with an id, a SKU, attributes and a stock level and nothing else — so seeding the modal from `productPicker.matches` opened every field blank however carefully it had been filled in last time, and the missing starting foreign price made it recompute and *change* the price on apply. The record is read when the modal opens (which also means the figures are what the catalogue holds now, not what the picker fetched at page load), and the modal does not render until it has arrived — opening on zeros is the bug, not a loading state. Same family as the proforma number, the settlement rate and «پ.ف: ناشناس»: a screen must not resolve a record out of a picker's matches.
- **The price calculator has a manual mode.** `PriceCalcInputs.mode` (`BREAKDOWN` | `MANUAL`, absent = BREAKDOWN so every stored record keeps computing as before). Not every item is imported: goods bought locally or quoted all-in have a cost that is simply known, and forcing that through a freight-and-customs breakdown meant inventing figures or leaving the cost blank. Both figures are entered in the **item's own currency**. The modal's `onApply` now hands the caller the landed cost alongside the selling price — it used to compute it and throw it away, which is how proforma lines came to keep the price and lose the cost that produced it. `calcSeedOf` in `productAdapter.ts` is the single list of calculator fields, shared by the modal's seeding and by what gets persisted (`PRICE_CALC_KEYS`, guarded by `_EveryCalcFieldIsPersisted`); spelling the fields out at a call site is how one comes to be collected and then dropped. **`landedUnitCostOf` in `costOfGoods.ts` is the single reader** of a stored calculator — the proforma form's suggestion and the customer-value fallback each had their own copy and had already drifted, the server inheriting the product's calculator for a SKU with none of its own while the client did not. A SKU's own figures win; one with none inherits the product's.
- **A catalogue item has one currency, and every SKU under it follows.** Changing `currencyForeign` on the product form rewrites all its variants; `ProductVariant.currencyForeign` is a copy, never an independent choice. The price calculator, though, runs in whatever currency it is opened in — often the proforma's — so writing its result onto a SKU together with *its* currency put that SKU out of step with its product, and since the form reads the **product's** currency the figure then displayed as if it were in a currency it was never in (150 دلار stored against a یورو product read back 15,000,000 rial instead of the 13,500,000 agreed). The rial column stayed correct, which is why it went unnoticed. `priceInWarehouseCurrency` in `src/utils/finance.ts` converts before the write and the currency is restated rather than replaced, which also repairs a SKU that had already drifted; it returns null when no rate is known, because the original number under the wrong label is the bug itself. Anything reading a SKU's currency must fall back to the **product's**, not to a hardcoded «یورو». **A price typed by hand into a proforma line does not reach the catalogue on its own** — a deal price is usually specific to that deal, so one negotiation must not rewrite the list price for everybody. `publishPriceToWarehouse` is the explicit button beside each line, deliberately the same gesture as the calculator's «اعمال»; it converts to rial at the document's own `historicalExchangeRate` (today's rate only as a fallback) and refuses rather than guessing when neither is known.
- **What an item last really cost is recorded beside the standard, never into it.** `Product`/`ProductVariant` carry `lastPurchaseCostRial`, `lastPurchaseQuantity`, `lastPurchaseDate(Jalali)`, `lastPurchaseOrderId`/`Number`, written by `recordLastPurchaseCost` when a purchase order is received. They are **not** `priceCalc`: the calculator holds the *standard* cost the company quotes from, while a line's share of an order's landed total carries the freight and customs of **that shipment** — five units flown in urgently genuinely cost several times what two hundred by sea do, so writing one into the other would price every future quotation off whichever delivery arrived last. The quantity is stored precisely so the screen can say how representative the figure is. Written from the **most recent received order** per position rather than from the order being saved, so re-saving a months-old purchase cannot overwrite a newer figure and saving twice writes the same thing. Neither `productScalarData` nor `variantScalarData` lists these, so a product save can never touch them; they are in `PRODUCT_COST_FIELDS` so a user without `costs` sees none of it, order number included. `costDrift`/`COST_DRIFT_THRESHOLD_PERCENT` in `costOfGoods.ts` decide when the gap is worth showing, and `LastPurchasePanel` shows it. **Adoption is a button, and the selling price never moves on its own** — `sellingPriceFor` only *displays* what the stored margin would imply, because a supplier's rise is not automatically the customer's. Adopting switches the calculator to MANUAL (a single landed figure cannot be decomposed back into purchase price, freight and customs without inventing the split) and converts at **4 decimals**: at 2 a 12,000,000 rial cost at a rate of 90,000 reads back 300 rial short and the warning the user just acted on never clears.
- **A purchase order's landed cost is apportioned to its lines** and stored (`PurchaseOrderItem.landedUnitCostRial` / `landedUnitCostForeign`), by value share, since freight and customs belong to every line on the order. `allocateLandedCost` reads the stored state back and runs **unconditionally** after both create and update — it used to be skipped when `items` was absent from the request, so entering customs afterwards left every line cost stale.
- **A rank can be set by hand, and the *mode* is the feature.** Overriding a rank means one of two different things and the system cannot guess which, so it asks: `locked` keeps the rank whatever the figures do; `resume` shows it now and lets the evaluation take back over at the next recalculation, which **clears** the override — leaving it would show a rank the metrics beside it no longer agree with. `resolveRank` in `src/utils/customerValue.ts` is the rule (a `manualRankLocked` with no rank is not an override, and must never blank a rank). `metrics.customerValueRank` is the rank *in effect* so the grid filters and sorts on one column, while `computedRank` keeps what the formula said — an override never hides what it overrode, and `rankIsManual` marks it in the grid and the export.
- **The manual half lives on `customers`, the computed half in `customer_value_metrics`.** People edit the first (five potential answers, payment behaviour, cost to serve); a recalculation rewrites the second wholesale. `paymentReviewed`/`costToServeReviewed` distinguish a judgement from the migration's placeholder. Changes to a potential assessment append to `customer_potential_history`. None of the computed columns is in the route's writable allowlist — a client that could set its own rank would set it to A. Editing thresholds changes nobody until `POST /api/customers/recalculate-value` runs.
- **`schemaCheck` understands `DROP COLUMN`.** It expects every column any migration adds to still exist, so a later migration retiring one would otherwise make the database look permanently broken — which is exactly what happened when the old single-axis customer level was replaced.
- **The dashboard assistant reads through the same services the API does.** `src/server/services/assistant/` is a provider client (OpenAI-compatible `/chat/completions` with tool calling, so one setting — the base URL — reaches OpenAI, OpenRouter, an Iranian gateway or a model on this network), a tool registry, and the loop between them. Every tool calls the same service a route calls, so record-level visibility and `canSeeCosts` hold unchanged — an assistant is not a second way into the data. The tools are **answer-shaped, not table-shaped**: `project_timeline` answers «کجا هولد شده و چند روز» and `activity_stats` answers «میانگین زمان انجام فعالیت», because a model handed `run_sql` writes plausible wrong queries. Arithmetic across rows lives in the tool, never in the model. **`permissions.assistant` is read strictly** (`=== true`), like `costs` and unlike every module flag: it can read every figure its user is allowed to see, all at once, so no account written before it existed gets it by default. The API key is a row in `assistant_credentials`, never in `settings` — that document is loaded whole by every browser. Pure config and prompt rules are in `src/utils/assistant.ts` and covered by `test:rules`. **`temperature` is `number | null`, and null means «do not send the field».** The reasoning models (o-series, gpt-5, and what the Iranian gateways proxy of them) accept only their own default and answer 400 to any explicit value — «does not support 0 with this model. Only the default (1) value is supported» — so a setting that could only ever produce a number made those models unusable, and an absent value read as 0 sent one anyway. `unsupportedParameterFrom` reads the refused field's name out of the provider's own 400 and `chat` sends the request again without it, at most once per field, so nobody has to guess which setting a provider dislikes; the token cap is **renamed** to `max_completion_tokens` rather than dropped, because it is the only thing between a confused model and a bill. `testAssistant` sends the *configured* temperature — it hardcoded 0 while the screen offered a box to change it, so the connection test exercised a request nobody had configured and failed however the setting was left.
- **The proforma form has a product adviser, and it only reads.** `src/server/services/assistant/advisor.ts` takes a customer's enquiry plus their files and proposes items; `POST /api/assistant/product-advisor` is the endpoint and `ProductAdvisorModal` the screen. Four things decide whether it is useful rather than a demo. **The catalogue is searched by feature value, not by name** — a flow meter is identified by «clamp-on, DN50~DN700, water», which no keyword match on a title finds, so the search reads the `features` JSON as text and hands the model each candidate's features and existing SKUs. **Ids come from the catalogue, never from the model**: every suggestion is resolved against the database before it leaves the service, and a product or SKU that is not there is downgraded (`exact` → `close` → `new`) rather than put on a line as a foreign key referencing nothing. **A card is a preview of the printed line** — the same two columns, the same «Label: Value» specification from `suggestionSpecText`, the same image — so «افزودن به ردیف» is not a leap of faith; the line lands in the form's own `items`, unsaved, and a wrong one is removed by deleting the row. **A file that could not be read says so.** `attachments.ts` extracts PDF text (`pdf-parse`, required at call time so its self-test never runs at import), reads spreadsheets through `xlsx`, and sends pictures as `image_url` content parts — which needs a vision model, and one that is not answers 400. A file silently ignored is worse than one never attached: the answer looks considered and is missing half the question. Attachments are read through `resolveUploadPath`, so a request cannot ask for a file outside `uploads/`.
- **The assistant proposes; a person confirms. There is no third path.** An action tool does not write — it calls `prepare`, which reads, resolves what the model asked for into a complete write, describes it in Persian, and stores *the payload itself* in `assistant_actions`. The browser receives a summary and an id; pressing «تایید و ثبت» posts the id back and `confirmProposal` executes the stored payload through the module's own service. The payload never makes a round trip through the client, because then the record written would be whatever the browser last held rather than what the person read. Four rules hold it: the guarding permission is the **module's own** `erp_*` key (`checkKeyAccess`, at both ends — a permission can be withdrawn between the proposal and the button, and withdrawing it has to mean something); the claim is a **conditional** `updateMany where status: "pending"`, which is what makes a double-clicked confirm issue one proforma rather than two; a proposal belongs to **one user** and expires after `PROPOSAL_TTL_MINUTES` (it is a photograph of the data at the moment it was prepared); and **document numbers are issued in `execute`, never in `prepare`**, so a proposal nobody confirms does not burn one out of the series. `failed` is terminal — the payload was built against a database that has since moved, so the next attempt is a fresh proposal, not a retry. `test:rules` reads the source and fails a `prepare` half that calls any Prisma write, an action guarded by a key `KEY_PERMISSION` does not know, or a numbering rule copied back into a route (`src/server/documentNumberSpecs.ts` is the single home of the proforma and packing-list series); `test:ui` renders the panel and asserts that drawing a card confirms nothing and that the button confirms exactly once. The confirm posts to `/api/assistant/…`, so the API client's automatic change event names a resource nothing reads — each action carries the `resource` it really wrote and the panel announces that instead, or the grid behind the panel keeps showing the old list.
- **A third party gets the same API, not a second one.** `Authorization: Bearer ata_…` is resolved in `requireAuth` — the one function every route reaches through `RouteDeps` — so n8n drives the existing REST API as a named user and every `checkKeyAccess`, every `visibilityClause` and every cost redaction applies unchanged. There is no integration permission model to keep in step with the real one. `src/utils/apiTokens.ts` holds the pure rules and `src/server/services/apiTokenService.ts` the rest. Four things it is worth not re-deciding: the token is stored as a **SHA-256**, not bcrypt — bcrypt's cost exists to slow dictionary attacks on a secret a person chose, this is 256 bits from `randomBytes`, and the unique index turns authentication into one index seek instead of a bcrypt comparison per row on every call an integration makes; a read-only token is refused **by HTTP method** rather than by a list of write routes, because the endpoint nobody remembers to add to such a list is the one that matters; `pathClosedToTokens` shuts two paths to every token however wide its scope — `/api/api-tokens/*` (a credential that can mint credentials outlives every decision made about it) and the assistant's `/confirm` (that button means "a person looked at this", which a request from an automation platform cannot mean); and `lastUsedAt` is written at most every five minutes, unawaited, or an integration polling every minute turns each read into a write on a database shared with Report Server. `findAuthUser` already refuses an inactive account, so deactivating somebody stops their integrations too. `docs/api-integration.md` is the guide handed to whoever wires it up.
- **Messaging is a module; automating it is not.** `src/utils/messaging.ts` holds the pure rules (SMS part arithmetic, template rendering, quiet hours, retry backoff, recipient resolution) and `test:rules` covers them. Three drivers behind one dispatch in `services/messaging/drivers.ts` — MeliPayamak-shaped REST, Bale's bot API, SMTP via nodemailer — each returning `{ok, error}` rather than throwing, because a provider being down is an ordinary outcome for a queue that will retry. **Nothing is ever sent inline**: `queueMessage` writes to `messages` and a one-minute `setInterval` in `server.ts` drains it, which is what makes scheduling, quiet hours and retries possible at all — each is only a `scheduledAt` in the future. `processQueue` refuses to overlap with itself. **A template's variables are one list** — `MESSAGE_VARIABLES` in `messaging.ts` carries the key, the label and a sample; the palette and the preview both render from it and `test:rules` reads `messageVariables` in the service and fails when the two sides disagree either way, because the palette used to be a hand-written line of names and a value the server started providing was invisible. `renderTemplate` keys on **presence**, not truthiness: a missing key stays written out so a typo is obvious, while a key that is there and empty is substituted — a company and a person of unrecorded gender both have no honorific (`namePrefixFor` in `src/utils/honorific.ts`, the single home of «جناب آقای مهندس»/«سرکار خانم مهندس», which used to be spelled out at four call sites in `ProformasView`), and `{namePrefix}` left standing is the placeholder itself reaching the customer; `addressee` joins prefix and name so the common blank case does not leave a double space. The variables describe **whoever the message is addressed to**, which is the project's messaging contact when it names one — the text has to agree with the envelope. The workflow engine's `send_message` merges `messageVariables` under its trigger payload for the same reason: the payload knows the new status and nothing about how to greet anybody. **A template is written in one place and referred to from the other.** The rule editor picks a `templateId`; it has no box to type a message into, and `template?.body || config.bodyTemplate` is the precedence (it used to be the other way round, from when a rule could only carry its own text — two editable copies of one message is how the two come to disagree). A rule saved before that keeps working through the fallback and the editor offers one button to turn its text into a real template; saving a `send_message` action with neither is refused, because the engine renders an empty body and skips the send without a word. `GET /api/messaging/templates` accepts `settings` as well as `messaging`, since the rule editor lives in the settings screen. **`settings.messaging` — quiet hours, `dryRun`, `maxAttempts` — is edited on the providers tab**; the server read all three from the start and nothing wrote them, so the dry-run switch existed and could not be found. A dry run is checked **before** the provider lookup: it never reaches a provider, so it must not require one either. **Automated sending is a third action type on the workflow engine** (`send_message`), sharing its 21 event triggers, its `time_elapsed` trigger, its conditions and its `workflow_firings` once-per-record index; there is no second engine and no automation tab. **A project can be exempted from the rules, and only from the rules.** `Project.suppressAutoMessages` makes the engine skip that job — the alternatives were disabling a rule for everybody or setting the customer's own `doNotContact`, which silences them on every other project too. The condition is `input.workflowRuleId && project.suppressAutoMessages`: dropping the first half turns a per-project exemption into a gag order and a person writing by hand sends nothing. It answers `suppressed: true` rather than a plain refusal so the engine can tell «nobody could be reached» — worth a notice to the module owner — from «we were asked not to», which would be a notice every time somebody used the setting. The project form's messaging recipient reads `linkedContactsPicker` (`linkedTo=<customer>`, `customerType=حقیقی`), the same one the financial and technical contact fields use; it used to look ids up in the customer picker's twenty-five search matches, where a company's own people never are, so the list was always empty. Two rules that are easy to get wrong: provider credentials never leave the server (masked hints out, and a blank secret on save means "unchanged" — the `passwordHash` rule), and an opt-out on the contact a project *names* stops the message rather than falling through to the customer's own number, which would be honouring the opt-out through one door and ignoring it through another. Persian SMS is UCS-2, so the part counter is 70 then 67 — it is money, not decoration. **Bale addresses a person by a numeric chat id, never by a phone number** — its `chat_id` takes a number or `@channelname` and nothing else, and it answers a mobile number with "no such group or user", which reads as a fault here rather than as the wrong kind of value. `isBaleChatId`/`looksLikeMobile` in `messaging.ts` refuse it before the request (a leading zero is what separates the two, not a length rule: an account id is a counter and never starts with one, while `9121234567` is genuinely ambiguous and goes through), `baleFailure` in `drivers.ts` turns Bale's English `description` into an instruction (`emailFailure` beside it does the same for SMTP — a certificate whose name does not match the server's is the shared-hosting case, and the two switches that answer it, `secure` and `allowSelfSigned`, existed in the config from the start with nothing drawing them, so the only way to reach them was a hand-written row; an explicit `secure: false` deliberately does not disable the port-465 inference), and `baleRecentChats` reads the id off `getUpdates` — sending no `offset`, so the updates are read and not consumed — because that is the only place it can be obtained: the customer cannot see it, nothing here derives it, and the bot cannot write to them until it has been typed in.
- **An activity carries a list of files, in two places at once.** `project_activities.attachments` is JSON (`[{name,size,url}]`) and the three original `attachment*` columns still hold the **first** entry, so the Power BI export and anything else reading them is unaffected — which is also why `parseAttachments` never reads both: the first file would appear twice. `src/utils/attachments.ts` is the whole rule and `test:rules` holds it. On the edit route an absent `attachments` means «not edited» and a present one means «this is the whole list», the same distinction `syncChildren` draws, because conflating them detaches every file from an entry whose text somebody corrected.
- **An activity category can be renamed but not deleted once used.** The settings screen's «وضعیت استفاده» column was a literal `const isUsed = false`, so every category read as unused and the delete button looked available on all of them; it now draws on `GET /api/activity-categories/usage`, one `groupBy` for the whole list rather than a request per row. A rename goes through `renameCategory`, which also rewrites `categoryName` on every `ProjectCategoryGroup` using it — that column is denormalised so a project's history survives the category being removed, which is exactly why a settings-only rename would leave every existing project showing the old wording for good. `test:rules` reads the screen and fails if the flag is hardcoded again.
- **The project activity feed is a messenger, and a mention is a referral.** Staff record what happened on a job in the same place they talk about it, so the feed composes like a chat: `ActivityComposer` has an `@` list, a reply banner and one send button. **The «ارجاع» checkbox is gone** — it sat beside a colleague picker and a separate "what should they do" box, three controls saying what the sentence already said and two texts to keep in step. Naming somebody raises the referral and **the message itself is the action required**. `src/utils/mentions.ts` is the pure rule and `test:rules` covers it: names are matched against the **real directory, longest first**, never against a pattern, because a name here is two or three words with spaces («@علی رضایی» would name a colleague called «علی» under any `@\w+` rule); `mentionSpans` reports indices into the **original** text so the feed can mark them, which is why `normalize` is length-preserving; the author is never mentioned into their own inbox; and `mentionIsComplete` closes the suggestion list once a name is picked, or Enter picks the same person again instead of starting a line. **`project_referrals.activityId` lost its UNIQUE index** (`20260903000000_activity_messenger`) — «@علی @رضا لطفاً بررسی کنید» is a request to two people, which the unique index forbade outright — so `activity.referral` is `activity.referrals[]` everywhere, each with its own `ReferralThread`. `replyToId` is a self-relation with **NoAction** (deleting a message must not silently take every answer with it, and the cascade paths here are already at SQL Server's limit) and the parent is checked against the same category group, since the id comes from a browser. `deleteActivity` refuses a message that has replies as well as one whose referrals have answers. **A message can become a task on your own list** (`TaskFromMessageModal`): half the work on a job is handed out in conversation without anybody being formally referred, and that left the person holding a commitment with nothing recording it. It is assigned to the reader and **only** to them — handing work to somebody else is what naming them does, and that raises a referral with a thread rather than a task appearing silently on their list. The reporting export still fills its five `referral_*` columns from the first request and gains `referral_count`, so a report built on them does not silently lose the rest.

- **A referral is a conversation, drawn by one component in both places it appears.** `ReferralThread` renders the request, the replies and the box to answer in; the referrals screen and the project's activity feed both use it, because the answer to a referral is usually read in the feed and that was the one place it could only be *read* — somebody who found the reply was not what they asked for had to go to the other screen to say so. Messages are sided **by account id** (`responderUserId` against `assignedByUserId`), never by display name: a renamed account put its whole side of the conversation back on the other one, the same trap the two ids on the referral itself exist for. The compose area sits below a rule, because everything above it happened and a draft in the same column reads as something already said. **The three server calls are `submitReferralReply` in `src/api/inbox.ts`, in one order** — reply, then a *silent* status change (the reply already told the other party the part that matters), then the forwarding, which sets its own status and so replaces the outcome rather than adding to it; a bare «اتمام کار» with nothing typed is a status change on its own, and an empty send is refused. `test:rules` stubs the three routes and holds the sequence. **The request itself is editable, by the person who raised it and nobody else** (`updateReferralAction`): the assignee rewriting their own instructions is how a referral gets marked done against a request nobody made, and the assignee is notified that it moved.

- **Module notes are their own table** (`/api/notes/:entityType/:entityId`), never a column. Folding a note into the record and saving the record discards it silently — which is exactly what happened on two screens.
- **`compressLZW` output format changed.** It now emits `[alphabet, codes]`. The old encoder seeded its dictionary with char codes 0–255, so every Persian character produced `undefined` → `null`, and every audit snapshot ever taken was unrecoverable. Old entries decode to empty rather than to garbage.
