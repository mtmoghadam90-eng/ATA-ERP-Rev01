# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Persian (RTL) ERP/CRM web app for "Abzar Tamin Arshia" — a single-company internal tool covering customers, projects (sales opportunities), proformas, products/inventory, suppliers, purchase orders, transactions, tasks, packaging/delivery, and after-sales service. UI text and enum values are in Persian throughout; comparisons and status logic frequently key off Persian string literals (e.g. `'برنده'` = won, `'باخته'` = lost).

## Commands

```bash
npm run dev          # tsx server.ts — Express + Vite middleware on http://localhost:3000 (frontend + API together)
npm run build        # vite build (client) + esbuild bundle of server.ts -> dist/server.cjs
npm run start        # node dist/server.cjs (production; NODE_ENV=production serves dist/ instead of Vite)
npm run lint         # tsc --noEmit — the only standing check; there is no test suite
npm run sync:report  # push a flattened copy of the data into the SQL Server reporting tables
npm run test:rules   # the derived-figure rules, with no database — run before every commit
npm run test:ui      # renders modals into jsdom; catches state reset by a re-render
npm run test:e2e     # drives the real HTTP API end to end (writes to the configured database)
```

Three scenario suites exist (`test:rules`, `test:ui`, `test:e2e`); there is no ESLint. `npm run lint` (type-check) is the sole standing gate — run it after changes. **`noUnusedLocals` is on**, so a dead import or an orphaned `useState` fails the build; that is what keeps the tree clean without a linter. Unused *parameters* are allowed on purpose. **It covers `scripts/` too, and `deploy.ps1` refuses to deploy when it fails**, so anything a script imports must be a declared dependency: `scripts/uiScenario.ts` imported `jsdom` while that package was only ever present locally as an extraneous leftover, and the deployment stopped on the server with TS2307. Note `clean` uses `rm -rf` (won't work in PowerShell; use the Bash tool or delete manually on Windows).

**A hook below an early return is a white page.** `useBrowserTab` was written next to the value it reads, which sits under `App`'s early return for the login screen — so it ran for a signed-in user and not for a signed-out one, and every sign-in crashed the whole application with React's "Rendered more hooks than during the previous render". Nothing here could see it: a hook is an ordinary call to the type-checker, no derived figure was wrong, every endpoint answered correctly, and there is no ESLint to run `react-hooks/rules-of-hooks`. `src/utils/hookOrder.ts` now reads the source for that shape and `test:rules` fails on it. **Call hooks above every `return` in a component**, and if a hook needs a value computed further down, compute that value at the top too.

**Verifying non-trivial logic.** Since there is no test suite, the working practice is to write a throwaway `__something.ts` script at the repo root, run it with `npx tsx`, and delete it once green — this has repeatedly caught real bugs (the SKU decoder round-trip, the delta-merge lost-update case, the `extractNameAndCode` regex). Never leave those files behind. Server endpoints are verified by launching a second instance on another port (`PORT=3100 npx tsx server.ts`) — but it reads `DATABASE_URL` from `.env` like any other, so **point that at a scratch database or clean up what the test created**.

## Architecture

**Single full-stack process.** `server.ts` runs Express and mounts Vite as middleware in dev, so one `npm run dev` serves both the React SPA and the JSON API. In production the same file serves the built `dist/`.

**Persistence is SQL Server, through Prisma.** `prisma/schema.prisma` holds 35 models; `src/server/db.ts` exposes a single `getDb()`. Every module is one service under `src/server/services/` (queries plus record-level visibility) and one route file under `src/server/routes/` (HTTP, validation, permission gate) — `customerService.ts` and `routes/customers.ts` are the reference implementation. Port is overridable with `PORT`; the connection with `DATABASE_URL`.

The flat JSON document store this replaced is **gone**: no `database.json`, no `ALLOWED_KEYS`, no `/api/data/:key`, no `/api/versions` polling, no `saveToStorage`. Comments across the codebase still explain what a piece of code used to do in those terms — that is deliberate history, not a live description. A few endpoints survive outside the module pattern, on `server.ts` itself:
- `POST /api/login`, `/api/change-password` — bcrypt auth with in-memory per-IP/per-user rate limiting
- `POST /api/upload` — multer + sharp image resize/compress to `uploads/`, with path-traversal guarding
- `GET /api/rates` — today's scraped rates, returned without being stored
- `GET /api/report/preview` · `GET /api/report/sql-test` · `POST /api/report/sql-sync` — Power BI reporting sync
- `GET /api/db-health` — connectivity plus the schema check (authenticated)

**Each screen owns its own data.** There is no global store worth the name: `src/useERPStore.ts` is down to the session, the settings and a couple of helpers. A view calls the list hook for its module (`useProjectList`, `useProformaList`, …), which pages against the server; a detail record is fetched when it is opened. Writes go through the module's `src/api/*.ts` client, and every non-GET emits a change event (`src/api/liveData.ts`) so anything showing a count or a list re-reads itself.

**Concurrency is resolved in the database, not in the browser.** Clients no longer hold collections, so there is nothing to reconcile: a write is a row update inside a transaction, and the "another user changed this while you were editing" machinery went with the document store.

**Passwords never round-trip in the clear.** The server hashes on save and strips the hash from login responses. Use `isBcryptHash()` to detect an existing hash — **not** `startsWith('$2b$')`: bcryptjs emits `$2a$`, and that mismatch used to re-hash stored hashes on every users save, permanently breaking that user's login. Seed users default to password `123`, which triggers `mustChangePassword`.

### Cross-cutting systems

- **Derived status logic** — Proforma and project statuses are computed, not stored raw. **Filtering the grid by status means filtering by the *outcome*, which is not a column**: the filter sent its value at `proformas.status`, where only «پیش‌نویس» and «ارسال شده» ever live, so «تأیید شده (برنده)», «باخته» and «لغو شده» matched nothing and the grid came back empty (and «نیمه برنده» could not be asked for at all). `outcomeWhere` in `proformaStatus.ts` turns each outcome into the query that finds it — spelled out without `not` on a nullable column and without `every`, so NULL needs no remembering — and `matchesWhere` is a small evaluator for that subset so `test:rules` can hold the clauses against `getProformaOutcome` over **every** combination of lines rather than against a second reading of the rule. The screen no longer re-filters the page it was handed. `src/server/proformaStatus.ts` is the authority (`getProformaOutcome`, `deriveProjectStatus`), and writing a proforma re-derives its project in the same transaction. `getProformaOutcomeStatus` in `useERPStore.ts` is a client copy of the same rule, kept only so a grid can colour a row without asking; change both or neither. `test:rules` runs both over every combination of document status, cancellation and line statuses and fails if they disagree, so the instruction is no longer the only thing holding them together.
- **Sales follow-up is a second axis on a proforma, and never a second spelling of the outcome.** A quotation sent three weeks ago with nobody on it and one the customer asked us to raise again after Nowruz have the *same* derived outcome — «جاری» — and are completely different situations for the sales desk. So `Proforma.followUpState` spells only the three things the outcome cannot: `OPEN`, `DEFERRED`, `NO_RESPONSE`. There is deliberately no `WON`/`LOST`/`CANCELLED`/`SUPERSEDED` here; those are derived one column away (`getProformaOutcome`) and a second copy is how two columns come to disagree. The pure rules are `src/utils/salesFollowUp.ts` and `test:rules` covers them. **The next action is not on the proforma either** — the open `SALES_FOLLOW_UP` task related to it *is* the next action, its date, its assignee and its priority, so there is one record to edit rather than four columns to keep in step; `test:rules` fails a `nextAction` column appearing on the model. **The owner is `Project.salesExpert`, never `Proforma.creator`**: a support engineer routinely prepares the document for a job somebody else is selling, and `SALES_EXPERT` in a workflow rule resolves through the proforma's project (which is why `enrichPayload` resolves the proforma **first** — it is what supplies the project id the other blocks then read). **Task creation stays in the workflow engine**: `create_task` gained `taskKind`, `skipIfOpenSameKind` (the duplicate check, an option on the action rather than a law in the engine — "one task for ever" is not true of every automation) and a proforma relation when the payload names one, and the new `proforma_status_change` trigger reports the *stored* status moving, which `proforma_outcome_change` cannot — sending a quotation changes the first and not the second. It fires only on a real change, and on a document created already sent. The standard rule is **seeded** in `seedData.ts` rather than written into code, so when it fires, who it lands on and how long they have are all editable in Settings; an existing database keeps its own `settings.workflows` and needs the rule added there by hand. **Completing a follow-up is one transaction** (`completeFollowUp` in `followUpService.ts`) — closing the task, recording the result, moving the follow-up state and raising the replacement must succeed together, or a quotation ends up marked as actively followed up with the task completed and nothing chasing it; the close is a conditional `updateMany` so a double-clicked button raises one next action. The generic task update **refuses** to tick a `SALES_FOLLOW_UP` task for the same reason, while the automatic closing writes with `updateMany` and is unaffected. A terminal outcome closes that proforma's follow-ups (both the ordinary save and the outcome modal do it, inside the transaction) and touches **no** `GENERAL` task — an ordinary task attached to the same document does not stop being necessary because the quotation was won. `settings.dropdownItems.followUpResults` is what the customer said and is **not** a loss reason: «خرید به تعویق افتاد» is a deferral, `settings.lossReasons` is untouched, and `test:rules` holds the two lists apart. **Three of those results do end a sale, and the screen asks before it writes one.** «تأیید نهایی خرید», «لغو خرید توسط مشتری» and «واگذاری به رقیب (باخت)» each *suggest* a commercial outcome through `impliedSettlement`, and everything else in the list — the deferral and the silence especially — suggests nothing, which `test:rules` pins in both directions. It is a **suggestion**: «تأیید نهایی خرید» on the phone can still mean two lines out of five, so a person confirms and can correct the outcome before saving, and a renamed list entry simply stops suggesting rather than guessing. Answering yes writes the outcome **inside the completion's own transaction** — every line set, `isCancelled` for a cancellation because that is a fact about the document rather than a line status, `syncProjectStatus` through the same function the outcome modal calls, and a customer-value recalculation because marking a quotation won is exactly what turns it into a sale. `SETTLE_OUTCOMES` deliberately omits «نیمه برنده»: a part-won document is decided line by line in the proforma's own outcome modal, and offering it as one button would mean guessing which lines the customer took. Settling an already-decided document is refused (it would re-stamp every line and re-date the sale the ranking counts from). **And it is what unlocks «بدون اقدام بعدی»**: that option reads `outcomeIsTerminal || settleOutcome`, because the old check saw only the outcome as it stood and greyed the option out at exactly the moment it was wanted — the call where the customer confirms the purchase is the call after which no next action is needed. **A settled quotation is not in the queue at all** — a won, lost or cancelled document needs no next action, and «نیمه برنده» is settled too (it is reached when some lines were won and the rest closed off, which the business reads as decided; the outcome rule does not separate that from a part-won document with lines still «جاری», and both are treated as settled), and «پیش‌نویس» has not been sent to anybody. That is a *derived* value, so filtering on `isCancelled` and the stored status lets every won and lost document straight through (a fully-won proforma still has `isCancelled: false` and a stored status of «ارسال شده»), which is how the screen came to ask for a next action on finished sales; `chaseableWhere` builds the clause from `outcomeWhere` and `test:rules` holds it against `getProformaOutcome` over every shape, including a stored status nobody designed for. **`proformas.status` is NOT NULL, so no clause may filter it against null** — Prisma rejects that on a non-nullable column with «Argument `status` is missing» and the whole screen renders its error text instead of a list; `openAt` carried such a branch and the sweep's own null case was hiding it. A *line's* status is nullable and its null branches are correct and necessary, which is why the check walks the tree and only inspects `status` keys outside an `items` clause. Excluding by outcome rather than by whether the automatic sweep has run is also what makes the screen right for documents written before the feature existed — theirs were never closed because they never had any. The queue (`listFollowUpQueue`) is **ranked, then paged**: the rank comes from the open follow-up task, so no database can sort by it — paging in SQL and sorting the page afterwards put an overdue quotation from six months ago on page three of a list whose entire purpose is to put it first, and reported the unfiltered total beside a health-filtered page, which reads exactly like a missing record. It is a bounded scan (`QUEUE_SCAN_LIMIT`) with a `truncated` flag the screen shows, two reads in total, and every figure on a row is derived, never stored.
- **A follow-up's two halves live on two rows, and the card had room for neither.** «شرح اقدام بعدی» is what the next chase is *for* — «قیمت رقیب را بگیر و ۵٪ تخفیف پیشنهاد کن» — and it had nowhere to go, because the only free-text box on the completion modal was the note about the call that had just ended; so the next task was created with `description: completionNote`, and the card telling somebody what to do described what somebody else had already done. `nextDescription` is its own field all the way through (`FollowUpCompletionInput` → the route → `completeFollowUp`), and **absent is not empty**: a caller that never sends it — n8n drives this endpoint, and DEFER has no box to type one into — keeps the carry-forward, while an empty box is a person saying there is nothing to add, which is why the route passes «not sent» through as `undefined` rather than flattening it to `null`. The other half was invisible for a plainer reason: `completionNote` and `followUpResult` were selected by `LIST_SELECT` and then dropped by `rowToTask`, so a completed chase read «انجام شده» and nothing about what the customer said; neither is in the task route's `WRITABLE`, since `completeFollowUp` is the only thing that may write them. **The card is a stack, not two columns.** It put the title on the left and every badge on the right, so a paragraph got whatever width the badges left it and rendered as a tall thin ribbon — the descriptions now run the full width of the card, with the badges in one wrapped row beneath, and `whitespace-pre-line` keeps the line breaks the writer typed. `test:rules` holds the field reaching the created task, the absent/empty distinction, and that nothing on the card is pinned into a side column again.

- **«وضعیت» is how the sale went; «مرحله» is where the work has got to, and they are two columns.** `Project.status` is the commercial outcome and every report reads it that way — `isWonStatus`, the dashboard's win rate and won-contract value, the workflow triggers, the grid filter, the Excel export. Putting «در حال ترخیص» into it would take a won project out of the won set the moment its goods shipped, and the company's conversion rate would collapse for a reason nobody could see. So `Project.stage` is a second, derived column answering «الان این پروژه در چه مرحله‌ای است؟» across the whole chain: quoting, chasing, ordering, the manufacturer, transit, customs, the warehouse, packing, delivery, service. `src/utils/projectStage.ts` is the rule and `PROJECT_STAGES` is the ordered list — **the order is the rule**, since `stageRank` is the index. The middle of the chain is the purchase order's own vocabulary through `STAGE_FOR_PO_STATUS`, which `satisfies` pins to `PURCHASE_ORDER_STATUSES`, so a status added to that module and not mapped here fails `npm run lint`. **The least-advanced open thing wins**: three orders with one cleared and two in transit is «حمل و ترانزیت», because that is what the job is waiting on — reading the furthest-along record instead would put «تحویل شده» on a project with two containers still at sea, and somebody would close it. Only when nothing is open does the furthest reached stand. A received order stops holding the project back and hands over to the packing list; **a status this build does not know still holds it** (as «در انتظار تأمین»), because skipping it would report the project as further along than it is. **Overriding it means two different things and the form asks which**: locked pins it whatever the records do — «توقف پروژه توسط کارفرما» is derivable from nothing — while unlocked is «show this now», and the first recalculation after it hands control back and **clears** the manual value, since leaving it would print a stage the records beside it no longer agree with. A `manualStageLocked` with no stage is not an override and must never blank the column, exactly as in `resolveRank`. `syncProjectStage` runs **inside** the writing transaction and is called from the end of `syncProjectStatus` (so it reads the outcome that write just stored, rather than the one from a moment ago) plus the purchase-order, packing-list, after-sales and project writes. It writes only on a real move, which is what makes `stageChangedAt` mean «since when», not «last saved». `stage` is **not** in the route's writable allowlist — only `manualStage` and its lock — because a client that could set it could tell the grid a project is somewhere its own records say it is not. **Reaching a stage is a workflow trigger** (`project_stage_change`), which `project_status_change` could not be: the status is the sales outcome and does not move when goods clear customs, and «وقتی رسید ترخیص گمرک، به تدارکات وظیفه بده» is the rule people actually want. It is **queued, not fired in the transaction** — a rule creates tasks, sends messages and reads rows the transaction has not released, and anything it throws would roll back a save that was otherwise fine. `projectStageEvents.ts` drains a few seconds later and **re-reads the project, dropping the event when the stored stage is not what was queued**: that is the half a delay alone would not give, because a transaction that rolls back after queueing would otherwise raise a task for a move that never happened. Coalesced per project keeping the first `from` and the last `to`, and a failure is logged and forgotten. `npm run fix:project-stages` fills in the rows already on disk (`--dry-run` reports without writing) and deliberately passes `recalculating: false`, since a repair is not an event and must not consume somebody's unlocked override; the backfill is a script and **not** DML in the migration, because SQL Server compiles a whole batch before running any of it and a statement reading a column that file adds dies with «Invalid column name» however it is guarded.

- **A project has one loss reason, and it belongs to its proformas.** There were two places to record why a job was lost — the lines of its quotations, and a box on the project form — and both meant the same thing, so «چرا پروژه‌ها را می‌بازیم» found two answers for one project or an answer in the place nobody had filled in. The quotations win, because that is where the loss is actually decided (line by line) and where the project's status already comes from: `deriveProjectLossReason` in `proformaStatus.ts` is the rule and `syncProjectStatus` writes the project's copy in the same transaction as its status, so the two cannot disagree. It reads the **deciding** proformas — the same `decidingProformas` selection — or a superseded revision would contribute a reason the winning quotation flatly contradicts. Where lines disagree the commonest wins, ties by document order, because a report needs one value and picking one deterministically is the point; the document's own `lossReason` is one vote, counted only when something on it was lost, so it answers a document written off without per-line reasons and never overrules them. **Three answers, and the last two are not the same thing**: a string, `undefined` («the proformas say nothing» — the project keeps what somebody typed before the first quotation went out, which is the only answer there is), and `null` («nothing is lost», so a reason left over from a status the project no longer has is cleared). Writing `undefined` into the column would blank exactly the case the box exists for. The form shows the derived value **read-only** once `proformaCount > 0` and sends `void 0` for it; `lossReasonRefusal` refuses a *changed* value on the server — compared against what is stored, so re-saving a lost project (the form sends the field on every such save) is not an edit — because a silently dropped field is the same fault as a toggle that does nothing. **A lost line must say why**: `lostLineWithoutReason` refuses the outcome endpoint, naming the row, since the project's reason now comes from there and n8n drives the same endpoint; the follow-up modal's own «دلیل باخت» is required for the same reason. `npm run fix:project-loss-reasons` walks the existing rows through the same pure function once (`--dry-run` reports without writing) — the rule fixes everything written from here on and nothing already on disk.
- **Some settings entries are named by a rule, and a default reaches only a fresh installation.** `settings` is one JSON row, seeded once and thereafter the user's; a default added to `seedData.ts` never reaches a live database. That is right for a company's dropdown lists and wrong for the three follow-up results `impliedSettlement` keys on — on every database seeded before them the option was **not in the dropdown at all**, so the settle-the-sale feature read as broken rather than unconfigured, which is exactly how it was reported. `src/utils/settingsPatches.ts` is a named, once-only addition: `applySettingsPatches` records each patch id in `settings.appliedPatches` and `ensureSettingsPatches` writes only when something changed, run at startup **and on every settings save** (the browser posts a whole document it may have read before the patch). Two rules keep it from overwriting people's choices: a patch only ever **appends**, never renames, reorders or removes; and it is recorded even when it changed nothing, so a fresh document is not re-decided every restart and an entry somebody deliberately deletes afterwards **stays** deleted. `test:rules` holds both directions plus that each of the three entries actually settles something — an entry that arrives and suggests nothing would be decoration.
- **A project has its own follow-up tab, and it is not the queue.** `projectFollowUpReport` / `GET /api/sales-follow-up/project/:projectId` answers «what has happened on *this* job», which is a different question from the queue's «what should the sales desk do next, across the company» — so it deliberately **includes the settled quotations** the queue excludes: a won document with three recorded chases behind it is exactly the history being asked for. Each quotation carries its own `settled` flag, and a settled one is offered no next action and no health badge, which is the rule the queue screen was corrected for. Two reads, never one per row: the project's quotations, then one query for every follow-up task belonging to them, with the history newest-first. Recording a result and raising the next action reuse `FollowUpCompletionModal` and `salesFollowUpApi.reactivate`, so one flow writes a follow-up wherever it is started. The route is registered **before** `/api/sales-follow-up/:proformaId/reactivate` or «project» is read as a proforma id.

- **A revision is an explicit relation; two quotations sharing a project are not versions of each other.** A project here legitimately carries several open proformas at once — the temperature instruments, the pressure instruments, the flow meters — so nothing may infer that an older one is superseded because a newer one exists. `Proforma.previousVersionId` is a self-relation a person creates through «نسخه جدید همین پیش‌فاکتور» on the Copy button, which now asks which kind of copy it is; «پیش‌فاکتور مستقل» is the old behaviour and records nothing. A second revision of the same document is **refused** (`assertVersionChain` / `versionRefusalReason`) because the chain would fork and neither branch would be the live one — the message names the revision to work from instead. After a revision saves, the screen asks what becomes of the previous version and offers exactly two answers: cancel it, or leave it. **«باخته» is deliberately not one of them** — issuing a revision is not losing a sale, and filing it as one would poison every report built on `settings.lossReasons`. Cancelling uses the ERP's own `isCancelled`, assigns no loss reason and closes the old document's open follow-ups; it is not offered at all when the previous version already has a settled outcome. Being the base of a revision blocks ordinary deletion (`countProformaReferences` counts `nextVersions`), with a message that says to cancel it instead.
- **The front page's sales figures are derived, and two of them were derived wrongly.** `src/server/dashboardMetrics.ts` is the pure half, covered by `test:rules`. **A won contract stops moving with the exchange rate once it is paid.** «مجموع قراردادهای برنده» converted every won document at *today's* rate, so a contract invoiced, collected and closed two years ago moved every time the dollar did. `wonValueRial` splits the value in two: the settled part is frozen at the rial that actually arrived (the receipt's own `exchangeRate` — the difference between it and the invoice's rate *is* the exchange gain, so the invoice's rate is only a fallback for a row written before that box existed), and the outstanding part still converts at today's. A fully paid contract therefore stops moving altogether, an unpaid one floats exactly as before, and a rial document comes out at its own amount whatever the receipts say. A foreign receipt with no rate at all settles **nothing** — guessing at today's rate would put the frozen figure back on the rate, which is the fault being fixed. Money paid above the invoice is not sale value, so the settled part is capped and the rial that went with the excess carved off in proportion; `effectiveRate` (`rial / wonAmount`) is what splits the same money across the document's lines so «درآمد به تفکیک دسته» still adds up to the total beside it. **Conversion is counted per opportunity, never per document.** A project here carries several live quotations and several revisions of each, so a job quoted ten times and won once read as one win in ten and every corrected typo pushed the company's conversion down. `opportunityGroups` makes one data point per project (a proforma with no project stands alone), and `opportunityOutcome` reads it through `decidingProformas` — the *same* selection `deriveProjectStatus` makes, extracted so the front page and the project card cannot disagree about who won. That also means a later quotation for extra scope does not un-win a project, which "just take the newest one" would. `conversionByCategory` uses the same set and is no longer a raw sum over every `proforma_items` row. `averageProformasPerProject` is «چقدر رفت و برگشت داریم». The cost of all this is that the service reads proforma rows rather than aggregating in SQL — unavoidable, since every one of these rules is derived from line statuses — so the projection is narrow and the reason is written where it happens.
- **Workflow rules engine** — `settings.workflows` (`WorkflowRule[]`) is a user-configurable automation system. Mutations fire `processWorkflowRules(triggerType, payload)` (e.g. `'customer_created'`, `'proforma_outcome_change'`, `'product_low_stock'`). When adding a mutation that should be automatable, emit the matching trigger. A rule can also be **time-based** (`triggerType: 'time_elapsed'`): it names a date the record already carries, a number of days, and which side of it — `direction: 'after' | 'before'`, so a reminder can fire *before* an expiry (`src/utils/workflowSchedule.ts`, shared by the editor and the engine so a subject cannot exist in one and not the other). `days` is never negative; the side is its own field, and `sweepRange` reaches into the future for a "before" rule or the record would never be looked at. There is no cron here, so `ensureWorkflowSweepRanToday` runs once per Shamsi day, started at login and never awaited (the rate refresh is the same shape on a two-hour clock); `POST /api/workflows/run-due` is the manual button. Each firing is inserted into `workflow_firings` **before** the actions run and the unique index `(ruleId, entityId)` is what enforces once-per-record — the sweep runs again tomorrow and the record is still past its due day. `executeRule` is the one implementation both kinds of trigger share.
- **A workflow rule can only ask about a value the engine actually emits, and for years most of them could not.** The rule editor's condition dropdowns were hand-typed beside the modules and drifted from them, and the drift is invisible: a rule that never fires looks exactly like one waiting for its event. The purchase order offered «در انتظار تأیید / تأیید شده / ارسال شده», three words this application has never stored — its statuses are «پرداخت و سفارش به سازنده», «حمل و ترانزیت», «ترخیص گمرک» and the rest; the project offered four values none of which exists; the delivery offered seven where the engine emits **two**; the inquiry seven where it emits four; the task offered «در انتظار / تکمیل شده» and priorities «کم / زیاد / بحرانی»; the referral offered «در حال انجام», which it never holds. Two triggers offered a *field* the payload never carried (`proforma_created.status`, `customer_updated.newStatus`), and `task_completed` was fired by the engine and offered nowhere at all. `src/utils/workflowTriggers.ts` is the one catalogue now — label, group, condition fields and the values each field can hold — and the settings screen reads it in all three places it used to keep its own copy (the `<option>` list, the `fieldMap` for a new condition, the `triggerLabelMap` on the rule cards; that last one knew eight of the twenty-four, so every other rule printed its raw English id). **The values are the modules' own lists, never a second typing of them**: `src/utils/moduleStatuses.ts` holds each status list once and pins it to its type union at compile time in both directions, so a status added to the union and not to the list fails `npm run lint`. **A status that is derived rather than stored is derived in one place** — a packing list has no status column and an inquiry has none either, so `deliveryWorkflowStatus` and `inquiryWorkflowStatus` are the rules both the service and the editor read, which is what makes it impossible to offer more values than can be emitted. The remaining gaps were closed from the other end: the services now emit `status` on `proforma_created` and `purchase_order_created`, `city` on `supplier_created`, `minStockLevel` on `product_created` and `taskKind` on `task_created`, so every field the editor offers is a key the event carries. `test:rules` holds the catalogue against the trigger union in both directions, reads each service for the keys it emits, and names the invented values so a list that merely has the right length cannot pass with them still in it.
- **Settling a sale from the follow-up form asks the same question the outcome modal asks.** Marking a quotation won through «ثبت نتیجه پیگیری» is the *same event* as marking it won in the proforma's own outcome modal — every line is stamped, the project's status is re-derived, the customer-value ranking is rescheduled — and that modal has always gone on to ask whether the project's «پیش‌فاکتور» activity category is finished with. Reaching the same state through the other door asked nothing, so a job could be won and its category left open for ever with nobody to notice. `completeFollowUp` reports `settledOutcome` and the `projectId` alongside its result, and `settlementCategoryPrompt` (pure, in `salesFollowUp.ts`) turns those into the prompt; deriving it in the browser would mean a second reading of `impliedSettlement` *and* of whether the person answered yes, which is exactly how two screens come to disagree. It answers **null** in the two cases with nothing to ask — nothing was settled (the ordinary «فقط نتیجه ثبت شود»), and a quotation belonging to no project, which has no category to close. All three screens that complete a follow-up (the tasks board, the sales queue, the project's own tab) call it, and `test:rules` holds that.
- **Per-project milestone automation** — a *second*, separate engine: `src/server/services/milestoneAutomation.ts`. `ProjectMilestone` rows are checkpoints on one job; `project.milestoneRules` (JSON) attaches "raise a task" / "notify someone" to a milestone by `triggerMilestoneId`. `runMilestoneRules` fires for the milestones that went open→done in a write (the transition, never the state, or every save re-raises everything); `applyCategoryMilestoneTriggers` completes the ones bound to an activity category when that category opens or closes, matching through `sameCategory`. - **A blank worth a warning is not the same thing as a required field.** `settings.projectDataGapFields` is a separate list, and the project card draws a small amber badge naming what is missing (`src/utils/projectDataGaps.ts`, covered by `test:rules`). The field catalogue is `REQUIRED_FIELDS_METADATA.projects` — no second spelled-out list of a project's fields — and three rules keep the badge honest: a key the record does not carry at all is skipped rather than reported (a list row omits some columns, and a gap nobody can fill in is a badge nobody can clear), a numeric zero is an answer and not a blank, and an **empty** configured list means «warn about nothing» and must not fall back to the default or the feature cannot be turned off. `test:rules` also checks every default field actually arrives on a grid row, since `rowToProject` writes each key explicitly and one it never sets would warn about nothing, silently.

- **A product's category is a string on the row, and there were two ways to write one.** There is no category table: the category is copied onto the product, so «نرخ تبدیل به تفکیک دسته محصول» and every other report groups by exactly what is stored — and two spellings of one thing are two categories that split every figure in half. That happened. The product form is a `<select>` over `settings.dropdownItems.categories` and **cannot** invent a category; the Excel import took `row["دسته بندی"]` **verbatim** and could, so a sheet saying «Flow» created a category beside the «فلو» somebody had picked from the list and the dashboard drew two flow bars, one at 38% and one at 0%. Same shape as the five customer creation forms: a rule enforced on one path is not enforced. `src/utils/productCategories.ts` holds the pure rules. `categoryKey` folds away what is only spelling — case, spacing, the ی/ي and ک/ك pairs, the zero-width joiner — and **deliberately does not translate**: «Flow» and «فلو» are the same equipment in two languages, which no string rule can know, so a person decides and `mergeCategory` writes it. The import now **reports** the categories a sheet names that the list does not have rather than refusing the row — rejecting a hundred-row sheet over one cell is worse than importing it, but doing it silently is how the taxonomy split unnoticed. The merge is a real `updateMany` over the products table, **not** a display-time alias: the category is what the dashboard, the grid, the filter, the Excel export and the Power BI flattener all group by, and the first reader anybody forgot to alias would show the split again. It moves the products and removes the source from the dropdown list **in one transaction**, because leaving the source in the list after its products have gone lets somebody pick it again the same afternoon and recreate what was just merged; the target is stored in the list's own spelling, never the caller's, and merging into a value the list does not have is refused (it would move every product onto a name the form cannot offer). Editing the taxonomy needs `settings`, not `products` — every warehouse account holds the latter. `GET /api/products/categories` is registered **before** `/api/products/:id` or Express answers 404 for a product whose id is the literal string «categories». The merge writes `settings` inside its own transaction, so the screen takes the result through `applyServerSettings` rather than re-posting the document, which would race with what was just saved.

- **The prices already obtained are searchable by the item, not only by inquiry.** «سوابق قیمت» (`InquiryPriceHistoryTab`, `GET /api/supplier-inquiries/price-history`, `listPriceHistory`) answers the buyer's actual question — «آخرین قیمتی که برای فلومتر توربینی ۶ اینچ گرفتم چقدر بوده» — and needed no new column: `supplier_inquiry_items` has carried `productId`/`variantId` since the module was written, so the whole history was already on disk with no way to ask. It queries the **lines**, not a page of inquiries: picking the matching lines out of a page of offers pages the wrong set, and a supplier whose one matching line sits on inquiry 200 falls off page 1, so the answer changes with the page size. Three rules it carries. **A line with no price is not a price** — an inquiry sent and never answered has lines at zero, and listing those as «قیمت‌های دریافتی» is the same error as an uncosted proforma line reading as pure margin. **The discount belongs to the offer, not to the line**, so the stored `priceForeign`/`priceRial` is a pre-discount figure: `discountKeepFraction` in `src/utils/inquiryPriceHistory.ts` derives the payable proportion *from `computeInquiryTotals`* rather than re-implementing percent-then-amount, which is what stops the history and the offer card quoting one offer as two amounts — `test:rules` sums the lines against `inquiryTotalRiyal` over five discount shapes. **The range spans every match, not the page** (a «کمترین قیمت» that changes when you turn the page is worse than none), so it is a bounded scan with a `truncated` flag, and it is computed **only once the query is narrowed**: the cheapest unit price across every part ever quoted mixes flow meters with bolts and the figure it produces is a bolt. Two things easy to get wrong: the route must be registered **before** `/api/supplier-inquiries/:id` or Express answers 404 for an inquiry whose id is the literal string «price-history» (pinned by `test:rules`), and a user without `costs` is **refused** here rather than served the redacted copy the rest of the module gives them — this screen is nothing but prices, and a blank table cannot be told from «no history». `test:ui` asserts the tab fetches nothing until it is opened.
- **A supplier's offer is a list of files, in two places at once.** A quotation arrives as a covering letter, a datasheet and a price list, and `technicalOfferUrl`/`financialOfferUrl` could hold one of each — so the rest went in as a second inquiry or nowhere. `technicalOfferFiles`/`financialOfferFiles` are JSON (`[{name,size,url}]`) and the original single-URL columns still carry the **first** entry, so the grid's link, the download button and the Power BI export are unaffected; `parseOfferFiles`/`offerFileColumns` in `src/utils/attachments.ts` are the only readers and writers, and never read both (the first file would appear twice). The service derives the URL column from the list on every write, so the two cannot be stored out of step, and a caller sending only a URL — every integration written before this — is still understood. The card's project label reads the row's **own** joined `project.code`/`project.name`; it used to resolve the id against the project picker's current matches, so a job outside that page read «نامشخص», and the code is there because several projects here are genuinely called the same thing.

It lived inside `ProformasView` until the supplier-inquiry form needed the same thing. Two rules it carries: a feature with **two** values ticked is a legitimate question for a supplier («316 or 304») but identifies no single SKU, so it produces specification text and no SKU rather than a wrong one; and the id of a created SKU is read back from what was saved, never made up — a line's `variantId` is a real foreign key. The inquiry form fetches the **full** product on opening, because a picker row's `configRules` are empty and a configurator that cannot see the rules offers combinations the catalogue forbids. `test:ui` renders it and asserts a rule fires as boxes are ticked. **A feature or an option can be defined from inside it** (`onCatalogueEdit`, gated on the `products` permission at both call sites and by the route itself): the catalogue is never complete at the moment somebody is quoting from it, and the alternative was to abandon the proforma, add the option on the products screen and start again. The modal builds the mutation and the *host* performs the write through its own `updateProductById`, because sending a picker row back erases `configRules` and the price calculator. `catalogueNameRefusal`/`catalogueCodeRefusal` are the pure rules: a name is what `mergeSpecText`, the SKU attributes and `decodeSku` all match on, so a duplicate (compared with the formatting and spacing removed) is refused, and a code is restricted to a SKU token because `decodeSku` splits on `-`.

- **A proforma line's specification belongs to the product it names, and the outgoing product is an argument.** `describeProductSpec` in `productConfig.ts` subtracts *both* products' stored descriptions and feature names before keeping what the user typed. It used to subtract only the incoming product's, so switching from A to B kept every line of A's description — and since a new line is seeded from whichever product the picker happens to hold first, the default product's specification was printed above the chosen one on almost every line. Lines are matched with `stripRichMarks` applied, for the same reason `mergeSpecText` does it. **A line can also be copied** (`handleDuplicateItemLine`), and the copy carries **no** `id`: that field is the row the client read the line under and `preserveLineCosts` matches on it, so two lines sharing one would both claim a single stored row.

- - **A task assigned by name has to reach an account, and «exactly equal» is not that question.** Every automation is handed a *name* — `project.salesExpert`, a workflow rule's assignee box, a milestone's — and has to find the account behind it, because a task belongs to a person by **id**: `assignedToUserId` is what «به من ارجاع شده» filters on and half of what `visibilityClause` shows at all. Four writers each did it with the same exact string comparison, and SQL Server's collation treats ی/ي, ک/ك, the half-space and the two digit sets as different characters — the whole reason `searchClause` exists — while a name typed into a project and one typed into an account are two different typings. A miss left the task with the name on it and **no id**: assigned on the card, belonging to nobody, missing from its own assignee's board and from every board but «همه وظایف». `nameKey`/`matchAssignee` (`src/utils/assigneeName.ts`) fold what is only spelling and `resolveAssignee` is the single query, over the whole directory because the comparison cannot be asked of the database. **The fallback is the important half**: a task nobody matched still lands on somebody's board — the previous follow-up's assignee, or the person who pressed «فعال‌سازی مجدد» — because an automation-raised task has no creator either, so a null there is a record nobody can see. `npm run fix:task-assignees` walks the rows already on disk through the same rule (`--dry-run` reports without writing) and only ever fills in a **missing** id, never moves a task that has one.
- **A project code is a link, everywhere it is printed.** It appeared on almost every screen and was ink: reading one meant remembering it, opening «پروژه‌ها» and typing it into the search box, and going the other way — from a job to the documents raised on it — meant the same in reverse. One rule now, in `src/utils/projectLinks.ts` and `ProjectCodeLink`: a code opens a module already filtered to that project. **The code travels, not the id** — every one of those screens searches by text, no two projects share a code, and several are genuinely called the same thing. The hand-off is held in `App.tsx` because it is *between* views, and `useProjectJump` **clears it the moment it is applied**: left in place, coming back to the module hours later through the sidebar would silently re-apply a filter nobody asked for, and a screen that filters itself for reasons the reader cannot see is worse than one that does not filter at all. Clearing is also what makes a second jump to the same code work. The link **stops the event**, because codes sit inside rows that open their own record and following the project is a different intent; with no handler it renders as the plain text it always was, which keeps it safe in a printed document and on a screen nobody has wired up yet. In the other direction, each activity category carries a link to the module where that kind of work is recorded: `moduleForCategory` matches on the **words** rather than an id, because the categories are `settings.activityCategories` — a company's own editable list with nothing fixed to key on — and the table's order *is* its specificity («استعلام خرید» is an inquiry, and putting purchase orders first would send it to the wrong module). A category nothing matches gets no link at all, which is the right way for this to degrade: a wrong link is worse than none.
- **A screen's own settings are remembered per person, in the browser.** Which column somebody filtered to, how they ordered it, whether the finished work is hidden — none of it is data and all of it was thrown away on every refresh, so the first thing anybody did each morning was set the same three controls again. `src/utils/viewPreferences.ts` is the whole of it: `localStorage`, keyed by **screen and account id**, because a shared machine is normal here and one person's filters appearing under another's sign-in reads as the screen having lost their work. It is not a column on the account precisely because it is a convenience of *this* browser — not worth a write to a database shared with Report Server, and losing it costs three clicks. Three rules: what is read is **merged over the defaults** and only for keys the defaults name, so a document from an older build cannot hand a control `undefined` or a value it has no way to render; every read and write is **guarded**, because `localStorage` throws outright in a private window and in a browser set to block site data, and a screen that will not draw because it could not remember a dropdown is worse than one that forgets; and it is written **on change, not on unmount** — the tab is closed, the browser killed, the machine sleeps. The remembered order is also pushed to the query once on the way in (`appliedRememberedOrder`): nobody presses the control after a refresh, so without that the board would ask for the default page and sort *those* rows, which is a slice of the middle.
**A screen that writes to the catalogue has to remember what it wrote.** The proforma form's SKU `<select>` draws its options from the product picker's rows, which were fetched before the configurator created the SKU — and a `<select>` whose value matches no option renders its placeholder, so the line read «انتخاب ترکیب مشخصات» with a perfectly good `variantId` on it. `productOverrides` keeps every product this screen has saved, replacing a row of the same id and otherwise appending, so a product written to stays reachable after the search term moves on.

- **Jalali/Shamsi dates** — the app runs on the Persian calendar. - **A working day is decided by the `holidays` table, and the days it replaced were a lunar month wrong.** Every promised delivery date, every follow-up's next action and every task due date is counted in working days, and what counted as one was three hardcoded sets in `dateUtils.ts`: the ten fixed solar days, plus hand-typed lunar dates for 1405 and 1406 and nothing after. Two faults, not one. **Beyond 1406 every lunar holiday silently disappeared**, so a date promised in 1407 was counted across Ashura as though it were an ordinary Tuesday. And **the two years that were there were a lunar month late** — the app had Ashura 1405 on 5 Mordad (25 July 2026) when it falls on 4 Tir (25 June 2026), and Arbaeen exactly one lunar month out beside it; `test:rules` pins that against the one date in the chain that is independently checkable, Ashura 1404 = 5 July 2025 = 10 Muharram 1447, and the arithmetic that a lunar year is 354–355 days while the removed date was 385 away. The pure rules are `src/utils/holidays.ts`. **`isHoliday` is a column and not the row's mere existence**, because the answer runs both ways: a company works some announced holidays and Iran occasionally turns a weekend into a working day, so a row saying `false` is the only way «this Friday we are open» can be said at all — and the explicit answer is what `isNonWorkingDay` consults *before* the weekend and the fixed solar list. **Editing by hand is the primary path, not a fallback**: Iran announces holidays for snow, pollution and elections at two days' notice and no yearly source has them, so an import never overwrites a `MANUAL` row (and an *edit* of an imported day restamps it `MANUAL`, or the correction would be undone by the next refresh), never deletes, and **refuses a year that looks nothing like a year** — an error page parses to zero holidays and writing that over a year people are quoting against is worse than not importing at all (`importRefusalReason`, `MIN_PLAUSIBLE_HOLIDAYS`). `time.ir` is deliberately not the source: it could not be reached from here to write a parser against, and a scraper written blind against markup nobody has seen reports success while producing nonsense; `settings.holidaySourceUrl` makes the address a setting so the company's own server can point at whatever it can reach. **The walk is bounded** (`countForwardDays`, `MAX_WORKING_DAY_SPAN`) — the old `while (count < workingDays)` had nothing stopping it, so one bad import would spin the browser's main thread for ever with no error. `isOfficialHoliday` is called synchronously while somebody types, so the calendar is *cached in the process*: `setHolidayCalendar` is pushed in once after sign-in (`src/api/holidays.ts`) and at startup on the server (`refreshHolidayCache`, since `projectSummary` proposes delivery dates too), and until it lands the fixed solar days are the fallback. `GET /api/holidays` needs only a session — every screen that counts a working day reads it, and a salesperson who could not would be quoting off a different calendar from everybody else — while every write needs `settings`.
- **A calendar paints the day the rule calls off, never the last column.** `ShamsiDatePicker` and `TaskCalendarModal` both coloured by grid position — `idx % 7 === 6`, which is Friday only because the grid starts on Saturday — so they could express exactly one thing: Nowruz, Ashura and every day imported or typed into the calendar were drawn as ordinary working days, and a Friday the company had marked as worked was still red. Both ask `holidayReason` now, so the colour and the delivery date the same rule produces cannot disagree. It returns the day's own title («عاشورای حسینی»), falling back to «تعطیل آخر هفته» for a weekend and «تعطیل رسمی» for a fixed solar day on a database nobody has imported a year into — the reason travels with the colour, because a red day nobody can explain invites the question it cannot answer. The titles reach `dateUtils` through the same `setHolidayCalendar` push as the map, so there is no second reading of the calendar. `test:rules` reads both components for it and **strips their comments first**: the note explaining the fix quotes the expression it replaced, so a check reading the raw file fails on the very comment saying it was fixed — the same trap the migration scan closes by dropping `--` lines. The weekday *header* keeps its `idx === 6`, which is right: that column is Friday whatever the calendar says.
- **A year nobody has imported draws exactly like a year with no religious holidays in it**, and the two mean completely different things — Fridays red, everything else plain, either way. That is how «تعطیلات قرمز نشد» came to be reported against a working feature. `holidayCalendarState()` (`src/api/holidays.ts`) reports `loaded` (false until the first successful read, so an empty database is `true`), the day count and which Shamsi years have anything stored, and `TaskCalendarModal` draws a notice naming the year and pointing at the settings tab rather than leaving somebody to conclude it is broken. The reason is written **on the day** as well as in its `title`, because that screen is read on a phone and a tooltip is unreachable there. **A late-arriving calendar has to repaint what is already drawn**: `isOfficialHoliday` reads a copy held in `dateUtils`, so a grid rendered before the fetch resolved has nothing telling it to draw again — `onHolidayCalendarChange` notifies on every apply, and `useHolidayCalendar` is the hook both calendars use (the picker calls it for the subscription alone, and `test:rules` reads both components for it).
- **The lunar holidays of a year move as a set, and no source removes the need for it.** Iran announces the start of each hijri month by **sighting the moon**; every calendar reachable from a server computes it instead — the source used here and `aladhan.com` behind it agree with each other and can both be a day away from what was announced, usually a day early. The solar days are fixed dates and are simply right, which is exactly the reported shape: Nowruz correct, Ashura a day out. So the fix is not a better source (the Iranian endpoints — `time.ir`, `holidayapi.ir`, `pnldev.com`, `api.keybit.ir` — are all unreachable from outside Iran, and the one reachable computed source gives the same answer as the current one): it is one offset for the whole lunar set of a year, `POST /api/holidays/shift`. `Holiday.calendarKind` comes from the source's own `holidayType` tag, which is what makes it possible to move Ashura without moving Nowruz. Three rules, in `planHijriShift`. **It is a re-derivation, not a nudge** — the target is computed from `sourceDateJalali`, what the source actually said, so pressing «forward» twice is idempotent rather than +2 and going back to zero restores the imported dates exactly; a row imported before that column existed has none, and its current date is the base, which is right because nothing had moved it. **A hand-entered day never moves** and is stamped `SOLAR` on save: somebody typed it *because* the computed calendar was wrong, and dragging it by the very correction they were working around would undo their answer. **A move onto an occupied day is refused and reported**, not merged — one row holds a date, and the day already there is either a person's answer or a solar holiday, both outranking a computed lunar guess. The offset is **stored per year** (`settings.hijriHolidayShift`, keyed by Shamsi year because a sighting is a fact about one year) and re-applied on import, or re-importing would silently cancel the correction. The re-placement is a delete-then-insert in **one transaction**: shifting a set of dates by a day means every target but the last is occupied by the day in front of it, so an in-place update fails on the first collision. The migration backfills `calendarKind` from the fixed solar ten — verified to agree with the source's own tag on all 25 days of 1405 — so a database that already imported a year can use the correction without re-importing, and `test:rules` pins the migration's copy of that list against `FIXED_SOLAR_HOLIDAYS`.
- **Live exchange rates** — `GET /api/rates` scrapes tgju.org HTML for USD/EUR/AED/CNY (alanchand.com behind it) with hardcoded fallbacks; used to price items in multiple currencies. `src/server/services/rateRefresh.ts` brings the *stored* rates up to date **every hour** (`FRESH_FOR_MS`): started (not awaited) at login, awaited with a short budget by `GET /api/exchange-rates`, and driven by a ten-minute `setInterval` in `server.ts` so an afternoon with nobody signing in still gets a fresh rate — the tick must stay well inside the window (`test:rules` reads it out of `server.ts`), because a half-hourly tick against an hourly window leaves ninety minutes between refreshes. **The failure mode is silence**: the scrape reads two web pages, and when a markup change or a blocked outbound request stops it, nothing on any screen said so — the rates simply stopped moving and the only symptom was somebody pressing the manual button every morning. `rateRefreshReport()` travels with `GET /api/exchange-rates` and the rates screen draws it, reason and unread currencies included. Freshness is the age of `lastUpdated`, asked of the database as well as of this process, so a restart does not re-scrape what was fetched minutes ago. Server-side because refreshing needs the `settings` permission and the first person in each morning usually lacks it; one in-process promise so a busy 08:00 does not scrape four ways at once. `refreshDecision` is the pure scheduling rule and is covered by `test:rules`.

### Frontend conventions

- One view component per module under `src/components/` (`CustomersView.tsx`, `ProformasView.tsx`, etc.), switched by `activeView` string state in `App.tsx` — there is no router. **`src/appModules.ts` is the single list of those modules** (id, name, description) and everything that has to agree about them reads it: the sidebar, the settings screen's ordering tab, the default order in `seedData.ts`, and the «no access to module X» message. There were four copies and the messaging module was added to one, so it appeared in the menu and could not be reordered — the ordering tab looks each stored id up in its own list and renders nothing for one it does not know. The catalogue is deliberately free of React so `scripts/seedDb.ts` can import it through `seedData.ts`; icons live in `src/components/moduleIcons.ts` as a `Record<AppModuleId, …>`, so a module added without one **fails `npm run lint`** and `deploy.ps1` will not deploy past it. `test:rules` covers the rest: every catalogue id has a `case` in `App.tsx`'s switch and every case is in the catalogue, the seed order matches, and neither screen has grown a fresh copy of the list. A `?printModule=&printId=` URL opens a document directly for printing.
- Tailwind v4 (via `@tailwindcss/vite`), dark mode through a `dark` class on `<html>` persisted to `localStorage`.
- **The palette is corrected in one layer, not in 1427 class attributes.** Measured against WCAG 2.1, most of it did not pass: `text-slate-400` was **2.56:1** on white across 676 elements, `border-slate-100` **1.10** across 479, `border-slate-200` **1.23** across 948, and the reported fault — the compose bar against the messages above it — was **1.03:1**, the same colour. `src/index.css` ends with a *contrast layer* that restates those utilities, scoped `html:not(.dark)` throughout because a value chosen to be darker on white is the wrong direction on a dark ground (and the dark block above already restates most of them). Three rules decided its shape. **The `--color-slate-*` scale itself is never redefined**: the same token is a text colour, a border *and* a fill, so darkening `slate-100` to fix 479 borders would darken 200 `bg-slate-100` surfaces, which the border problem does not imply. **Two large surfaces are not pulled to 3:1** — in a light interface that is only reachable by making one obviously grey, and the 3:1 threshold is about a component's *boundary*, not its fill; so the separation is carried by `--color-edge` (**3.63** on white, **3.17** on a sunken surface) while the fills stay as they were, which is what the compose bar's `border-t-edge` does. **A body-text value must clear 4.5 on every ground it lands on** — white *and* `slate-50` *and* `slate-100` — because one chosen against white alone fails the moment the same text sits inside a card; the ramp stays three legible steps (5.10 → 6.19 → 7.58) rather than collapsing into one weight, and `slate-300` deliberately stops at 2.90 because it is icon strokes and disabled states, not text. `--color-edge` and `--color-hairline` are `@theme` colours so `border-edge`/`border-hairline` are real utilities and dark mode restates the value in one place. `border-slate-150` is in the layer for a different reason: it was used **149 times and does not exist** — Tailwind's slate ramp goes 100 → 200, so no rule was generated and every one of those borders fell back to `currentColor`, drawing in whatever text colour it inherited. `test:rules` recomputes every ratio from the stylesheet with the WCAG formula (pinned against black-on-white = 21:1) and fails on any that drops below its floor, so the palette cannot drift back.
- **Both themes answer the same list of roles, and the sweep reads both.** Light mode was measured and corrected while dark mode had never been measured at all — and it carried the identical defect: `--border-primary` at **1.09–1.41** on every surface, an input outline at **1.13** against its own fill, and status colours the override block never addressed, so `text-sky-600` sat at **4.03** on a card and `text-indigo-600` at **2.62**. Reading one theme is not reading the palette. `:root` and `.dark` now define the same role names — `text-faint`/`muted`/`soft`/`secondary`/`primary`, `color-edge`/`border-firm`/`border-card`/`color-hairline`/`border-divider`, and `text-info`/`success`/`danger`/`warn`/`violet` — and both the light contrast layer and the `.dark` block map utility classes to those names instead of to literals, so a value corrected in one theme can no longer be left behind in the other. **Status colours go the other way in the dark**: the light layer darkens them and dark mode lightens them, which is why they are roles and not one value. `slate-400` and `slate-500` had also collapsed into a single dark value, so the ramp read as three steps on white and two in the dark; they are separate roles now. `test:rules` walks **every text role against every surface in both themes** and reports the worst pair by name — that sweep is what found `text-danger` at **4.29** on the hover fill, which the per-class checks (all measured against white) had passed. Two things the sweep guards against passing vacuously: it asserts both role sets parsed, and that the two themes answer the same roles. The resolver follows the `var(--role)` hop — a check reading only for a hex went silently null the moment the indirection was introduced, passing nothing while reporting nothing. Note the CSS got **~1.9 KB larger**, not smaller: dark mode gained the status rules it never had, and that outweighs the consolidation.
- **Dark mode is a list of class names, and anything not on it keeps its light value.** That is the shape of every dark-mode fault here, and the roles above do not fix it: they fix what a covered class *maps to*, not which classes are covered. **160 uses across 33 classes were uncovered**, the worst being `bg-slate-50/50` on 44 elements — the header band of every dashboard card, which rendered as a translucent near-white strip over a dark card with the correctly-mapped near-white heading printed on top of it. The opacity variants are **separate class names**: `.bg-slate-50` and `.bg-slate-50\/50` share no rule, so covering the base never covered them. An attribute selector (`[class*="bg-slate-50/"]`) would close the whole family in one line and was **rejected**: 178 uses are `hover:`/`focus:`/`disabled:` variants it would match too, making every hover state permanent. So the list is explicit, generated from what the components actually use, and `test:rules` fails when a component introduces a light surface the stylesheet does not answer — which is the only thing that keeps an explicit list honest. Its predicate is held four ways: the class that broke, its state-prefixed form, a surface that is already dark (`bg-slate-900/60`), and `bg-slate-500/20`, which a careless slash rule swallows. Deliberately excepted: `bg-white/5`·`/10`·`/15`·`/40` are translucent overlays on coloured hero panels — a ground already dark in both themes — and `after:bg-white` is a toggle switch's thumb, white in both themes in every interface that has one.
- Types are centralized in `src/types.ts`; seed data in `src/seedData.ts` (`DEFAULT_SETTINGS`, `SEED_EXCHANGE_RATES`) except `SEED_USERS`, which lives in `useERPStore.ts`. Both are imported by `scripts/seedDb.ts` for `npm run seed:db`, not by `server.ts`.
- Excel import/export via `exceljs`/`xlsx` in `src/excelUtils.ts`; financial math in `src/utils/finance.ts`.
- **Printed documents are HTML printed by the browser, never rasterised.** Each screen builds a whole standalone page, `inlineDocumentAssets` turns its `/uploads/…` paths into data URIs, and `printHtmlDocument` (`src/utils/printDocument.ts`) writes it into a hidden iframe and prints that. The resulting PDF carries embedded fonts and real selectable text — verified. Do **not** reach for html2canvas/jsPDF: those photograph the page, and Persian text photographed at screen resolution is the poor quality this replaced. Each document owns its `@page { size: A4; margin: … }` and `print-color-adjust: exact`; without them the browser prints its own URL-and-date header and drops every background colour.
- **A printed proforma runs to several pages, and the rules for that live in `src/utils/proformaDocument.ts`.** It was six hundred lines of template literal inside `ProformasView`, which is why nobody could look at it: judging a printed document means printing it, and that needed a browser, a session and a database. As a pure function of its inputs it can be rendered to a real PDF by a real browser in a throwaway script and the pages examined — which is how the reported fault was reproduced and the fix confirmed. **An eight-item proforma printed page one with a letterhead, a buyer panel and no goods at all**, and began the items on page two: the goods table sat in a box marked `break-inside: avoid`, so the browser was being told to keep the *entire* list on one sheet, and when it would not fit it moved the lot. Four rules now hold the layout, and `test:rules` reads the document the builder produces and fails on each of them. **Keeping a row whole is the `<tr>`'s job and keeping the table whole is nobody's** — the avoidance is scoped to `.table-container tr`, because the document frame's own rows are `<tr>`s too and an unbreakable one there would mean the whole body had to fit a single page. **Nothing of unbounded length may be unbreakable**: the terms are free text a user can make as long as they like, so `.notes-card` and `.financial-grid` lost their avoidance while the totals panel, six short rows, kept it. **The letterhead repeats because it is the frame table's `<thead>`** — `display: table-header-group` is the one mechanism a browser implements for this, and unlike a `position: fixed` banner it *reserves* the space on every page instead of painting over what is there. **The address bar is defined once and placed twice**: the copy in the `<tfoot>` reserves the strip on every sheet and its ink is hidden when printing, while a `position: fixed` copy draws it — a footer group alone leaves the bar floating mid-page on a short final sheet, and a fixed bar alone reserves nothing, which is what used to print the last row of goods underneath it. Two smaller things that cost a render each to find: a repeated footer group is given very slightly less room than it occupies and the overflow is painted over the *next* page's letterhead, so `.print-footer` keeps `padding: 8px 0 6px` of slack (a sweep of twenty page shapes needed six pixels; zero failed eleven of them); and `white-space: pre-line` keeps the newline between a tag and its interpolation, which printed a blank line above every specification. **The seal block is compact, and it never starts a page alone.** It was about 48pt tall with 20px of air above it and a heading repeating what the panel below already labelled; at 38pt, with the heading gone and the strip shorter, four of the shapes that used to end on a sheet carrying nothing but a stamp no longer do. Shrinking cannot win that argument on its own — whatever height the block is, some document ends a point short — so `.signatures` also carries `break-before: avoid`, which asks the browser to keep it with the totals; being a preference rather than a demand it cannot recreate the unbreakable-block fault above. Its sizes are in **one** place now: every dimension used to be an inline style written out twice, once for a template with a company stamp and once for one without, so the same block was two different heights depending on a setting nobody connected to it. **Verifying a change here means printing it**: `renderProformaDocument` is pure, so a throwaway script drives a headless Chromium over a sweep of documents — item counts crossed with the length of the terms — and asserts on the resulting PDFs (one letterhead per page, the address bar at the same y on every page, nothing painted above the top margin, goods on page one, and no last page carrying only the seal). Serve the Google font from a local cache while doing it: a render that silently falls back to Tahoma paginates differently and will send you chasing a break that does not exist — `src/fonts/Vazirmatn-Variable.woff2` is checked in, and substituting it for the `@import` before printing is a two-line replace; confirm it took by looking for «Vazirmatn» in the PDF's own font list, because the fallback is silent in both directions. **The web address is part of the letterhead, not a fourth contact detail.** It sat in the address bar at the foot of the page, inside a wrapping flex row it shared with the address, the telephone and the email, so it was pushed to whichever end the wrap left it; it is under the company name and the line of business now (`.company-site`). Those two secondary lines are one block and share one tone — the tagline was `#94a3b8`, 2.56:1, which on paper is close to absent — and the address is separated from it by size and tracking rather than a second typeface, since the document loads one and a face that falls back paginates differently from the one that was proofed. Latin inside an RTL block still needs its own `direction`/`unicode-bidi`, or a trailing dot is reordered and the address prints wrong on a document that goes to a customer. Adding a line to the repeated `<thead>` is a page-count question, so it was answered by printing: ten item counts from 1 to 25, before and after, identical pagination throughout.
- **A proforma line's specification carries formatting, and it is still plain text.** `src/utils/richText.ts` defines four markers — `**درشت**`, `__زیرخط__`, `_مورب_`, `==هایلایت==` — and `RichTextField` is a textarea with a toolbar that wraps the selection plus a preview. Storing HTML instead was rejected for three reasons that all still hold: the product configurator reads that field line by line and tags in the middle of «جنس بدنه: …» would stop it recognising its own output (`mergeSpecText`/`selectionsFromSpecText` strip marks before matching, so bolding a feature line does not make the configurator append a duplicate); the field is interpolated straight into the printed document, and `renderRichText` **escapes first and applies the marks after**, which closes the hole a stray «<» in a tolerance already opened; and every plain-text reader keeps working, with `stripRichMarks` for the ones that want the words alone. Underline is matched before italic or `__` reads as two empty italics, and a run never spans a newline so an unclosed marker formats nothing rather than swallowing the rest of the page. `test:rules` covers the arithmetic, `test:ui` covers the toolbar reading the textarea's own selection. The proforma's own **«شرایط و توضیحات» block is the same field type**, and it is not only printed: `updateNotesWithDelivery` (now in `src/utils/deliveryNotes.ts`, extracted so it can be tested) writes and rewrites the delivery section *inside* it and finds that section by the words at the start of a line — so it compares against a `stripRichMarks`ed copy while splicing the original lines, or bolding «زمان تحویل:» hides the section and every later delivery change appends a second one below the first.
- **Money is formatted by `formatMoney` (`src/numUtils.ts`), in Latin digits.** Amounts get copied into bank portals and spreadsheets. `toLocaleString("fa-IR")` on an amount is a bug; on a count in prose («نمایش ۵ از ۱۲») it is correct.

## SQL Server

The move off the flat JSON document store is **finished**: all 18 modules have a Prisma-backed service and REST API, and every screen reads and writes through it. Nothing loads `database.json` any more, and the file, its endpoints and its seeding are gone.

### What the migration was for

The recurring pattern, and the one to expect in anything added next: a screen holds every record so it can compute something across all of them, and that computation silently breaks once the list is paged. Each of these moved to the server, where the whole set is still visible:

- **the winning supplier inquiries of a project** — found by walking every inquiry in memory (a project may have several: one supplier per part of the scope)
- **how much of a won item is still unshipped** — promised minus already shipped, across every proforma and delivery
- **document numbers** — `startSeq + collection.length`, which under paging is one page. The count moved to SQL but the arithmetic stayed, and it was wrong in a second way: every template is scoped (a project code, a year and month, a transaction type) while the count was the whole table, so a document on one project advanced the next number of every other, and a failed-then-retried save came back «…-C2» with «…-C1» never issued. `nextSequence`/`renderAround` in `src/server/documentNumbers.ts` count the numbers already issued under the same rendered prefix; `startSeq` is the floor. Covered by `test:rules`.
- **an after-sales record's status** — rolled up from its rows, and the column the grid filters on
- **dashboard revenue** — eight collections reduced to a dozen numbers

- **Schema** — `prisma/schema.prisma`, 35 models, deployed via `prisma/migrations/0_init`. Things Prisma can't express (the filtered unique index on `customers.economicCode`) live in `prisma/sql/extra-indexes.sql` and must be re-run after any migration that rebuilds those tables.
- **Client** — `src/server/db.ts` exposes a single `getDb()`. **Prisma 7 has no built-in SQL Server connector**: it connects through `@prisma/adapter-mssql`, and without the adapter the first query throws "requires a driver adapter". One client per process — the adapter owns the connection pool (`mssql` default max 10), and a client per request would exhaust SQL Server.
- **The customers grid's per-column header filters run on the server** (`CustomerColumnFilters`/`COLUMN_FIELDS` in `customerService.ts`, one allowlisted query parameter per column, each through `searchClause` so Persian variants match). They were collected into local state and never applied at all — the inputs did nothing. Filtering what the browser holds would have been worse than nothing: it filters one page and calls it the answer.
- **Lists are paginated, always** — `src/server/listing.ts` (`parseListQuery` → `paginationArgs`/`buildResult`). `MAX_PAGE_SIZE` is 200, so no caller can pull a whole table. Sort and filter field names are **allowlisted per endpoint**; an unchecked value would go straight into Prisma's `orderBy`. `searchClause` expands a term into its Persian variants (ی/ي, ک/ك, fa/ar digits) because SQL Server's collation treats them as different characters and a search would silently miss rows.
- **Module pattern** — one service under `src/server/services/` (queries + record-level visibility) plus one route file under `src/server/routes/` (HTTP, validation, permission gate). `src/server/services/customerService.ts` and `src/server/routes/customers.ts` are the reference implementation; follow their shape. Routes take `RouteDeps` (`src/server/routes/types.ts`) so they reuse `server.ts`'s single definition of `requireAuth`/`requireKeyAccess`; `sendError` maps Prisma error codes to Persian messages without leaking table names. **Settings, exchange rates and the audit log are the one exception** — all three share a single `src/server/routes/admin.ts` (backed by `adminService.ts`) rather than one file each. None of the route files mount through `express.Router()`/a path prefix either: every `register*Routes(app, deps)` call extends the same shared `app` directly with full `/api/...` paths, registered in sequence from `server.ts`.
- **Two screens borrow another module's permission flag** — `afterSalesServices` and `supplierInquiries` have no permission key of their own; access is gated server-side by `packagingDelivery` and `suppliers` respectively (`KEY_PERMISSION` in `src/server/auth.ts`). The client mirrors this via `SCREEN_PERMISSION_ALIAS` in `src/types.ts`, used by both `App.tsx`'s route guard and `Sidebar.tsx`'s menu filter — checking `permissions[screenId]` directly for either screen is wrong, since that key never exists on `User.permissions`.
- **A tasks board shows your own work, and `tasksAll` is the second permission that is not a screen.** `visibilityClause` in `taskService.ts` used to return «no restriction» for anybody holding the `tasks` permission — and `hasPermission` reads an **absent** key as granted, which is the right default for module flags that predate the stored accounts and catastrophic here: every account has the tasks module because everybody needs to see their own work, so every account saw every task in the company. The only way to get privacy was to be *denied* the module, which is backwards — denying it was meant to hide the screen. A task now belongs to **two** people, the one it was given to and the one who gave it: `{ OR: [{ assignedToUserId }, { createdByUserId }] }`. Scoping to the assignee alone would have been worse than the fault, because a task you raised for a colleague has no other column naming you and would vanish from your own board — which is why `tasks.createdByUserId`/`createdByName` were added (`20260904000000_task_creator`) and are stamped **from the session**, never from the body, and left out of the route's `WRITABLE`. `canSeeAllTasks` is read **strictly** (`permissions?.tasksAll === true`), like `canSeeCosts` and for the sharpest version of the same reason: a flag inheriting the module default would have reproduced the fault on the day it shipped. The screen's «به من ارجاع شده» / «من ارجاع دادم» tabs are `scopeClause`, applied *on top of* the visibility and never instead of it, so a client that omits or invents a scope widens nothing; «همه وظایف» is drawn only for somebody who actually holds the flag. The badge count, the reminder endpoint and the assistant's `list_tasks` all go through the same service and were all leaking the same way. **Referrals were already correct** — the inbox sends `scope=toMe|fromMe` and `listReferrals` forces the caller's own id into the clause, with no way to widen it from the screen.
- **«کارتابل ارجاعات» is a tab of «وظایف و پیگیری», and a referral is still its own record.** The two screens asked the same question — what has been given to me to do — so a person had to look in two places and remember which kind of thing they were after. `tasks` now has three views: **تخته کار** (the board), **فهرست وظایف** (what this screen always was) and **اعلان‌ها**, which renders `ReferralsView` with `notificationsOnly` — there is no «کارتابل» tab, because a referral **is** a task on the other two views, with the same filters, the same order and the same search, and a second list of the same records under another name would be two places to look again. Both of those views draw the referrals, not only the board: one that appeared on the board alone would be invisible to anybody who prefers the list. **One filter bar decides for both**, and the rule is written once in `referralPassesTaskFilters`: a record is filtered on the value it *effectively* has. A referral answers the status filter **through its column** (so «انجام شده» finds the closed ones and «کنسل شده» finds none, because a referral cannot be cancelled), counts as «متوسط» for priority — the same value `effectivePriority` orders it by, so it answers one choice rather than vanishing from every one or surviving all of them — is always about a project, and **drops out of any question about a due date**, which it does not have. The search box reaches them too: `listReferrals` matches the request, both colleagues, and the project and its customer through the relation. `referrals` is gone from `APP_MODULES`, from `moduleIcons` and from the users screen; a stored `permissions.referrals` and a `sidebarModuleOrder` still naming it are inert, because both readers already tolerate an id they do not know. **A referral is not copied into `tasks`.** It keeps its own row and its own conversation thread, and `src/utils/workBoard.ts` maps each kind's own status onto one of three columns — materialising it as a task row would be two status columns to keep in step, which is the fault this codebase keeps repairing. **The board never files open work as done**: an unrecognised status falls to an open column, because an open task hidden among the finished ones is the failure that matters. «کنسل شده» sits in the last column *marked*, not given a fourth column and not hidden. Moving is a toolbar press over ticked cards, not a drag — dragging needs a library to work at all and is unusable on the phone this is read on — and it is **one request** (`POST /api/tasks/board/move`, registered before `/api/tasks/:id`), tasks and referrals together, because a person drags a card and not a record type. A **sales follow-up is refused** by a move into «انجام شده», the same rule the ordinary edit enforces, and the refusal is *reported* rather than swallowed. **A column is ordered three ways** — arrival, due date, priority — and each breaks its ties by arrival, because a column of nine «متوسط» cards in arbitrary order is not sorted at all. **An undated card sorts last, never first**: Shamsi dates compare as strings, so an empty one would come before every real date and put everything undated at the top of a column somebody opened precisely to see what is due soonest. **The same order governs the list**, over one array holding both kinds of row — the tasks used to be drawn in whatever order the server returned with the referrals sorted after them, so the control moved half the screen and left the other half where it was. And **changing it re-asks the server** (`serverOrderFor` → `setSortOrder`), because the sort runs over the two hundred rows in hand: without that the top of a column is a slice of the middle, which is the fault the follow-up queue was corrected for. Priority is the one it cannot ask for — SQL orders those four words by collation, which is alphabetical and has nothing to do with urgency — so the due-date order stands in and `PRIORITY_ORDER` does the rest. **The two dates go opposite ways**: `startedAt` is stamped once and never cleared (the day work began is a fact; a card pushed back and picked up again did not start twice), while `completedAt` is cleared on reopening (a completion date on a card sitting in «در حال انجام» claims exactly what moving it back denied). `laneTimestamps` is the rule, and the same one governs a referral. **A new task is created as «برای انجام»** in the service, not by a column default: every row written before the board carries «در حال انجام», which is what it has always meant, and rewriting them would also change how a workflow rule keyed on that status fires. **The status filter names a column, and used to name a word.** Every automation raised its task as «در انتظار» — the workflow engine, the milestone rules, the sales follow-up and the assistant, five writers between them — a **fourth** value `TASK_STATUSES` does not name and no dropdown ever offered. `taskLane` put it in the open column correctly, but the filter was an exact match on the three literals the dropdown listed, so choosing «در حال انجام» asked for a string those tasks did not carry and **answered with nothing at all** on a board full of them. The dropdown offers the columns now (`LANE_FILTERS`) and `laneWhere` turns one into the query that finds it, with the **middle column written as an exclusion** — «not one of the other three» rather than a list of the values that mean in-progress — so it agrees with `taskLane`'s own fallback and a status nobody anticipated stays findable. Same rule as `countsTowardBalance` and `chaseableWhere`, and for the same reason. The five writers now name `TASK_TODO`; rows already carrying «در انتظار» are found by the exclusion without being rewritten, so nothing on disk changes. `referralPassesTaskFilters` takes the column too, which is the thing the two record types share — their own status words never matched. The card opens what it *is* — a referral its `ReferralThread`, a follow-up the same `FollowUpCompletionModal` the sales screen opens (over a row the server derives, `GET /api/sales-follow-up/tasks/:taskId`, never assembled in the browser), an ordinary task its edit box. **The list's tick opens it too**, because the bare tick is refused for a follow-up and the refusal used to name «پیگیری فروش» in the proformas module — a second screen and a second button for something already on this one; the message names the button now. The completion posts against **the task that was pressed**, never the row's own `nextActionTaskId`: the row belongs to the quotation and the completion is written against one task, and the two coincide only while the card pressed happens to be the open one. A follow-up already closed opens the ordinary edit box instead, since `completeFollowUp` would refuse a second completion anyway.
- **A colleague is texted the work another person hands them, and nothing else.** The board says what is on somebody's plate the next time they open it, which is no use for a request raised while they are at a customer site — and Web Push is unavailable here (the app is served over plain HTTP on a LAN, and Push needs HTTPS), so the notification is an SMS through the outbox the customer messages already use: the same `queueMessage`, the same quiet hours (a task assigned at midnight arrives at eight rather than waking somebody or being dropped), the same dry-run switch and the same retries. There is exactly one sending path and there must not be a second. **Two events, and the exclusions are the design.** A `SALES_FOLLOW_UP` is never texted — it is a call that person scheduled themselves, it sits in «در انتظار مشتری» until its day and arrives in «در حال انجام» on the morning it is due, and several a day per salesperson about their own diary is how the texts that matter stop being read; it is refused **before the account is read**, because `completeFollowUp` raises one several times a day and each would otherwise cost a user lookup for a message never sent. The **category notices are not texted either**: «بار از گمرک ترخیص شد» is worth knowing and is a request to nobody, which is the whole reason `activityRecipients` is a separate, quieter path. `src/utils/staffNotifications.ts` is the rule — `staffSmsRefusal` for what needs no account (off, follow-up, no assignee, your own work) and `staffRecipientRefusal` for what the account says (deactivated, no number, not a mobile) — and each answer is a **named reason**, because «no mobile on the account» is fixed on the users screen and «this is a follow-up» is not a fault at all. A reassignment is compared against what was **stored**, never against the field being present: the form posts the whole record, so «`assignedToUserId` was sent» would text the same person on every edit of a task already theirs. `User.mobile` is the address and is **absent from `DIRECTORY_SELECT`** — a colleague's phone number is not something every account may enumerate through the assignment pickers — and it is stored as typed, with `normalizeMobile` folding `+98`, the leading zero and the spaces where the message is *sent*. `settings.messaging.staffSms` carries the switch and the two texts; **absent reads as on**, because a live settings document never sees a default added to `seedData` and this was asked for, and `settingsPatches` writes the key in once so a later deliberate `false` sticks. The wording is editable on the messaging screen with the same `smsLength` counter beside it — Persian SMS is UCS-2, 70 characters then 67 per part, which is money — and `test:rules` holds the palette against the keys the sender fills in **in both directions**. One latent bug went with it: that screen rebuilt `settings.messaging` from the three fields its sending panel knows, so saving the retry limit dropped every other key in it.
- **How large a file this application accepts is one number, in one place.** It was five, and they did not agree: three forms refused a non-image over **2 MB** with their own hand-written check and their own sentence, the server refused an image over **10 MB** and anything else over **20 MB**, and multer stopped the request at 20 before any of them ran — so the answer to «چقدر می‌توانم پیوست کنم» depended on which form you were standing in, and the two forms that never grew a check had no limit at all until the upload was on the wire. `MAX_UPLOAD_BYTES` in `src/utils/uploadLimits.ts` is enforced in exactly two places: in `uploadFile`, which is the only path a browser has (so a form that never thought about it is covered), and on the server, which is the authority and what an integration meets. A check in a component is a courtesy that saves the round trip and names the file; it is never the rule.
- **A reply typed into a referral's thread lands in the project's feed too.** The other direction always worked — writing in the feed under a message that named you is mirrored into that request's thread by `addActivity` — but answering from «وظایف و پیگیری», which is where the request is actually read, wrote a `ReferralMessage` and nothing else: the feed showed the question with no answer under it and whoever raised it was left looking at their own message. `addReferralMessage` now writes a `ProjectActivity` **replying to the message that named this person** (`replyToId: referral.activityId`), in the same transaction as the thread message, and picks the request up on the same rule the feed uses — only the assignee replying moves it, and one already done is never reopened by a reply. The row is created directly rather than through `addActivity`, deliberately: that function mirrors a reply *into* the thread, so calling it would write the message twice. **A closed category reopens to accept the answer** — «اتمام کار» says the work under that heading is finished and an answer arriving afterwards says it is not — and the completion date is cleared with it, because a closed group holding a message posted after its end date is a group whose own dates contradict it; the writer is told, since it is a change to the project they did not ask for. `GROUP_OPEN`/`GROUP_CLOSED` are named in `workBoard.ts` for the reason `REFERRAL_DONE` is: `setReferralStatus` once compared a *referral's* status against «اتمام کار», which belongs to the category table, and the branch could never fire.
- **«آماده تحویل» is a delivery unit, not a fifth field.** Goods on the shelf are not a length of time, so `deliveryRange` and `deliveryType` have nothing to say and `deliveryPhrase` does not read them — reading all four blindly is what produces «۳-۴ آماده تحویل کاری». It lives in `deliveryUnit` because a fifth column would be a fifth thing to keep in step on every line of every quotation, to express what one value in one of the four already says; the form stands the two number boxes down when it is chosen rather than taking answers that are dropped. `deliveryPhrase` is also the one place the four defaults are read — they were read out three times in that file, and a fourth reading is how «۳-۴ هفته» comes to mean one thing in the printed document and another in the summary beside it. **Its sentence carries no trailing condition either**: «موجود در انبار و آماده تحویل پس از دریافت پیش پرداخت» contradicts itself, because goods that are ready are not waiting on a payment — so the printed section is exactly «زمان تحویل:\nموجود در انبار و آماده تحویل», and the payment condition goes in a section of its own. **`updateNotesWithPayment` writes «نحوه پرداخت: ۱۰۰٪ کل مبلغ در زمان تحویل کالا» only when *every* line is ready stock**, because a document with one item on the shelf and one on six weeks' order has no single payment rule and that sentence over half of it is worse than nothing. It is **managed, not merely written**: it is replaced when the goods change and removed when they are no longer ready — but removal is *exact*, so a staged payment somebody typed under that heading themselves survives, since a rule that manages a section may take back what it put there and nothing else. `updateNotesForItems` applies both sections in one call, which is what stops nine call sites each remembering to do two things.
- **A withdrawn opportunity is not a lost one.** `opportunityOutcome` returned «lost» for a job whose every deciding quotation was «باخته» *or* «لغو شده», so the front page's conversion card counted a customer who pulled out as a sale the company was beaten on — and «چرا می‌بازیم» has answers that «چرا لغو می‌شود» does not share. `"cancelled"` is its own outcome and its own figure beside «باخته»; «کل فرصت‌ها» and the win rate are untouched, and «در جریان» subtracts all three. Which of the two a mixed job counts as is `decidingProformas`, exactly as its own status is: with no winner among them the **latest** quotation stands for the rest.
- **The front page opens the tab it names.** «مشاهده فهرست پیگیری» opened «پیش‌فاکتورها» and landed on «اسناد» — the right module, the wrong half of it — and «مشاهده و ویرایش نرخ ارزها» opened Settings on «عمومی». `tabJump` in `App.tsx` is the hand-off, the same shape as the project jump and for the same reason (the choice is *between* views, so it cannot live in either), and it is **cleared the moment it is applied**: left in place, returning through the sidebar hours later would silently reopen a tab nobody asked for and a second press of the same button would do nothing. **The front page's two work cards became one**, because the modules behind them are one board now — and the tasks half was filtering on the literal «در حال انجام», which is one of the four words a task can carry, so it showed a slice of the board and called it the urgent work; it asks for «not finished» now, scopes «من / همه» on the server by account id rather than by comparing display names, and ranks both kinds of card against each other with `rankForTopUp`. The tick is offered only for an ordinary task: a chase is closed by recording what the customer said and a referral on its own thread, so for those the card opens the module where the right form is.
- **A chase's column is its date, and «در انتظار مشتری» is what that means.** A sales follow-up agreed for after Nowruz is neither «برای انجام» nor «در حال انجام»: it is sitting with the customer, and there is nothing to do about it until the day comes. `taskBoardLane` puts an open `SALES_FOLLOW_UP` task in **WAITING** while its due date is ahead and in **DOING** otherwise, and consults its status word for nothing but «is it finished» — which is the point, because the automations raise one as «در انتظار», `completeFollowUp` as «برای انجام» and an old row carries «در حال انجام», and none of those three was ever a statement about whether the customer had answered. Because nothing is *stored* saying a card is parked, it leaves the column the morning it is due with **no sweep, no nightly job and no second status column to keep in step** — the fault this codebase keeps repairing. The board and the column *filter* have to agree about it in two vocabularies (a Shamsi string, and a comparison on the DATE column), so `laneWhere` takes a date and `test:rules` holds the two against each other over every combination of status, kind and date, asserting also that every row lands in exactly one column. **`dueDate` is nullable, so the «not parked» half is spelled out** as «no date or a date that has come» rather than as `NOT (dueDate > today)`, which SQL evaluates to unknown for a NULL and would drop exactly the undated chases — the ones nobody planned, which the health check already ranks above what is merely upcoming. **WAITING is not a destination**: `MOVABLE_LANES` is the typed subset a move may write, the route refuses the fourth by name, and the column draws no button and explains itself instead — a card is parked by recording «موکول به تاریخ دیگر», which is where the date comes from. Pulling one *forward* is the mirror of that and moves the **date**, not a status: to today, which is also what it now means, so the queue, the health badge and the project's own tab all agree with the board. A chase pushed into «برای انجام» is refused for the same reason, and the refusals are a **set of sentences** rather than a count — three cards can be refused by three different rules, and one hardcoded message could only ever describe the first.
- **How much work one person may hold is two numbers on the account, and both default to nothing.** `User.minActiveTasks` / `maxActiveTasks`; the pure arithmetic is `src/utils/workLimits.ts` and the queries are `workLoadService.ts`. The **maximum** refuses a move into «در حال انجام» — eleven cards there is not eleven things being done, it is one being done and ten being forgotten — and the refusal carries the numbers, because a limit that stops somebody without saying what it is reads as the board being broken. The **minimum** is the opposite failure: an empty middle column beside a full «برای انجام» means somebody decides what to start every morning and starts whatever is at the top of the screen, so below it `topUpActiveWork` pulls the most pressing cards up itself (`rankForTopUp` — due date leads, priority breaks its ties, and **age breaks priority's, oldest first**, which is the opposite of how the same column is *displayed*). **Absent and 0 are both «no limit»**, in both directions: every account written before these columns has neither, and a maximum of zero would mean «may never work», which nobody means by typing 0 into an empty-looking box. A minimum above the maximum is refused where it is typed, against the pair **as it will stand** rather than the pair that was sent, or a form posting one of the two could store a contradiction the board would then promote into and refuse on the same press. **A referral counts toward the load exactly as a task does** — it is one board, and a cap enforced on one kind is walked straight past by anyone whose work arrives as the other — but only tasks are *promoted*: a referral has no due date so it would rank behind everything, and picking one up notifies the colleague who asked, which is a thing a person does. The top-up is a **POST** (`/api/tasks/board/top-up`) and never a side effect of reading the board; the screen calls it on mount and after anything is finished, and an account with neither limit costs one read and stops.
- **The task form asks which kind of work it is, and a chase does not go through `POST /api/tasks`.** A follow-up is not a task with a word written on it: it belongs to a quotation, it moves that quotation's `followUpState`, it must not be the second open chase on one document, it cannot exist on a settled sale, and it is closed by recording what the customer said. All of that is `reactivateFollowUp` — the same endpoint «فعال‌سازی مجدد» on the sales queue posts to — so the form posts there, and `taskKind` is deliberately **absent from the tasks route's `WRITABLE`**. A second creation path would be a second copy of every one of those rules, which is what the five customer creation forms stand for. The two shapes differ where they must: a chase asks for the quotation rather than «مرتبط با ماژول», its date is required and labelled «تاریخ اقدام بعدی» because that is what decides its column, and it offers neither a reminder (the due date already puts it in front of the right person on the right morning) nor the tasks module's custom fields, whose answers that endpoint has nowhere to store.
- **Searching the tasks board reaches the job, not only the task's own words.** `relatedToName` is one string the *browser* resolved out of a picker at save time, so a search for a project code found a task only if somebody had happened to type the code into that field — and the customer behind the job was not reachable at all. `relatedToType`/`relatedToId` is a **polymorphic** link with no relation for Prisma to filter through, so `relatedIdsForSearch` resolves the term into ids first (a project by code, name or customer; a quotation by its number or by the job it belongs to; a customer by name) and `buildTaskWhere` puts them **inside the same OR** as the task's own columns. A sibling AND would mean «matches the words *and* belongs to a matching job», which answers nothing for a task whose title does not repeat its project's name — almost all of them. Every match goes through `searchClause`, never a bare `contains`, or ی/ي and the two digit sets silently miss rows that are on the screen; the scan is bounded (`RELATED_SCAN_LIMIT`) because a one-letter term would otherwise name every project in the company. An empty search adds no clause at all — `relatedToId in []` matches nothing and would empty the board.
- **A referral is gated as a task, and used to be gated as a project.** The referral endpoints share a route file with the activity feed and inherited its key, `erp_project_category_groups` → the **projects** permission — so a user holding the referrals module and not the projects module got 403 on their own inbox. Nobody hit it because that module was rarely granted alone; merged into the board, where every account has `tasks`, it would have been every account. `erp_referrals` → `tasks` is the key now, and reading your own referrals needs no project permission: `listReferrals` forces the caller's id into the query and `setReferralStatus` refuses anybody who is neither party, while the wider «all referrals» view still checks `canSeeProjects` inside the service.
- **`setReferralStatus` compared against the wrong «done».** It read `newStatus === "اتمام کار"` to pick which notice to send — but that is a *category group's* closing status, from another table; a referral closes as «انجام شده». The true branch could never fire, so **every completed referral told the person who raised it that it had been reopened**. Nothing else read the value, which is why it went unnoticed. `REFERRAL_DONE` in `workBoard.ts` is the single name for it now and `test:rules` fails the literal reappearing. The middle status «در حال اقدام» is new — with two states the board's middle column could not be said at all — and the inbox badge counts «still open» as an **exclusion** (`open=true`) rather than the exact pending status, or picking a referral up would have made it vanish from the count of what is on your plate.
- **`Task.relatedToType` is stored in two languages, and the card's context only read one of them.** The task form writes the Persian words the type union declares — «پروژه», «پیش‌فاکتور», «مشتری» — while every automated writer stores a Latin key: `followUpService` raises each sales follow-up as `"proforma"`, and `workflowService`, `milestoneAutomation` and the assistant raise theirs as `"project"`. `withProjectContext`, which puts the job and the customer on each card, compared against the Persian spellings alone — so **every automation-raised task showed no project and no customer at all**, and that is most of what is on the board. `src/utils/taskRelations.ts` (`taskRelationKind`) reads both, in one place, because the stored values cannot be changed: `completeFollowUp` and several queries filter on `relatedToType: "proforma"` exactly, and rewriting the column would orphan every row on disk. A task on a **customer** is resolved too, in a third parallel query, with `code` and `name` left empty — the card prints those as the project, and a customer standing in for one would read as a project that does not exist, so the badge guards each part rather than printing «کد | نام |» around a blank. `test:rules` pins both spellings, pins that the writers still write the Latin ones, and fails a comparison against a spelling written out at the call site again.
- **«پنهان کردن انجام‌شده‌ها» is a clause on the query, not a filter over the page.** The board is paged at fifty, so dropping the done rows after they arrive would empty a page of twenty completed tasks and print the unfiltered total beside it — the same fault as the follow-up queue's ranking. `hideCompleted` travels as a query parameter, is read **strictly** (`=== true`) so a caller that omits it still gets the whole list, and **an explicit status choice wins**: somebody who has picked «انجام شده» from the dropdown is asking for exactly what the toggle hides, and honouring both would answer with nothing and explain nothing. The button is disabled while that dropdown names a status, because a toggle that silently did nothing reads as broken. It hides the **whole last column**, cancelled work included, because that column is what «انجام‌شده‌ها» means here and leaving the cancelled ones behind is a button that half works. The column filter it stands down for has to be **normalised** first: the screen sends the literal «all» when nothing is chosen, and reading any non-empty string as a choice made `Boolean("all")` true and stood the toggle down permanently — which is exactly how it was reported as broken. `test:rules` calls `buildTaskWhere` with the shapes the screen actually sends, so the precedence is held against the clause it produces rather than against a second reading of the rule.
- **A task belongs to two people, and the card drew one of them.** `createdByUserId` is the second arm of `visibilityClause` and the whole of what «من ارجاع دادم» filters on, so a row that appears under «همه وظایف» and in *neither* tab is simply one somebody else raised for somebody else — correct, and completely unexplained, because the card printed «مسئول» and nothing about who asked. It arrives on the list row already (`createdByName`) and is now printed beside the assignee. **An absent creator is not a gap in the record**: it is what every automation-raised task carries (the workflow engine, the milestone automation, the sales follow-up and the assistant raise tasks with nobody acting) and what every task written before `20260904000000_task_creator` carries, since that migration backfilled nothing and could not — so the badge names it rather than drawing a blank.

- **`costs` is the one permission that is not a screen.** Every other flag answers "may this user open this module"; `costs` answers "may they see these fields inside modules they already have" — warehouse staff need the inventory screen and the sale price, and must not learn the purchase price. `canSeeCosts` in `src/server/auth.ts` reads it **strictly** (`permissions?.costs === true`), *not* through `hasPermission`, which treats an absent key as granted; absent means denied here so no account written before the flag existed is quietly given access. `src/server/costs.ts` is the single list of what counts as a cost, now across **five** places: the product/SKU price calculator (`priceCalc`), purchase-order landed cost and line prices, supplier-inquiry offers (including the auto step notes, which quote the amount back in prose), **proforma line `unitCost`/`costCurrency`/`costSource`**, and **customer gross profit** (`grossProfitRial`, `grossMarginPercent`, `costCoveragePercent`, `grossProfitScore` — revenue and the rank stay). Redacting one and not the others just moves the leak. Redaction happens **in the route, on the way out**, never only in the component: hiding a column hides it from the person looking at the screen and from nobody else. Writes split two ways — purchase orders and inquiries are *refused* (`refuseCostWrite`), while products and proformas go through with the cost put back (`stripProductCostInput`, `preserveLineCosts`), because those are records such a user legitimately edits all day. `preserveLineCosts` matches by the line `id` the client read the row under, which is why `ProformaItemInput` carries an `id` that `mapItem` deliberately never stores. `assertLinesCosted` is skipped for these users too — demanding a cost from somebody with no way to enter one locks them out of the screen. The screens hide the same fields (`canSeeCosts` in `src/utils/permissions.ts`) purely as a courtesy, so nobody is shown boxes they cannot fill.
- **Append-only collections never go through `syncChildren`** — inquiry steps, project activities, referrals and their messages, module notes, and the stock ledger. Each has its own add-one endpoint. Removal is restricted: a derived (`isAuto`) inquiry step cannot be deleted at all, and an activity cannot be deleted once its referral has replies.
- **Money and stock are computed, never accepted.** Proforma and purchase-order line totals are recomputed from quantity × price; a PO's landed cost from its own stored exchange rate. Transactions convert foreign amounts at the document's rate. **A proforma's money is computed by one rule, `computeProformaTotals` (`src/utils/proformaTotals.ts`), which the form and the server both run.** There were two implementations: the form rounded the discount and the tax to whole units and the server did not, so a document approved on screen as «۹۶۸ دلار» was stored — and printed, and settled against — as 968.22. The rounding is the form's, because the form is what a person reads and agrees to before pressing save. What is deliberately **not** rounded is the line totals and therefore the subtotal: a line has to read quantity × unit price and the lines have to sum to the subtotal printed under them, so only the figures a percentage derives are rounded — and `finalAmount` is built from the rounded parts, so the printed document adds up. `getWonItemsCurrencyAmount` rounds its own share-of-the-document figures the same way for a نیمه‌برنده. The printed document reads the stored totals rather than recomputing, so there is no third copy; `test:rules` fails either side that grows its own discount arithmetic again. Existing records keep their old figures until re-saved.
- **The settlement rate is the rate on the day the money arrived, and it is never the invoice's own rate.** The difference between the two *is* the realized exchange gain, so filling the receipt's rate box with the proforma's `historicalExchangeRate` — which this form briefly did — makes every rial paid above the invoice's rial value read as an overpayment: a real 100,454,200 gain filed under «مبالغ تخصیص‌نیافته» while the gain column said zero. `calculateProformaFinance` was right; its input was not. The box is no longer prefilled; both rates are offered as one-click buttons with what each would realize spelled out, the implied one computed to **four decimal places** because that is what the column stores (rounded to the whole rial it strands a few hundred rial as a phantom overpayment). The field is also shown whenever the linked proforma is in another currency, not only beside a typed foreign amount — for a rial receipt against a dollar invoice, the ordinary case here, the figure that decides the whole exchange gain could not be entered at all. `ProformaFinanceReport.actualReceivedRiyal` means every rial received; `allocatedReceivedRiyal` is the part that went against the debt and is what the realized gain is measured on — the two were one field reporting the second under the first's name.
- **A foreign amount of zero is not a foreign amount.** `rialAmountOf` derives a document's rial figure and the test was `foreign != null` — zero is not null, so a plain rial receipt that happened to carry a settlement rate was rewritten to `0 × rate`. The form sends `0` for an empty foreign box by construction and fills the rate in from the proforma being paid, so **every rial receipt against a foreign-currency proforma was stored at zero**: the document existed, the ledger read «۰ ریال», and nothing said why. Guarded in the service rather than in the client that tripped it — the server is the authority on this figure and an integration posting the same shape hits the same thing — and `positiveOrNull` now stores both `amountForeign` and `exchangeRate` as NULL when they are not figures, so the column says which kind of document this is. **Sold, received and outstanding must be three figures about one thing:** the finance row reported `totalRemainingCurrentRiyal` (today's rate) beside a sales figure at the historical rate, so a project with nothing received showed more outstanding than it had ever sold — and people typed the larger figure into a receipt and were warned it exceeded the sale. It reports `totalRemainingHistoricalRiyal`; the today's-rate figure and the exchange gain or loss stay in `summary` under their own headings.
- **A ledger row names things from itself, never from a picker's matches.** The grid printed «پ.ف: ناشناس» and the incomplete-rates tab silently skipped documents, because both resolved the proforma by `proformas.find(...)` against the *picker's* current search results — so a document was named only while its proforma happened to be loaded, which in practice meant only the one just saved, and saving a second renamed the first. `LIST_SELECT` joins `proforma` (number **and** currency, the second being what decides whether a receipt needs a settlement rate) alongside customer, supplier and project. Same trap on the write side: the party name was resolved out of the customer/supplier picker and stored as «مشتری ناشناس» when the match list had moved on — a blank is stored instead, and `rowToTransaction` falls back to the joined name.
- **Searching the transactions ledger reaches the project and the counterparty, not only the document's own columns.** `transactionSearchClause` adds relation filters for the project's code and name, the customer, the supplier and the proforma. Every row shows those, and the «تراکنش‌ها» button on the project summary puts a project into the search box — so a flat search over `documentNumber`/`referenceNumber`/`partyName`/`notes` answered «no results» for a project that plainly had documents. `partyName` is often null in particular: the grid falls back to the joined names. The button sends the project **code**, because codes are unique and several projects here are genuinely called the same thing.
- **A transaction entered by mistake is edited or deleted** — there is no reversing entry, by explicit decision. There used to be one, the textbook answer, and the screen never grew a button to issue it: every document is written «تأیید شده», a confirmed one refused deletion, and the error told the user to do something the application gave them no way to do. Deleting removes the effect in full because the effect *is* the row — a transaction moves no stock and reconciles nothing, it only contributes its amount to totals computed from the rows that exist — and the audit entry keeps the whole document. `countsTowardBalance` is the balance rule and is written as an **exclusion** (`پیش‌نویس`, `لغو شده`): a status nobody anticipated must count as money rather than silently vanish. `ابطال شده` still counts, because a database written before this may hold a reversed original *and* its opposite entry, and those cancel only if both are counted. Three things around it were broken in the same way — by a rule that could not be acted on: the amount guard compared a stored `undefined` against the form's `0` so it refused **every** edit of a confirmed document while blaming a figure nobody had touched; the three summary cards summed the page in hand over every status while a correct server `/summary` existed unused; and the settlement rate was read off a proforma **list row**, which did not carry `historicalExchangeRate`, so the box was filled with nothing every time.
- **A received purchase order reconciles stock against the ledger**, not by revert-then-reapply: it reads what it has already credited (`referenceType`/`referenceId`), compares with what its lines and status now say, and writes only the difference. Idempotent and self-correcting; un-receiving targets zero.
- **Passwords are write-only.** Every user read goes through an explicit `select` that omits `passwordHash`, so a new column cannot leak by default. Callers without the `users` permission get a name-only directory projection rather than a refusal, because the assignment pickers need it. Changing permissions, deactivating an account, or setting a password bumps `sessionEpoch`, which invalidates cookies already issued.
- **`toNumber` translates Persian punctuation, not just digits** — `٫` (U+066B) is the decimal separator; leaving it in place turned `"۱۲٫۵"` into NaN and then into the fallback, silently storing 12.5 as 0.
- **All 18 modules converted**: customers, projects, proformas, products/inventory, suppliers, purchase orders, transactions, tasks, supplier inquiries, deliveries, after-sales, users, settings, exchange rates, audit log, project activities, referrals, module notes.
- **Dates are two columns** (`xDate` DATE + `xDateJalali` string) and `src/server/dates.ts` is the only place that maps between them. Use `expandDateFields` in a service, `jalaliRangeFilter` for a range. Two traps it exists to close: a JS `Date` built from local midnight serializes as 20:30 the *previous* day on this UTC+03:30 host (everything here is `Date.UTC`, read back with UTC getters), and both calendars are written `YYYY/MM/DD` — so `"2026-07-28"` parsed as Shamsi becomes 2647 CE. The year selects the calendar (1200–1600 ⇒ Jalali).
- **Line-item grids** use `syncChildren` (`src/server/childSync.ts`): delete and re-insert inside the parent's transaction, with `lineNo` recording the user's order. Absent means "not edited"; `[]` means "the user removed them all" — conflating those wipes a grid on any partial save. **Never use it for entities that are referenced or append-only** (product variants, activities, referrals, inquiry steps, the stock ledger); rebuilding those breaks foreign keys and destroys history. Variants are reconciled by identity in `productService.ts` instead.
- **Money and derived status are computed server-side, never taken from the request.** `src/server/proformaStatus.ts` holds the outcome rules (a proforma's outcome derives from its line statuses; a project's status derives from its proformas) and writing a proforma re-derives its project in the same transaction. Proforma totals are recomputed from the stored lines.
- **Stock moves only through `applyStockDelta`**, which writes the ledger entry and the new level together — so a movement can't exist without its history. An edited stock field is diffed into a movement; manual adjustments take a signed delta, not a new level, so concurrent adjustments add up. For a product with variants the parent level is the sum of its SKUs.
- **`stockLevel` means *free to sell*, not *physically present*.** Goods bought against a job were sold before they were bought, so they must never become quotable. Won proforma lines supplied from the warehouse deduct the level at the moment they are won (`reconcileProformaStock`). A packing list's issue always passes `affectsAvailable: false` — it writes the ledger and leaves the level alone. A foreign purchase order's receipt does the same **only when the order is tied to a project** (`reconcileStock` in `purchaseOrderService.ts` passes `affectsAvailable: !po.projectId`): those goods were sold before they were bought, so they were never anyone's to promise. An order with no project is a general/warehouse purchase — nothing has claimed the units, so receiving them raises the available level like any other stock. The ledger is the physical record; the level is the promise, and the two differ on purpose while job-specific goods sit on the shelf. All of these reconcile by difference against what they have already written (`referenceType`/`referenceId`), so editing or deleting the document corrects the ledger instead of doubling it.
- **The ledger is append-only for everyone except a system administrator**, who can correct or delete a single row (`updateInventoryTransaction`/`deleteInventoryTransaction`). The gate is `user.isSystemAdmin`, not the `products` permission — a warehouse account with full stock write access still cannot rewrite what the warehouse did. The level is corrected by the **difference** inside the same transaction, and only when the row's own stored `affectsAvailable` says it moved the level in the first place; that flag exists on the row precisely so a correction can put back exactly what it took. A row's product, SKU and source document are not writable — moving a row between products is a delete plus a fresh adjustment, where both halves are visible. Both operations write an audit entry with before/after.
- **Record-level access is applied inside the query**, never as a post-filter — otherwise the pagination totals leak the existence of records the user can't see. `visibilityClause` returns `undefined` for a user with the module permission and `{ ownerUserId: user.id }` otherwise, and writes re-check it before touching the row.
- **Bodies are picked, not spread** — routes copy only an allowlist of writable fields, so a client can't set `id`, `createdAt`, `ownerUserId`, or a derived column like `mobileNormalized`.
- **Seeding** — `npm run seed:db` (users, settings, exchange rates only; no demo business data). Idempotent: users upsert on `username` and never have their password overwritten, settings and rates are create-only so live values aren't reset.
- `npm run db:deploy` / `db:generate` wrap the Prisma CLI. `GET /api/db-health` reports connectivity (authenticated — the error text names the server and database).

## Power BI reporting

Reporting is a **separate, one-way export** and is unaffected by the migration above — it targets its own `ata_erp_reporting` database. `src/reporting/flatten.ts` turns the document store into 25 flat tables (each nested array becomes a child table carrying its parent's keys denormalized), and `src/reporting/sqlSync.ts` loads them into a SQL Server `rpt` schema inside one transaction (replace-all; volumes are small). **Custom fields get two of those tables**: `custom_fields` is the dictionary (id → module, label, type, options) and `custom_field_values` is every record's answers unpivoted to one row per (module, record, field) with the label denormalized on. They exist because `customValues` is keyed by field *id* while the label lives in `settings.customFields`, which never reached the reporting database — so the JSON arrived as a bag of `cf-…` keys nobody could read. The per-module `custom_values` JSON column stays for existing reports. A value whose field was later deleted is kept with `is_defined = false` rather than dropped. **All ten modules the settings screen offers now carry `customValues`** — `packagingDelivery` and `afterSalesServices` got theirs in `20260823000000_custom_values_two_modules`; before that a field could be defined for either and filled in nowhere, because no table had a column for the answer. `CustomFieldsForm`/`CustomFieldsDetailView` take `CustomField['module']` rather than their own spelled-out union, which is how they came to be two modules behind. `FlatDataset.columnTypes` declares types the loader must not guess: `value_number` is empty until a numeric field is filled in, and inference would create it as NVARCHAR and silently turn every later figure into text. Power BI reads that with its native connector. Dates stay Shamsi **strings** by explicit user decision — they convert them in Power BI. `flattenUsers` deliberately omits `password`; credentials must never reach the reporting DB. Setup and suggested relationships: `docs/powerbi-setup.md`.

## Gotchas

- `server.ts` is bundled by esbuild (`npm run build`), which resolves every import at bundle time — so its imports (routes, services, `src/server/*`) must stay statically analyzable, no dynamic paths. Seed constants (`SEED_USERS` etc.) are **not** among them: `scripts/seedDb.ts` imports those directly and runs unbundled via `tsx`, never through `server.ts`.
- Seeding is `npm run seed:db` and creates users, settings and exchange rates only — never demo business data. It is idempotent: users upsert on `username` and never have a password overwritten.
- The server binds `0.0.0.0` and has no session/token auth beyond the login endpoint; it assumes a trusted LAN. Do not expose its port to the internet.
- **A callback prop handed to a child that fetches must be stable.** `MessagingView` built its `report`/`flash` helpers inline, and the tabs below list `onError` among the dependencies of the `useCallback` that loads their data — correct in itself, but a new function on every parent render meant a new `load`, so the effect watching it fired again. `App` re-renders whenever the sidebar badge poll returns (a minute) and on every live-data change event (any write, anywhere), so the screen refetched over and over and jumped back to the top each time. `useCallback` with an empty dependency list is right for a helper that closes over nothing but state setters. `npm run test:ui` renders the screen under a parent that re-renders and asserts the fetch count does not grow — the same shape as the price-calculator test below, and the same family of bug.

- **`<input type="number">` cannot hold a decimal being typed.** The HTML value-sanitisation rules report a value that is not a *complete* floating-point number as the empty string, so the instant somebody types the point in «0.7» the handler is given `""`, `Number("")` is 0, and the controlled value re-renders over what was typed — the field is unreachable by keyboard and only the spinner arrows get there. It was reported on the assistant's «خلاقیت», and the same control was on the supplier-inquiry discount, where the same three keystrokes silently turn 2.5% into 25%. `NumberField` (`src/components/NumberField.tsx`) is the answer and every numeric box should use it: a text input with `inputMode`, the typed text held as a draft, and a number reported only once `parseDecimalInput` finds a whole one — `null` means «not yet», which is what lets «0.», «-» and «» exist on the way to a figure. It accepts Persian digits and `٫`, rejects a keystroke that could never become a number, and resyncs the box on blur so a clamped figure shows the cap. The rules are pure in `src/utils/numberInput.ts`; `test:rules` covers them and `test:ui` types a decimal one keystroke at a time through the real DOM node — jsdom implements the same sanitisation, so driving the handler with a made-up `{value}` would skip the very step under test.

**A modal must not seed its state from an object prop.** `useEffect(..., [initialValues])` where the parent builds `initialValues` inline re-seeds on *every* render of the screen behind the modal — and those screens re-render on their own, so a half-typed form was silently reset to zero, repeatedly. Key the seeding on what means "start again" (open, and the subject's id) and read the values through a ref. `npm run test:ui` renders the price calculator and asserts a typed figure survives a parent re-render.
- **Shallow-copying arrays of records is a trap.** `const next = [...items]; next[i].field = x` mutates the objects the store still holds, which made before/after comparisons identical — that silently stopped SKU stock changes from being logged as inventory transactions and corrupted audit-log snapshots. Always replace the element: `next[i] = { ...next[i], field: x }`.
- Persian text in **console/CLI** output is mangled by the Windows console codepage, so `scripts/*.ts` print English. JSON API messages stay Persian (they render correctly over HTTP and are shown to users).
- Windows PowerShell 5.1 doesn't enable TLS 1.2, so GitHub downloads fail until `[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12` is set.
- **`DATABASE_URL` is a JDBC-style string, not a URL.** `sqlserver://host:1433;database=…;user=…;password=…` — do **not** percent-encode the password: `%40` is read literally and fails with `P1000`. Only `; = { }` need escaping, by wrapping the value in braces.
- **`GO` is not T-SQL and must never appear in a migration.** It is sqlcmd's batch separator, and `prisma migrate deploy` hands each statement to the driver on its own — so a `GO` between them is parsed as an identifier and the whole migration dies with «Incorrect syntax near 'GO'», taking the deployment with it (`deploy.ps1` stops and restores the previous build, so the running app is unaffected, but nothing ships). That is not hypothetical: `20260903000000_activity_messenger` shipped with them and failed on the server. Separate statements with a **blank line**, which every other migration here does; `20260901000000_sales_follow_up` is the proven shape for the awkward case — a column added, then indexed, then given a foreign key, all in one file. `test:rules` now fails any migration carrying a bare `GO`. **The other half of the same trap is a column read in the batch that adds it**: SQL Server resolves column names when it *compiles* a batch, before running any of it, so a plain `UPDATE … SET [newColumn]` in the file that adds `newColumn` dies with «Invalid column name» (207) even though the `ALTER` is above it — and even though `IF COL_LENGTH(…) IS NULL` guards it, because the guard is evaluated at run time and the compile has already failed. `20260906000000_holiday_calendar_kind` shipped that way and stopped the deployment. **DDL is not affected** — `CREATE INDEX` on the new column compiles when it executes, which is why five migrations here write those plainly and have always worked — so what must be deferred is the DML, wrapped in `EXEC(N'…')` the way every backfill in this tree already does it (`cost_of_goods`, `customer_value_ranking`, `proforma_sent_date`). `test:rules` reads every migration for it, with the EXEC literals removed by the T-SQL string rule `'(?:[^']|'')*'` — a backfill's doubled quotes and its semicolons are both inside one — and the predicate held against the plain, the wrapped and the index-only shapes so it cannot pass by matching nothing. A migration that fails half way leaves the statements before the failure applied, which is the other reason every step is guarded (`IF COL_LENGTH(...) IS NULL`, `IF NOT EXISTS (SELECT 1 FROM sys.indexes ...)`): the retry has to be safe. Prisma records the failure and refuses to go on until somebody runs `npx prisma migrate resolve --rolled-back <name>`.

- **`sqlcmd` connects with `QUOTED_IDENTIFIER OFF`**, and SQL Server refuses to create filtered or computed-column indexes in that state (`Msg 1934`). `prisma/sql/extra-indexes.sql` sets it explicitly; pass `-I` as well when running SQL by hand.
- **A second instance on another port is not an isolated one.** `PORT=3100 npx tsx server.ts` still reads `DATABASE_URL` from `.env`, so any endpoint you exercise writes to the **real** database. Point `DATABASE_URL` at a scratch database, or clean up what the test created and assert the counts back to zero.
- **Git Bash mangles Persian in `curl -d`** — the UTF-8 arrives as `?????`, which then looks like an application bug (e.g. `mobileNormalized` coming back `null`). Drive HTTP tests from a Node script using `fetch` instead of composing them in the shell.
- npm blocks package install scripts by default here. That was harmless for `esbuild` (its binary arrives via optionalDependencies) but **not** for Prisma, whose engines come from its install script — approve with `npm approve-scripts` and `npm rebuild` if Prisma commands fail.
- **A migration that has shipped is history — never edit it.** Prisma records a migration by *name* and never runs it again, so amending an applied one reaches every repository and no database. This is not hypothetical: `discountAmount` was added to `20260808000000_inquiry_discount` after that migration had run, so `discountPercent` existed and `discountAmount` did not, and the whole supplier-inquiry module answered P2022 — "The column `discountAmount` does not exist in the current database" — on every read and write, while `_prisma_migrations` listed every migration as applied. Add a new migration instead, guarded with `IF COL_LENGTH(...) IS NULL` so it is safe on databases built after the amendment. `src/server/schemaCheck.ts` now verifies the *columns* the migrations create, not just their names, because names alone cannot see this.
- **`npx prisma migrate dev` cannot run here** — the SQL login has no `CREATE DATABASE` right, so the shadow database fails with `P3014`. Write the migration SQL by hand (see `prisma/migrations/20260803000000_*`) and apply it with `npm run db:deploy`. `migrate diff` is also unhelpful: it wants to re-create ~18 DEFAULT constraints that introspection does not report, burying the real change.
- **`assertComplete` cannot see a handler that builds a fresh object.** The partial-record guard fires on a list row *spread* into a write payload, so a handler that reads a row and constructs a new literal slips past it — `handleCopyProforma` copied a proforma from the grid row, whose lines carry only name, quantity and status, and the new document came out with no prices, no product ids, no specs and no costs. What surfaced was the cost check refusing the save, naming lines whose cost was filled in perfectly well on the document being copied. Any handler the grid calls with a row must load the detail record itself (`isPartial` → `api.get(id)` → `detailTo…`), the way `handleOpenPrint` does; `test:rules` pins both.
- **A cast is not a check.** The client adapters end in `as unknown as Product` and friends, because the client types carry fields a list row does not. That means a wrong field name inside the object literal compiles cleanly and fails at runtime — three separate bugs reached the browser this way (`calculatedLandedCostRIYAL`, `calculatedLandedCostForeign`, and `useUserDirectory()` returning `{ users }` rather than an array). Open the screen; a green type-check proves less here than usual.
- **Ids belong to the database, and a line's `productId`/`variantId` is a real foreign key.** The proforma configurator auto-created a SKU, gave it `var-${Date.now()}`, saved the product *without awaiting it* and put its own id on the line — but `reconcileVariants` assigns the id on insert, so the line referenced nothing and the whole proforma failed with P2003. `sendError` mapped that to «این رکورد … قابل حذف نیست», which describes a delete the user was not doing. Three things now hold it: `src/server/refIntegrity.ts` (`scrubProductRefs`) drops a dangling reference so the document still saves, `sendError` answers a non-DELETE P2003 with "one of the selections no longer exists", and `test:rules` reads the source for both — every line-writing service must scrub, and no screen may write a made-up id onto a foreign key.
- **After-commit side effects must never fail the request.** The audit entry, the notification, the workflow rules and the project timeline run *after* the write transaction on purpose — but they were awaited plainly, so anything one of them threw came back out of the route as a failed save: the record existed, its document number was taken, and the user made a second one. `src/server/afterCommit.ts` logs and swallows. Same rule as `milestoneAutomation.ts`.
- **An uploaded folder name must be Latin.** `/api/upload`'s `folder` query param is sanitized with `[^a-zA-Z0-9_-]`, so a Persian name reduces to an empty string and the file lands in the uploads root instead — silently. The Persian folder names users see (the project documents tab) are a *logical* grouping stored on the record as `manualDocuments[].folderName`, not directories; the two are unrelated. Customer satisfaction letters show the pattern: logical folder «رضایت‌نامه‌ها», physical folder `satisfaction-letters`. `src/server/uploadsDir.ts` owns `UPLOADS_DIR` and is the only place that maps a `/uploads/...` URL back to a path — `resolveUploadPath` returns null for anything outside it, which is what stops the letters zip from being asked for arbitrary files.
- **A "kind" tag identifies a document, not its name or folder.** Both `projectConfirmation` and `satisfactionLetter` are entries in a project's `manualDocuments` JSON marked with `kind`, because a user may rename a file or move it between folders — so neither can stand in for what the document *is*. `src/server/services/satisfactionLetters.ts` reads them back with a `manualDocuments: { contains: kind }` pre-filter (a cheap `LIKE` that SQL Server can run) and then parses each candidate, which is the authority. That screen deliberately answers with the whole filtered set rather than a page: its amount filter is computed from won proformas and Prisma cannot put a relation count in a `where`, so paging first would filter the wrong set. The whole-set work happens on the server, bounded, with a `truncated` flag rather than silently dropped rows.
- **Customer value is two axes and a matrix, never an average.** `src/utils/customerValue.ts` is the rule and is pure: *Realized* (gross profit 50, frequency 20, recency 15, payment 10, cost-to-serve 5) and *Potential* (five 1–5 judgements weighted 30/20/20/20/10), each 0–100, and the A/B/C/D rank comes from the **matrix** of the two against `highRealizedThreshold`/`highPotentialThreshold`. `CVI = realized×0.6 + potential×0.4` orders customers *within* a rank and must never decide one — a new customer with no history and high potential has to come out C, and averaging first calls them D. A customer whose five potential answers are not all filled in is `PENDING`, not zero: unknown is not low. **A customer who has never had a confirmed purchase is `PROSPECT` («مشتری بالقوه») and gets no rank at all** — half of A/B/C/D is a judgement about money that has changed hands, so ranking a lead puts them at D, "low value, low priority", which is backwards for an account the sales team is working on. `determineRank` takes `hasConfirmedPurchase` as a **required** argument so the type-checker names every call site, and checks it *before* the potential assessment (an unassessed prospect is still a prospect). Their stored `realizedValueScore` is 0 and `customerValueIndex` is null — not a low score but an inapplicable one, since payment and cost-to-serve are 15 points of manual opinion about somebody who has never paid an invoice — and they are sorted by potential instead, excluded from the matrix and from the population averages. The signal is `hasEverPurchased`, which reads `lastPurchaseDate` (**every** sale ever) and never `purchaseFrequency` (the evaluation period only): a customer who last bought three years ago is *lapsed*, not a prospect, and their recency score already says so. The first confirmed sale moves them into the matrix with no other change, through the recalculation the write already schedules. `test:rules` covers all ten acceptance scenarios plus this rule. Weights must total exactly 100 or the settings refuse to save — they are the divisor of a weighted average, so 90 would deflate every score by a tenth and the whole table would drift down a rank together.
- **Where the sales figures come from.** A sale is a proforma whose outcome is won or part-won (`getProformaOutcome`, so a cancelled document with `برنده` lines is not one); one proforma is one purchase however many lines it has; **the sale's date is the project's `winningDate`** — «تاریخ تایید (ابلاغ قرارداد)», stamped when the project first becomes won — falling back to the proforma's `issueDate` only when there is no project or none was stamped (`saleDateOf`). Not the issue date: a quotation written in Farvardin and approved in Mehr is a Mehr sale, and that gap is routine here, so the issue date puts the sale in the wrong evaluation period and makes the customer look months staler than they are — 2 months against 8 in the covered case, which is two whole recency bands. Because the effective date can come from the project, the evaluation window **cannot be a SQL `where`** on `issueDate`: `collectRawFigures` scans candidates cheaply, lets `saleDateOf` decide what falls in the period, then reads only those in full. **Cost of goods is now a column on the sale line** — see the entry below; the two older sources survive only as fallbacks for rows written before it, and a line with none of the three is left out of **both** sides of the margin rather than counted as pure profit, with `costCoveragePercent` recording how much of the revenue could be costed so a suspiciously good margin reads as missing data. Gross profit and frequency are **percentiles against customers active in the period**, so they are meaningless alone and one customer's sale moves everyone else's score — which is why there is no correct way to recalculate a single customer, and why `recalculateAll` is the only real entry point. Writes schedule one through `customerValueRecalc.ts`, which coalesces and can never fail a save; a daily job ages recency on.
- **Every proforma line carries its own cost.** `ProformaItem.unitCost` / `costCurrency` / `costSource` are the home of record, and a save is **refused** — client and server both, `assertLinesCosted` in `proformaService.ts` — if any line has neither a figure nor an explicit «بدون بهای تمام‌شده». The rules are pure in `src/utils/costOfGoods.ts` and covered by `test:rules`. Four things force the design: a product's cost changes, so looking it up when a report needs it rewrites last year's profit and re-ranks customers who bought nothing since; a free-text line has no product to look anything up from; `PurchaseOrderItem.proformaItemId` is a plain column that `syncChildren` orphans on the next save; and an uncosted line reads as **pure margin**, which flatters exactly the sales nobody bothered to cost. The figure is in the **proforma's own currency**, matching `unitPriceRial` beside it — that is what makes the margin *percentage* independent of the exchange rate, and it is why `handleCurrencyChange` must convert cost and price together. `costSource` distinguishes evidence (`PURCHASE_ORDER`, `PRICE_CALCULATOR`) from assertion (`MANUAL`), a deliberate zero (`NONE` — a service line, or goods the customer supplies) from a blank, and the migration's own guess (`BACKFILL`). **A received purchase order corrects the estimate** — `pushActualCostToProformaLines` in `purchaseOrderService.ts` writes the real landed cost onto the lines it supplied, but only where the stored source was never a person's answer (`null`/`PRICE_CALCULATOR`/`BACKFILL`/`PURCHASE_ORDER`; `MANUAL` and `NONE` are left alone). It sums across **every** received order pointing at that line, so a split purchase blends by quantity and re-saving writes the same figure; un-receiving does not restore the guess. It schedules a customer-value recalculation, because the gross profit behind those ranks has moved. `NONE` storing a real zero rather than a null is the whole reason the check can tell "there is no cost" from "nobody has got to this yet". Two screens capture it: the line grid on the proforma form, and the **outcome modal** — a line marked won with no cost is the one that corrupts the ranking, so that table has a cost column too and legacy documents get answered there rather than dead-ending on save. A technical proforma quotes no prices and is exempt at both ends. `TransactionsView`'s rate-only write deliberately **omits `items`** so it does not have to pass the check.
- **The proforma line's price calculator loads the whole product; the screen only has list rows.** A product `LIST_SELECT` carries no `priceCalc`, and its variants come back with an id, a SKU, attributes and a stock level and nothing else — so seeding the modal from `productPicker.matches` opened every field blank however carefully it had been filled in last time, and the missing starting foreign price made it recompute and *change* the price on apply. The record is read when the modal opens (which also means the figures are what the catalogue holds now, not what the picker fetched at page load), and the modal does not render until it has arrived — opening on zeros is the bug, not a loading state. Same family as the proforma number, the settlement rate and «پ.ف: ناشناس»: a screen must not resolve a record out of a picker's matches.
- **The price calculator has a manual mode.** `PriceCalcInputs.mode` (`BREAKDOWN` | `MANUAL`, absent = BREAKDOWN so every stored record keeps computing as before). Not every item is imported: goods bought locally or quoted all-in have a cost that is simply known, and forcing that through a freight-and-customs breakdown meant inventing figures or leaving the cost blank. Both figures are entered in the **item's own currency**. The modal's `onApply` now hands the caller the landed cost alongside the selling price — it used to compute it and throw it away, which is how proforma lines came to keep the price and lose the cost that produced it. `calcSeedOf` in `productAdapter.ts` is the single list of calculator fields, shared by the modal's seeding and by what gets persisted (`PRICE_CALC_KEYS`, guarded by `_EveryCalcFieldIsPersisted`); spelling the fields out at a call site is how one comes to be collected and then dropped. **`landedUnitCostOf` in `costOfGoods.ts` is the single reader** of a stored calculator — the proforma form's suggestion and the customer-value fallback each had their own copy and had already drifted, the server inheriting the product's calculator for a SKU with none of its own while the client did not. A SKU's own figures win; one with none inherits the product's.
- **A catalogue item has one currency, and every SKU under it follows.** Changing `currencyForeign` on the product form rewrites all its variants; `ProductVariant.currencyForeign` is a copy, never an independent choice. The price calculator, though, runs in whatever currency it is opened in — often the proforma's — so writing its result onto a SKU together with *its* currency put that SKU out of step with its product, and since the form reads the **product's** currency the figure then displayed as if it were in a currency it was never in (150 دلار stored against a یورو product read back 15,000,000 rial instead of the 13,500,000 agreed). The rial column stayed correct, which is why it went unnoticed. `priceInWarehouseCurrency` in `src/utils/finance.ts` converts before the write and the currency is restated rather than replaced, which also repairs a SKU that had already drifted; it returns null when no rate is known, because the original number under the wrong label is the bug itself. Anything reading a SKU's currency must fall back to the **product's**, not to a hardcoded «یورو». **A price typed by hand into a proforma line does not reach the catalogue on its own** — a deal price is usually specific to that deal, so one negotiation must not rewrite the list price for everybody. `publishPriceToWarehouse` is the explicit button beside each line, deliberately the same gesture as the calculator's «اعمال»; it converts to rial at the document's own `historicalExchangeRate` (today's rate only as a fallback) and refuses rather than guessing when neither is known.
- **What an item last really cost is recorded beside the standard, never into it.** `Product`/`ProductVariant` carry `lastPurchaseCostRial`, `lastPurchaseQuantity`, `lastPurchaseDate(Jalali)`, `lastPurchaseOrderId`/`Number`, written by `recordLastPurchaseCost` when a purchase order is received. They are **not** `priceCalc`: the calculator holds the *standard* cost the company quotes from, while a line's share of an order's landed total carries the freight and customs of **that shipment** — five units flown in urgently genuinely cost several times what two hundred by sea do, so writing one into the other would price every future quotation off whichever delivery arrived last. The quantity is stored precisely so the screen can say how representative the figure is. Written from the **most recent received order** per position rather than from the order being saved, so re-saving a months-old purchase cannot overwrite a newer figure and saving twice writes the same thing. Neither `productScalarData` nor `variantScalarData` lists these, so a product save can never touch them; they are in `PRODUCT_COST_FIELDS` so a user without `costs` sees none of it, order number included. `costDrift`/`COST_DRIFT_THRESHOLD_PERCENT` in `costOfGoods.ts` decide when the gap is worth showing, and `LastPurchasePanel` shows it. **Adoption is a button, and the selling price never moves on its own** — `sellingPriceFor` only *displays* what the stored margin would imply, because a supplier's rise is not automatically the customer's. Open tasks were filtered against a hardcoded `new Set(["انجام شده", "کنسل شده"])` — which happened to be right, but only by luck: every automation writes «در انتظار», a fourth value no dropdown ever offered, and the next status nobody anticipates would have been counted as finished. It is `taskLane(status) !== "DONE"` now, the board's own rule and an exclusion, so an automation-raised task, a sales follow-up and a task somebody logged for themselves are all counted deliberately rather than incidentally. The other half was a real gap: referrals were asked for with `scope=toMe`, so a request this user **raised** and is waiting on sat on their own board under «من ارجاع دادم» and in nobody's count. `scope=mine` is both directions — `{ OR: [{ assignedToUserId }, { assignedByUserId }] }`, the same two people `visibilityClause` says a task belongs to — and it is a *new* scope rather than dropping the filter, because `listReferrals` with no scope answers with the whole company's referrals for anybody holding the projects permission. **The header carried the same number twice, as two halves.** The inbox icon counted only the referrals and the calendar beside it counted only the tasks — two icons, neither of which answered «چقدر کار روی دستم مانده». `openWork` is the sum, made once in `useSidebarBadges` and drawn by both the sidebar's «وظایف و پیگیری» badge and the inbox icon; the calendar has no badge at all, because it is a way of *looking* at the work rather than a second count of it. **And it counts the work assigned to you, not the work you handed out.** Both records belong to two people, and both halves appear on your own board, so which one a badge should count is a real question — it is the assignee's: a badge on an inbox answers «چقدر کار روی دستم مانده», and a request raised *for a colleague* is on their plate rather than yours. Both halves were wrong in the same way and for different reasons: the referrals asked for `scope=mine` (both directions, deliberately), and the tasks asked `/api/tasks/summary` for nothing at all — so `visibilityClause`, which is «assigned to me **or** raised by me», was the only narrowing there was. Both ask for `toMe` now, and `taskSummary` takes a scope, applied *on top of* the visibility rule and never instead of it. `mine` is still a scope and still right for the board's «همه» view and for the assistant; it is simply not what a badge means.
- **A request is a label on the message, and answering it is the feed's own reply.** The project feed drew each referral as a panel *under* the message, headed «اقدام خواسته‌شده» and quoting the very sentence two lines above it, with a compose field of its own — the request said twice and answered in a second place. The message and the mention already say who is being asked and what for, so all that is left is where it has got to: a chip per request naming the assignee and its status, plus one press for either party to close or reopen it through `referralStatusForLane` (the board's own mapping, so the two screens cannot disagree about what a column means). A status nobody can move from the screen they read it on is a status nobody moves. **The reply is the answer**: `addActivity` mirrors a reply into the thread of every open request on the parent that the author is a party to, **inside the message's own transaction** — a reply that reached the feed and not the referral leaves the person who asked looking at «در انتظار اقدام» under a message that plainly answers them. Either party may write into the thread (whoever raised it reads the answer in the feed and says there that it is not what they asked for), but only the **assignee** replying moves the status to «در حال اقدام»; somebody chasing their own request has picked nothing up, and a request already done is never reopened by a reply. The notice goes to the counterpart, because the message's own notices reach the category's members and the people it names and the person who raised the referral is usually neither. And **editing the message edits the requests it raised** (`updateMany` where `actionRequired` still equals the old text): the request *is* the message, one text and not two, but only one copy was being rewritten — survivable while the feed printed the referral's text beside it, and invisible now that it prints only a status.
- **«باز» is not one status, and comparing against one hid the button that closes a referral.** `ReferralThread` read `status === 'در انتظار اقدام'`, which was the whole truth until the merged board gave a referral a middle state — so the moment anybody picked one up, «ثبت اتمام کار» vanished for the assignee and «ثبت پاسخ و ارجاع مجدد» appeared for the referrer against a referral that was not finished, leaving no way to close it from the thread at all. That is exactly how it was reported. `referralIsOpen` — the same exclusion the inbox badge and `laneWhere` use — is the rule everywhere now, and `test:rules` fails the literal reappearing in either screen. The inbox had the same fault three more times: it sorted picked-up referrals down with the finished work, counted them as done, and drew a badge that chose between two words and so could not say the middle state at all.
- **A product carries its own literature.** `images` answers «what does it look like» and nothing else; what a sales engineer reaches for when quoting is the manufacturer's catalogue and the item's datasheet, and those had nowhere to live — so they sat on somebody's desktop or were attached to whichever project happened to need them first. `Product.documents` is `[{name,size,url,kind}]` in one JSON column rather than a table: it is a short list, never queried across products, and a table would be a join on every read of the catalogue. `src/utils/productDocuments.ts` is the only reader and writer. **The kind is chosen before the file is picked**, because a person renames a file and moves it between products and the kind is what the screen groups by — the same reason a project's `manualDocuments[].kind` exists. Three rules `test:rules` holds: an entry with no URL is dropped (the name alone points at nothing and would put a dead link on the product), the same file picked twice is one, and **an unknown kind becomes `OTHER` rather than being discarded** — the list may gain an entry and lose one, and a file filed under a kind that no longer exists is still the file somebody uploaded. The upload names the folder `product-docs`, in Latin, because `/api/upload` sanitizes it with `[^a-zA-Z0-9_-]` and a Persian name reduces to an empty string and lands the file in the uploads root, silently. A copy of a product carries the documents: both records point at the same `/uploads/...` path, which is what a shared datasheet actually is.
- **A form has one scrollbar.** A list that scrolls inside a modal body that scrolls is two, and the inner one is a window onto a list whose shape the reader cannot see — the reported case was the supplier inquiry's goods table, capped at `max-h-80` inside a `max-h-[75vh]` form. Every such inner container inside a form is gone: the inquiry's goods, the purchase order's item rows, the user form's permissions grid, the customer form's linked-customer checklist, the quick-add relationship selector, the project's milestones and automation rules, the required-fields list in Settings. **Horizontal is a different axis and stays** — the goods table is 950px wide and has to scroll sideways whatever the height is. Deliberately kept: every absolutely-positioned popover (`SearchableSelect`, the mention list, the reaction picker, the autocompletes), which is not part of the form's flow and has to cap a list of five hundred options; and the modal bodies themselves. `test:rules` scans each of those files for a line carrying both `overflow-y-auto` and a `max-h-`, excluding popovers and the body itself — **and asserts the outer body still scrolls**, because a screen "fixed" by removing that one would clip the form instead.
- **A category has members, and being a member is the quiet half of being named.** The feed became a messenger and had no membership: the only way to reach a colleague was to name them, which raises a **referral** — an explicit request with an action and an inbox of its own. That is right for «لطفاً دیتاشیت را چک کن» and wrong for «بار از گمرک ترخیص شد», which the people working the job want to *know* without being asked to do anything. `ProjectCategoryGroup.memberUserIds` is that second thing: a notice per message, no referral, no action. It is **per project and per category** — the people involved in «خرید» on one job are not the ones involved in it on the next — which is why it is not `settings.activityCategories[].responsibleUserId`, a different question (who owns this kind of work in the company) that is untouched. `src/utils/activityMembers.ts` holds the rules and `test:rules` covers them. `activityRecipients` excludes three sets and each one is the difference between a feature people keep on and one they mute: **the author** (`notifyUser` already makes that exception), **anybody the message named** (their referral notice says strictly more, and two notices for one message teaches people to dismiss the pair), and **an account that has since been deactivated** — filtered on save *and* again on send, because a stored list is not rewritten when somebody leaves. **Absent means «not edited»** all the way from the route to the column: `upsertCategoryGroup` is also what the date editors and the «اتمام کار»/«بازگشایی» buttons call and none of them sends a member list, so reading absent as «nobody» would empty the membership every time a category was closed; the client likewise sends the key only when it is what changed, or a date edit would write the screen's copy back over somebody else's. The notice is its own `afterCommit` block, so a failure there cannot stop the mention notices somebody is waiting on.
- **A message can be answered with one press, and it says who has read it.** «دیدم», «موافقم», «ممنون» should not cost a message of their own — a job's history is read top to bottom and a column of one-word replies buries the work in it. `src/utils/reactions.ts` holds the six allowed reactions and `summarizeReactions`; `MessageReactions` draws them and the eye. Four things decide the shape. Both are **one row per person** (`activity_reactions`, `activity_reads`) and never a JSON column on the message: two people reacting in the same instant would be a read-modify-write race, and the unique indexes are what make «press it again to undo» and «mark it read again» things the database settles. The emoji is **allowlisted on creation only** — it is rendered on everybody else's screen so it is checked coming in, but a value stored before the list changed still renders rather than vanishing from under whoever left it. The reactions travel with the feed and the readers do **not**: `_count.reads` is what the eye draws, and the names are one request away (`listActivityReaders`), because every reader of every message would be the largest thing in a feed response and nobody looks at more than one at a time; `test:ui` asserts the eye fetches nothing until it is pressed. And **a receipt is written only for what is on screen** — every category arrives with the feed and each is folded until somebody opens it, so the *screen* passes the expanded groups' ids and the hook deduplicates them per session; posting it also uses `api.postQuietly`, because announcing it would make the feed re-read itself and the re-read is what posts the receipts. The author is never recorded against their own message: «چه کسانی دیده‌اند» answers «did this reach anybody», and they are not an answer to that.
- **The feed reads oldest-first and the category list newest-first, deliberately opposite.** A conversation is written downwards, so the newest message sits directly above the box you reply in — reversed, a reply appears above the message it answers. Categories are not a conversation: they are the parallel strands of work on one job, and the one opened most recently is the one being worked, so an old finished category must not sit between the reader and it. Both orders are in `listCategoryGroups`'s single query and the screen renders them as they arrive (the composer is drawn below the list, which is what puts the newest message beside it); `test:rules` pins both, because flipping either back is a one-word edit nothing else would notice.

- **A referral is a conversation, drawn by one component in both places it appears.** `ReferralThread` renders the request, the replies and the box to answer in; the referrals screen and the project's activity feed both use it, because the answer to a referral is usually read in the feed and that was the one place it could only be *read* — somebody who found the reply was not what they asked for had to go to the other screen to say so. Messages are sided **by account id** (`responderUserId` against `assignedByUserId`), never by display name: a renamed account put its whole side of the conversation back on the other one, the same trap the two ids on the referral itself exist for. The compose area sits below a rule, because everything above it happened and a draft in the same column reads as something already said. **The three server calls are `submitReferralReply` in `src/api/inbox.ts`, in one order** — reply, then a *silent* status change (the reply already told the other party the part that matters), then the forwarding, which sets its own status and so replaces the outcome rather than adding to it; a bare «اتمام کار» with nothing typed is a status change on its own, and an empty send is refused. `test:rules` stubs the three routes and holds the sequence. **The request itself is editable, by the person who raised it and nobody else** (`updateReferralAction`): the assignee rewriting their own instructions is how a referral gets marked done against a request nobody made, and the assignee is notified that it moved.

- **Module notes are their own table** (`/api/notes/:entityType/:entityId`), never a column. Folding a note into the record and saving the record discards it silently — which is exactly what happened on two screens.
- **`compressLZW` output format changed.** It now emits `[alphabet, codes]`. The old encoder seeded its dictionary with char codes 0–255, so every Persian character produced `undefined` → `null`, and every audit snapshot ever taken was unrecoverable. Old entries decode to empty rather than to garbage.
